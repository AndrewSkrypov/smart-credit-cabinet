# Умный кредитный кабинет — план решения (Альфа Хак 2026)

## 1. Что на самом деле оценивают

Из кейса (стр. 6–15) жюри смотрит не на «красивую анкету», а на **связанный конвейер**:
клиент → заявка → проверка полноты → обогащение (ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», БКИ)
→ скоринг → **кредитное решение (не бинарное!)** → оффер → подписание → выдача (смоделированы).
Данные сохраняются, статус меняется последовательно и виден клиенту в реальном времени.

Критерии → чем закрываем:

| Критерий | Чем закрываем |
| --- | --- |
| Целостность | Один сквозной путь «от потребности до денег», без заглушек-экранов |
| UX | Мастер потребности → подбор продукта; «что сейчас происходит и что от вас нужно» на каждом статусе |
| Согласованность модулей | Единый объект заявки, конечный автомат статусов, журнал событий, данные клиента вводятся один раз |
| Enterprise | Гексагональная архитектура, JWT deny-by-default, outbox, идемпотентность, оптимистичные блокировки, retry/circuit breaker, аудит, версии правил |
| Потенциал | ADR-ы: почему так, ограничения, путь к Kafka/ML-скорингу/реальным интеграциям |
| Готовность к проверке | `docker compose up` одной командой, тестовые ИНН под каждый исход, README со сценарием, Swagger, Postman |

Жёсткие ограничения, которые легко пропустить:
- **LLM — только открытые веса.** Адаптеры Anthropic/Gemini из ТРЕКа в сдаваемую версию не попадают → Ollama + Qwen2.5/Llama 3.x.
- **Никаких платных API** и корпоративных систем — все внешние источники = локальные симуляторы.
- **Почта/SMS/мессенджеры не участвуют в сценарии** — уведомления только в продукте (колокольчик + лента событий заявки). `platform-mail` не берём.
- Только веб, не мобильное приложение (адаптив при этом нужен).
- GitHub (не GitLab), тег версии на дедлайн, доступ для `alfa-hack-2026`.
- Обязательно: README, THIRD_PARTY_NOTICES, архитектурная схема, OpenAPI, коллекция запросов, диаграмма состояний, модель данных, тестовые сценарии, lock-файлы.

## 2. Что берём из ТРЕКа (sbertrack-platform)

Паттерны подходят почти полностью — это ровно то, что жюри называет enterprise-ориентированностью.

| Из ТРЕКа | Как используем | Правки |
| --- | --- | --- |
| `build-logic` + `gradle/libs.versions.toml` | Сборка, версии, ktlint, BOM-оверрайды = «фиксация версий» | Добавить Resilience4j, Testcontainers |
| `libs/platform-common` | Ошибки (`ApiException`, `GlobalExceptionHandler`), JWT (`JwtVerifier`, `TokenClaims`), deny-by-default, RequestId, OpenAPI | Переименовать пакет, в claims роль банка и `companyId` |
| Гексагональная структура `domain/model · domain/port · application · infrastructure · controller` | Все новые модули | — |
| Доменная модель с охраняемыми переходами (`Submission.submit()/review()`) | Основа `LoanApplication` — переходы только через методы с `require` | Вынести таблицу переходов в явный автомат + журнал |
| Условные адаптеры (`AgentGatewayMockAdapter` + `*KeyPresentCondition`) | Интеграции ЕГРЮЛ/ФНС/БКИ: порт + HTTP-адаптер к симулятору; LLM-порт: Ollama или детерминированный fallback | Anthropic/Gemini → Ollama (OpenAI-совместимый API) |
| `PlatformNotifications` (после коммита, в фоне) | Уведомления в колокольчик | Для конвейера — настоящий transactional outbox (см. ниже) |
| `services/identity` | Вход, роли, блокировка перебора, согласие 152-ФЗ | Пользователь ↔ компания (собственник, бухгалтер), роли банка |
| `services/file` | Загрузка документов: сверка сигнатуры с расширением, лимиты, throttle, MinIO/локально | Типы документов, привязка к заявке |
| `services/community` (notification) | Центр уведомлений | Только уведомления, мероприятия/новости не берём |
| `services/mentor` | Каркас ИИ-ассистента (сессии, сообщения, мастер-промпты) | Новая специализация «кредитный помощник» + RAG по продуктам |
| `docker/service/Dockerfile`, `docker/gateway/nginx.conf`, `docker-compose.yml` | Как есть: один Dockerfile, gateway по путям, healthchecks, non-root | Меньше сервисов, профиль `ai` для Ollama |
| `frontend`: `api/client.ts`, `useApi`, `EmptyState`/`ErrorState`, `PageHeader`, `RoleGuard`, `AppShell` | Каркас SPA | Дизайн — в конце, под новый стандарт |
| `e2e` (Playwright, desktop + mobile) | Сквозной сценарий «заявка → деньги» как автотест = доказательство работоспособности | Новые спеки |
| `AuthorizationTest`, правило «чужое — 404, нет прав — 403» | Тест доступа на каждый эндпоинт | — |
| Flyway «только новые миграции» | Как есть | — |

Не берём: catalog, submission, trajectory, core-агрегатор, Helm/k8s и GitLab CI (заменяем на GitHub Actions: build + test + Trivy), `platform-mail`.

**Важно про «никаких выдуманных данных».** Правило остаётся, но кейс требует синтетику: отдельный
набор сидов с пометкой «синтетические данные» в интерфейсе симуляторов и в README. Цифры в
аналитике и скоринге — только вычисленные из реальных записей системы.

## 3. Целевая архитектура (облегчённая)

8 сервисов по 640 МБ жюри на «обычном ПК» не поднимет. Берём 4 + инфраструктуру (~3 ГБ без ИИ). Отдельный file-сервис не нужен: документы компании нельзя отдавать по ссылке без проверки прав, а права на заявку знает credit, поэтому документы — модуль credit (подробнее — [docs/architecture.md](docs/architecture.md)):

```
frontend (React SPA, nginx)
   │
gateway (nginx)  ── /api/v1/auth, /users ─────────────▶ identity      (пользователи, компании, роли)
   │             ── /api/v1/applications, /products,
   │                /underwriting, /rules ─────────────▶ credit        (заявка, автомат, конвейер, скоринг, решение, документы)
   │             ── /api/v1/notifications, /assistant ─▶ engagement    (колокольчик, ИИ-ассистент)
   │
credit ──HTTP (Resilience4j: timeout, retry, CB)──▶ external-sim (ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», БКИ, ПЭП-подписание, АБС-выдача)
engagement ──▶ ollama (profile ai, открытые веса)
PostgreSQL (база на сервис) · том для документов (адаптер S3 из ТРЕКа — когда понадобится несколько экземпляров credit)
```

Почему `credit` один сервис: автомат заявки, конвейер, скоринг и решение меняют один агрегат
в одной транзакции (тот же довод, что у submission+portfolio в ТРЕКе). Внутри — отдельные модули
`application`, `pipeline`, `scoring`, `decision`, `offer`, `underwriting`; вынести можно позже.

Почему `external-sim` отдельный сервис: так интеграции честные (сетевой вызов, контракт, таймаут,
недоступность), а в README пишем «смоделированная интеграция» — ровно как просит кейс.

## 4. Модель процесса

### Роли
- **Клиент** (пользователь компании): собственник/директор, бухгалтер, уполномоченный — у компании несколько пользователей, заявку видят все сотрудники компании.
- **Кредитный менеджер** — проверка полноты, запрос недостающего, связь с клиентом.
- **Андеррайтер** — ручное рассмотрение нестандартных заявок, контрпредложение.
- **Администратор рисков** — продукты, пороги правил (с версиями), аналитика воронки.

### Статусы заявки
Полная диаграмма, таблица переходов и инварианты — [docs/state-machine.md](docs/state-machine.md).
```
DRAFT → SUBMITTED (проверка полноты) ⇄ INFO_REQUESTED
      → ENRICHMENT (ЕГРЮЛ, ФНС, БКИ; источник недоступен → повтор)
      → SCORING → OFFER_ISSUED (вид оффера: APPROVED / COUNTER) | MANUAL_REVIEW | REJECTED
MANUAL_REVIEW → OFFER_ISSUED | INFO_REQUESTED | REJECTED
OFFER_ISSUED → SIGNING → DISBURSING → DISBURSED;  отказ/истёк срок → CLOSED
WITHDRAWN — клиент отозвал на любом шаге до подписания
```
Каждый переход — запись в `application_events` (кто, когда, из какого статуса, причина) → это и
аудит для банка, и лента «история заявки» для клиента.

### Конвейер (enterprise-часть, которую стоит показать на защите)
- Отправка заявки идемпотентна (`Idempotency-Key`), агрегат с `version` (оптимистичная блокировка).
- Шаги конвейера — задачи в таблице `pipeline_jobs` (transactional outbox + воркер с `FOR UPDATE SKIP LOCKED`). Без Kafka, но с тем же гарантированным выполнением; в ADR — путь к брокеру.
- Вызовы симуляторов — Resilience4j (таймаут, 3 повтора с backoff, circuit breaker). В симуляторе переключатель «сломать БКИ», чтобы на демо показать: заявка не падает, ждёт и продолжает.
- Снимок входных данных и версия правил сохраняются в `decisions` — решение воспроизводимо.

### Скоринг и решение (разделены, как требует кейс)
1. **Стоп-факторы** (knockout): компания ликвидируется/в процессе банкротства, недостоверный адрес/руководитель, активная просрочка > 90 дней, бизнесу < 3 мес.
2. **Балльная карта** (прозрачная, ~8–10 факторов): возраст бизнеса, выручка и её стабильность, долговая нагрузка (обязательства/выручка), история платежей БКИ, число запросов в БКИ за 30 дней, отрасль (ОКВЭД), налоговые недоимки, сумма запроса к выручке. Каждый фактор → баллы → итог → рейтинг A–E и PD-диапазон. Вклад каждого фактора сохраняется (объяснимость).
3. **Кредитная логика**: продукт × рейтинг × сумма × срок → APPROVED / COUNTER_OFFER (калькулятор максимальной суммы по DSCR, увеличение срока, другой продукт) / MANUAL_REVIEW (серая зона, крупная сумма, расхождение заявленного и ЕГРЮЛ/ФНС) / REJECTED.
4. Пороги и веса — в таблице `rule_sets` с версиями, редактирует администратор рисков.

### Продукты (синтетические, но правдоподобные)
Овердрафт · Кредит на пополнение оборота · Инвестиционный кредит (оборудование) · Кредитная бизнес-карта · Кредит по госпрограмме МСП. У каждого: диапазон суммы/срока, ставка от рейтинга, требования к документам и залогу.

### Тестовые ИНН под каждый исход
Один ИНН — один сценарий: автоодобрение, контрпредложение, запрос документов, ручное рассмотрение,
отказ по стоп-фактору, недоступность БКИ. Список — в README и на экране входа демо-стенда.

## 5. Функционал по экранам (MoSCoW)

### Клиент
- **Must**: вход → «Ваша компания» по ИНН с автозаполнением из ЕГРЮЛ (ввод один раз); мастер потребности (цель, сумма, срок) → подбор продуктов с объяснением «почему подходит» и калькулятором платежа; анкета с автосохранением черновика и проверкой полей на лету; загрузка документов; карточка заявки: шкала этапов, «что сейчас происходит», «что нужно от вас» (задачи от банка); оффер со сравнением с запрошенным; согласие и подписание кодом (смоделированная ПЭП, код показывается в интерфейсе); экран выдачи с графиком платежей.
- **Should**: чат с менеджером внутри заявки; лента уведомлений; несколько пользователей одной компании.
- **Could**: ИИ-помощник «объясни простыми словами» по продукту, отказу, оффере; распознавание выписки/отчётности (Tesseract) для автозаполнения выручки.

### Банк
- **Must**: очередь заявок с SLA и фильтрами по статусам/продуктам; карточка: заявленное vs данные источников с подсветкой расхождений, скоринг по факторам, рекомендация системы, действия (одобрить / контрпредложение / запросить / отказать с кодом причины); журнал событий.
- **Should**: настройка порогов правил и продуктов с версиями; воронка и время на этапе (считается из `application_events`).
- **Could**: ИИ-сводка по заявке для андеррайтера (из структурированных данных, без выдумок).

### ИИ — только где есть понятная ценность
1. Помощник клиента: объясняет термины, статус и причину решения на основе данных заявки + RAG по описаниям продуктов. Открытые веса (Ollama, Qwen2.5-7B-Instruct), профиль `ai` в compose; без него — детерминированные шаблонные объяснения, сценарий не ломается.
2. (Опционально) Распознавание документов — Tesseract (Apache-2.0), без LLM.
Скоринг — **не** LLM: правила прозрачны и воспроизводимы, это сознательное решение (ADR).

## 7. Открытые вопросы
- Дедлайн и состав команды — от них зависит, сколько Should/Could брать.

- Новый стандарт дизайна — какой именно (Альфа-стиль/Figma-макеты)? Понадобится к этапу 9.
