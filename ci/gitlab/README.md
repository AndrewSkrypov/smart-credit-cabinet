# GitLab CI and release

## Release from protected main (opt-in)

Feature merge requests target `dev`. Their required pipeline contains quick
backend and frontend checks, plus Helm lint when the chart changes. A branch
pipeline on `dev` is suppressed. A release merge request targets `main` from
`dev` in the same project and runs the small `release-mr` admission gate.

Merge the approved release MR in GitLab. With the protected project variable
`PUMP_MAIN_RELEASE_ENABLED=1`, the resulting `push` on protected `main` starts
the full pipeline. The merge itself authorizes release. The published revision
is the resulting merge commit, including any conflict resolutions. Test and
scan failures block the automatic `main-release-images` job. Both
`main-dev-deploy` and `main-prod-deploy` start automatically in the same stage
after one `main-release-activation` checkpoint. All three jobs compare their
artifacts with the protected canonical publisher receipt and verify the same
pipeline, commit, Git tree and manifest hash before reading deployment secrets.
Each environment runs its existing deployment acceptance checks and uses its
own resource group shared with the corresponding legacy jobs.

An obsolete main checkout fails the current-tip check after the runner acquires
the environment lock. A deployment that has entered the rollout can finish.
If one environment fails, inspect its acceptance and retry only that deployment
job while that SHA is still the tip of `main`. Restage scoped Prod JIT inputs
bound to the approved receipt if they need renewal. The publisher serializes
its attempts in `cabinet-main-publisher` and restores the first canonical
receipt on retry. Record the release as deployed when both environments succeed.

### Enablement after the legacy release finishes

1. Resolve the source merge of the current `main` and accepted release trees
   and retain both histories. Review a separate MR for this CI change. Create
   `dev` from the reviewed integration baseline containing the new workflow.
2. Require successful pipelines and reviews for `dev` and `main`; disable
   direct pushes and force pushes on both. Limit merges into `main` to release
   maintainers, require `dev` as its MR source, and require owner review for
   changes to CI, deployment scripts and Vault roles. Verify that no matching
   wildcard branch rule grants broader access. Release MRs need no deploy
   runner or deployment credentials. Disallow pipeline variable overrides by
   developers, including overrides of predefined CI identity variables.
3. Have the Vault owner review the two role definitions generated by
   `ci/gitlab/vault/render-role.py pump-ci-dev-main` and
   `ci/gitlab/vault/render-role.py pump-ci-prod-main`. Each role allows only a
   protected `main` push on its own runner and environment with action
   `start` and the existing environment-scoped read policy. The local handoff
   additionally verifies the exact CI job, pipeline and SHA claims. Main
   deploys fail closed without Vault. Existing legacy JWT roles, parity
   canaries and SHA activation markers keep their current behavior.
4. Add `cabinet-deploy-main-dev` only to protected runner **#2**, alongside its
   existing `cabinet-deploy` tag. Verify that protected runner **#4** is the
   only eligible project runner with `cabinet-deploy-prod`. Both checks require
   active project assignment and protected status. Keep legacy runner tags.
5. Protect the Generic package `cabinet-release-ci` against untrusted writers
   and deletion during the release/retry window. Configure GitLab to reject
   duplicate filenames for this package. Verify that a second upload to the
   same version and path is rejected, and exclude the receipt from automated
   cleanup while any pipeline can use it. One private package version
   `<CI_COMMIT_SHA>-<CI_PIPELINE_ID>` stores the original evidence and manifest
   as one file named `publisher-receipt.json`. The release, Dev and Prod runners
   must have authenticated read access. Only the protected publisher path needs
   write access.
6. Check the native CI Lint and the pipeline cases below with the GitLab owner.
   Confirm the protected production environment, authorized checkpoint operators,
   scoped Vault role read-back, registry and deployment inputs, and authenticated
   read access to `main` on all three runner types. Keep
   `PUMP_MAIN_RELEASE_ENABLED` disabled until these checks and the scoped JIT
   staging steps are agreed.

### Scoped Prod JIT for the first main release

1. Wait for `main-release-images` to succeed. Verify the canonical receipt
   against the exact project, pipeline, SHA and first publisher job. Verify
   that the manifest digest in `release-evidence.json` matches `release.json`.
2. The runtime owner issues a fresh `cabinet-prod-release` TokenRequest for
   `cabinet-prod` via the approved operator context, with the existing
   60–90 minute TTL and pinned CA and namespace UID. Stage the scoped JSON
   kubeconfig and the synthetic jury credentials as protected, raw file
   variables with environment scope `production`, using
   `CABINET_MAIN_PROD_KUBECONFIG` and `CABINET_MAIN_PROD_JURY_CREDENTIALS`.
   Check in the runner #4 service context that its umask gives GitLab file
   variables owner-only mode `0600`. Keep debug tracing off.
3. Stage the third protected raw file variable
   `CABINET_MAIN_PROD_JIT_CONTEXT` in `production`. Its JSON fields are
   `format: 1`, `project_id`, `pipeline_id`, `publisher_job_id`, `revision`,
   `release_sha256`, `namespace_uid`, `kubeconfig_sha256` and `jury_sha256`.
   Copy the first five identity values from the evidence fields `project`,
   `pipeline`, `publisher_job`, `revision` and `manifest_sha256` as strings.
   Take the namespace UID from `CABINET_PROD_NAMESPACE_UID` and compute the two
   file hashes over the exact staged bytes. Keep the context file private.
4. Play `main-release-activation` once in that pipeline. It verifies the
   publisher receipt and staged JIT on runner #4 using environment action
   `prepare`. The artifact records the publisher and checkpoint identity
   and manifest digest. It excludes credentials and credential hashes.
   Both deployments can start once this checkpoint succeeds. Prod revalidates
   fresh files and the namespace UID before the Vault/deployment path, with at
   least 45 minutes remaining for its 40-minute job. After terminal deployment
   status, remove the temporary main-only JIT variables via the owner.

Unattended issuance is a separate follow-up. Preserve this checkpoint until
a broker can verify the signed GitLab job identity and canonical release
receipt server-side and mint a TokenRequest only for
`cabinet-prod-release` in `cabinet-prod`. The issuer's operator credentials
stay outside the runner and CI variables.

### Pipeline checks

- Feature MR to `dev`: `quick-backend`, `quick-frontend`, and `quick-helm`
  for chart changes. An unprotected source push with an open MR is skipped.
- Same-project MRs from `feature/fantech-dev-final` and
  `feature/backend-code-style` to `dev` run the full source checks and both
  Alpha jobs.
- Branch pipelines on `dev` are skipped by default. An API or web pipeline
  on protected `dev` runs the full checks when `CABINET_ALPHA_PILOT=1`,
  `CABINET_DEV_DIAGNOSTICS=1`, and all four runtime mode variables are
  `remote`. Publication, diagnostics, and the Dev deployment are manual.
  The pipeline has no production deployment job.
- Same-project `dev` MR to `main`: `release-mr` only. Any other source
  branch or source project fails that gate.
- Protected `main` push with the flag: all quality, verify and extended
  gates, then one publisher, one blocking activation checkpoint, and both
  automatic deployments in the same stage.
- Protected `main` push without the flag, or schedule on an existing ref:
  normal quality configuration and no new deploy jobs. Manual/API
  `main` with the flag is skipped, except explicit Alpha or diagnostics checks.
- Protected legacy release ref: existing manual publisher, Dev and Prod.
  Prod requires the existing `dev-release.sha256` from that pipeline.
- Alpha opt-in and the existing Alpha MRs retain their requirements.
  Alpha publication downloads the analytics artifact in either release path.
- Protected runner canary ref with its flag: only the canary jobs.

The publisher builds each deployable OCI once. The quality pipeline retains
its existing Compose and scan fixture builds. Moving those checks to the
published digests requires staging the candidate images before the quality
gate and updating the Compose inputs. That can be tested independently.

## Runners and canary

Restrict every runner to this project and tagged jobs. Keep `cabinet-ci` isolated
from deployment credentials and existing workloads, with one job per quality
Docker daemon. See [quality runner provisioning](quality/README.md). Install Helm
3.19+ or Helm 4 on quality and deployment runners. The protected release runner
needs the Docker buildx plugin and enough disk for image scanning. The protected
deploy runner needs SSH, Git, and Python. The protected `cabinet-deploy-prod`
runner additionally needs kubectl and a route to the new private API.

Once the selected runners are online, start a pipeline on the protected
`feat/final-runner-canary` branch with `CABINET_RUNNER_CANARY=1`. Jobs run in
order. The CI runner builds and uploads a tiny image and emits
`runner-canary-image.txt`. The release runner pulls this exact digest and checks
the OCI revision. The deploy runner checks its local tools. Record the pipeline
URL and digest. Remove the canary variable before starting the quality pipeline.

## Promotion

1. Create a normal pipeline on the protected release ref. Required checks include
   the extended jobs. Click `release-images` after the gates pass. It checks the
   producer hashes, scans the locally built images and publishes
   `release.json` with the revision and Registry digests. Keep the image tags
   and pipeline artifact for the rollback window.
2. Run `dev-deploy`. It streams a Git archive of the revision to the Dev VM and
   applies the immutable release manifest with the Dev host's own runtime
   settings. Only Caddy publishes ports. After HTTPS and jury-role checks pass,
   the job records the manifest hash for promotion.
3. Run `prod-deploy` only after the protected production environment and the
   initial synthetic roles are configured. It verifies the Dev manifest hash
   and the new namespace UID, renders the chart with server dry-run, waits for
   upgrades, checks the Kubernetes revision and matches the public frontend
   bytes to both pods. The jury-role smoke must also pass.

The deployment SSH key is a protected file variable scoped to `dev`. Add its
public key on `pump-final` using
`restrict,command="/usr/local/sbin/cabinet-dev-deploy"`. Pin the verified SSH host
key in a separate protected file variable. Install
[dev-ssh-entrypoint.sh](dev-ssh-entrypoint.sh) as a root-owned executable at that
path. The account `cabinet-deploy` can run Docker on the dedicated Dev VM. Keep
its host environment and Registry read-only login private. See
[the Dev runbook](../../deploy/README.md) for initial setup and recovery.

Set the dedicated Dev runner's service and login-shell umask to `0077`. Before
releasing TCP 80/443 from the bootstrap Caddy, confirm that GitLab creates the
deployment SSH file variable with mode `0600`. Check the mode using
`test "$(stat -c '%a' "$CABINET_DEV_SSH_KEY")" = 600` without reading the file.
If the job stops before the app Caddy binds, start the bootstrap Caddy again
with its existing TLS volumes and verify HTTPS before retrying the same release.

Enable monitoring in the host environment with `CABINET_OPTIONAL_PROFILES=monitoring`.
The deployment applies `monitoring/compose.ops.yaml` after the runtime overlays.
The dedicated Dev host can add `monitoring/compose.paging.yml` last by setting
`CABINET_ALERTMANAGER_PAGING_DIR` in its private environment. Start with the
inactive smoke rule and let the observability owner activate it in the agreed
test window.
After acceptance, check the synthetic journey and the Grafana dashboard from
the Dev host's loopback monitoring endpoints.

Set these GitLab variables in their matching protected environment.
File values are indicated explicitly.

- Dev uses `CABINET_DEV_SSH_HOST`, `CABINET_DEV_URL`,
  `CABINET_DEV_SSH_KEY` (file), and `CABINET_DEV_KNOWN_HOSTS` (file).
- Production uses `CABINET_PROD_CONTEXT`, `CABINET_PROD_NAMESPACE`
  (`cabinet-prod`), `CABINET_PROD_NAMESPACE_UID`, `CABINET_PROD_URL`,
  `CABINET_PROD_KUBECONFIG` (file), `CABINET_PROD_VALUES` (file), and
  `CABINET_PROD_JURY_CREDENTIALS` (file).

Use separate deploy job credentials. Apply [prod-rbac.yaml](prod-rbac.yaml) once from the confirmed cluster operator
context. Apply the updated role before the first Catalog gateway reopening.
The release identity uses its gateway-specific scale permissions to close traffic if acceptance fails.
Issue a short-lived TokenRequest for `cabinet-prod-release` or use a
scoped GitLab Agent identity with equivalent access. Pin the cluster CA and
private API in the runner's kubeconfig. The Prod Helm release stores its state
in ConfigMaps and requires no direct Secret API access. The Kubernetes Secret and namespace pull
secret are provisioned separately from Helm values, with only a
`read_registry` token in the pull secret. The app gateway stays on ClusterIP.
Ingress uses class `cabinet-public` and the Edge-managed
`cabinet-prod-tls` Secret. In the values file, pair `ingress.sourceNamespaces=[cabinet-prod]` with
`ingress.sourcePodLabels.app.kubernetes.io/instance=cabinet-edge-cabinet-prod`.
Enter the observed controller peer addresses and cluster DNS address.
List `www.credit-cabinet.ru` in `ingress.aliases` to redirect it over HTTPS
to the canonical `credit-cabinet.ru` origin using the shared certificate.
Set `monitoring.namespaces=[monitoring]` and
`app.otlpEndpoint=http://tempo.monitoring.svc:4318/v1/traces` when the
observability owner installs `cabinet-observability` in `monitoring`.
With internal S3, the app requests 104 GiB on 6 RWO claims and observability
requests 68 GiB on 6, for 172 GiB on 12 claims total. Edge owns NodePorts 30080 and 30443.

On first Prod release, apply the chart with infrastructure only, then run the app
upgrade using the Dev-accepted artifact. In the private operator session, use
the chart's jury provisioner to initialize the synthetic identities. Retry the
Prod job to check the running service. See the [chart runbook](../../helm/cabinet/README.md)
for migration, backup and recovery. Treat Helm rollback and PostgreSQL restore
as separate operations. Verify an isolated restore before any live recovery.

For acceptance retain the Git SHA, artifact manifest hash, pipeline/job URLs,
certificate/HTTPS result, three role results and negative access result.
Keep private settings, credentials and database dumps on their respective hosts.
