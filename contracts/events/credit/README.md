# ApplicationStatusChanged.v1

`credit` публикует новое состояние статуса заявки. Значение записи Kafka — JSON
в UTF-8 по [схеме v1](application-status-changed.v1.schema.json). Ключ записи
Kafka — строка `applicationId` в UTF-8, побайтно совпадающая с этим полем JSON.
Логическое имя события — `ApplicationStatusChanged.v1`.

## Запись и чтение

| Поле | Откуда берётся значение |
| --- | --- |
| `eventId` | UUID записи журнала перехода, `transition.entry.id`. При повторной доставке используется тот же UUID. |
| `applicationId` | UUID сохранённой заявки, `saved.id`. Оба UUID кодируются строчными шестнадцатеричными символами с дефисами. |
| `applicationVersion` | `saved.version`, возвращённая репозиторием после `saveAndFlush`. Представляется целым JSON-числом в диапазоне от 0 до `Long.MAX_VALUE`. |
| `status` | Новый статус сохранённой заявки, `saved.status.name`. Все 14 значений `ApplicationStatus` входят в v1. |
| `occurredAt` | `transition.entry.occurredAt` в формате ISO-8601 UTC. Кодируется как `Instant.toString()` с суффиксом `Z` и точностью до наносекунд. |

В `Transitions.commit` запись outbox создаётся в транзакции сохранения
заявки и журнала, когда `transition.entry.isTransition` истинно. Например,
создание черновика, добавление документа и действия внутри текущего
статуса не порождают событие смены статуса.

`analytics` применяет полное новое значение только при версии выше сохранённой.
Пропуски версий и повторная доставка штатны. Разные статусы при одной версии
диагностируются. При подсчёте `currentStatuses` исключаются
`DRAFT` и `PENDING_CLIENT_CONFIRMATION`. `WITHDRAWN` учитывается в том числе
до подачи заявки.

Пример значения Kafka. Ключ этой записи — `a4fd57ac-6182-4647-bdd2-176221bab0c2`.

```json
{
  "eventId": "32bb5ccb-40b9-41eb-a75e-715360e17517",
  "applicationId": "a4fd57ac-6182-4647-bdd2-176221bab0c2",
  "applicationVersion": 7,
  "status": "SUBMITTED",
  "occurredAt": "2026-11-26T12:15:11.123456789Z"
}
```

Producer и consumer получают имя одного topic из конфигурации поставки.
Предлагаемый шаблон — `alpha.<environment>.credit.application-status-changed.v1.<generation>`.
Например, `alpha.shadow.credit.application-status-changed.v1.g001`.
После восстановления базы из более раннего снимка у нового поколения отдельные
topic и consumer group. Пример следующего topic —
`alpha.shadow.credit.application-status-changed.v1.g002`.

## Совместимость

Схема v1 закрыта. Поля обязательны, множество статусов фиксировано.
Добавление даже необязательного поля или нового статуса несовместимо со строгим
читателем v1. Изменение формы, допустимых значений, семантики, кодировки или
ключа требует новой версии контракта и отдельного версионированного маршрута.
При миграции сохранённые записи v1 продолжают читаться как v1. Уточнения
документации и фикстур с сохранением прежних правил совместимы с v1.

## Проверка

Из корня репозитория с Python 3.11+ и `jsonschema` 4.19.2 выполните:

```bash
python3 contracts/events/credit/check_contract.py
```

Проверка читает [примеры записей](fixtures/valid.json) с отдельными ключом
и значением и применяет [недопустимые замены](fixtures/invalid.json) к
первому примеру. Проверяются обязательные свойства каждого поля, границы версии,
календарная дата и ключ. Kafka и БД для этой проверки не нужны.

В GitLab CI эту команду можно добавить в стадию `quality` отдельной
проверкой после предоставления Python и `jsonschema` на раннере.
Проверка A01 на интегрированном кандидате также использует JSON, записанный
реальным producer, и его чтение реальным consumer.
