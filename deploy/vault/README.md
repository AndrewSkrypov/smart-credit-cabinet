# Vault для PUMP

Vault CE работает на отдельной ВМ с TLS и Integrated Storage. На первой ВМ
один участник Raft. Остановка ВМ или запечатанный сервер временно отключают
операции Vault. Уже запущенные контейнеры используют материализованные настройки
и продолжают работать.

## Установка и начальные полномочия

1. Сверьте идентификатор ВМ, SSH-отпечаток, отдельный зашифрованный диск,
   его точку монтирования и адреса доверенных клиентов. Порт 8200 доступен
   только этим клиентам. Raft 8201 остаётся локальным в установке с одним узлом.
2. Установите закреплённый официальный Vault через `host/`. Сертификат
   содержит точное имя API в SAN. Клиенты проверяют отдельный CA, его
   публичная часть распространяется по защищённому каналу. Закрытый ключ CA
   хранится отдельно от ВМ.
3. Инициализируйте только новый пустой узел. `owner-custody.py probe`
   проверяет запись, чтение и очистку синтетической записи в macOS Keychain
   владельца. На защищённом FileVault Mac задайте отдельный каталог `0700` и
   используйте операции `init`, затем `unseal` и `configure`. Каждая операция
   принимает точный origin и PEM CA. Для SSH-forward есть `--tunnel-port`,
   который сохраняет SNI и проверку имени. `init` также принимает `--directory`.
4. `init` сохраняет три части Shamir с порогом два в Keychain вне ВМ и CI.
   При ошибке Keychain ответ инициализации остаётся в аварийном файле `0600`
   на FileVault вместо повторного запуска инициализации. По окончании проверки
   выполните `revoke-bootstrap`. Последующие перезапуски требуют `unseal`
   с того же защищённого аккаунта владельца. Части находятся у одного владельца.
   Потеря его Keychain без утверждённой резервной копии лишает возможности
   разблокировать Vault и восстановить снимок. Резервное хранение частей
   согласуется отдельно от сохранения Raft snapshots.

## Области доступа

- `pump/dev/ci-deploy` хранит SSH-материал CI для `cabinet-deploy`, включая
  доверенный `known_hosts`. `pump/prod/ci-deploy` хранит запрошенные значения
  выпуска. Каждая роль GitLab JWT читает только собственный документ. Идентификаторы
  проекта и раннера, protected release ref и имя окружения проверяет Vault.
- `pump/dev/compose` хранит проверенные существующие сервисные данные Dev.
  Для прямого чтения с Dev выполните `owner-custody.py configure` с
  `--dev-approle-source` и подтверждённым публичным IPv4 выхода Dev. Опция
  воспроизводит роль `cabinet-dev` в `pump-dev-approle`: SecretID одноразовый,
  действует пять минут и ограничен одним IPv4, токен чтения действует две
  минуты с максимальным сроком три минуты. Передавайте SecretID и токен
  только защищённым потоком. После проверки используйте `revoke-self`.
  На хосте остаётся рабочий `cabinet.env` с правами `0600`. Сверку проводите
  под штатной блокировкой и вне окна Alpha. Совпадение оставляет файл без правок
  и само по себе не переключает Compose или CI на Vault.
- `pump/prod/kubernetes/<имя>` содержит данные узкого списка существующих
  Kubernetes Secrets в `cabinet-prod`. Скоуп отдельного синхронизатора
  ограничен именами и UID namespace. Приложение продолжает использовать эти
  объекты. TLS cert-manager, личные учётные данные жюри, ключи операторов,
  и JIT kubeconfig в пилот миграции не входят.

Первичное заполнение использует отдельные краткоживущие права на чтение и
создание с `cas=0`. При совпадении существующей записи сверяется версия.
Изменение пароля требует отдельной согласованной ротации потребителя.
Отключение опции Vault в CI оставляет предыдущий защищённый путь к данным
до приёмки. Удалять копии статических секретов CI можно после проверки
Vault, отзыва доступа старого потребителя и проверки пути возврата.

## Проверка и восстановление

До переноса данных проверьте TLS с разрешённых адресов, успешную проверку
GitLab JWT по реальному раннеру и отрицательные сценарии для чужого
окружения, protected ref и адреса. Проверьте изоляцию ACL на синтетических
записях. Примените и примите Dev первым. Prod использует тот же формат
проверки через отдельные роли и путь.

Сохраняйте Raft snapshots вне Vault VM с ограниченным доступом и проверкой
целостности. Каждый снимок сопровождается временем, идентификатором кластера
и принятой версией конфигурации и секретов. Восстановление сначала выполняют
на изолированной ВМ с доверенным TLS и частями Shamir. Снимок старше текущего
порога допускается к эксплуатации после сверки отозванных и ротированных
учётных данных и повторной проверки обоих потребителей. Переключение DNS
и доступа выполняют после этой приёмки. Snapshot token имеет право читать
снимок. Восстановление требует отдельной административной сессии.
