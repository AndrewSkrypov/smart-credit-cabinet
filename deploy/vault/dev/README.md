# Secrets Dev Compose в Vault

Этот этап переносит согласованные секреты из действующего PUMP Dev
`/var/lib/cabinet-dev/cabinet.env` в KV v2 `pump`, ключ `dev/compose`.
Скрипт выполняется вручную от владельца каталога состояния на `pump-final`.
Для обычной выкладки по-прежнему используется локальный `cabinet.env`.
Переключение автоматической выкладки на Vault и ротация действующих учётных
данных требуют отдельных изменений и приёмки.

## Границы переноса

- Обязательны `POSTGRES_PASSWORD`, `JWT_SECRET`, `SIM_API_KEY`,
  `IDENTITY_LINK_KEY`, `VALKEY_PASSWORD` и пары
  `{IDENTITY,CREDIT,ENGAGEMENT}_{DB,MIGRATION}_PASSWORD`.
- При наличии мигрируют `S3_ACCESS_KEY`, `S3_SECRET_KEY`,
  `S3_ADMIN_ACCESS_KEY` и `S3_ADMIN_SECRET_KEY`. Для активного S3 обязательны
  обе пары. Пароль для входа администратора Grafana остаётся вне этого KV.
- `GRAFANA_PASSWORD` учтён отдельно. Compose передаёт его в
  `GF_SECURITY_ADMIN_PASSWORD` для первоначальной настройки Grafana. Для
  согласованного отдельного переноса выделите `pump/dev/observability/grafana-admin`
  с доступом только у оператора наблюдаемости. Проверяйте доступ и ротацию через
  Grafana после сохранения существующей базы. Этот адаптер не создаёт такой KV
  и не копирует туда пароль.
- `SMTP_USERNAME` и `SMTP_PASSWORD` входят в перенос только с
  `--include-service-smtp` для отдельно согласованной сервисной учётки PUMP.
  Передавайте тот же флаг при чтении этого KV. Личные SMTP-учётки туда не входят.
- Alpha использует пять отдельных секретов
  `CABINET_ALPHA_DEV_PG_{ADMIN,OWNER,APP}_PASSWORD`,
  `CABINET_ALPHA_DEV_READ_TOKEN` и `CABINET_ALPHA_DEV_JWT_SECRET`.
  Для них нужен собственный этап и путь. Переключатели Alpha и идентификатор
  поколения остаются настройками хоста.
- Реестр, GitLab/SSH, ключ H100, учётки жюри, данные публичного демо и
  Alertmanager relay обслуживаются отдельно. Этот адаптер не читает их файлы
  и не пересылает содержимое неизвестных ключей `cabinet.env`.

## Первый перенос

### Проверка на pump-final перед первой выкладкой с Vault

Проверка относится к 15 секретам приложения из `pump/data/dev/compose`. Для
неё не нужны GitLab JWT, CI-флаг, runner или отдельное сетевое правило.
`cabinet-dev` использует AppRole `auth/pump-dev-approle/role/cabinet-dev`,
одноразовый SecretID и короткую сессию с правом чтения только этой записи.
Оператор с согласованным доступом передаёт сессию через закрытый ввод, затем
отзывает её. Не используйте root token или долговременный SecretID в Dev.

1. Сверьте SHA подготовленного checkout и `release.json` с согласованным
   immutable релизом. На `pump-final` как `cabinet-deploy` проверьте TLS с
   `/etc/pump-vault-client/ca.pem` и SNI `vault.pump.internal`. Проверенный
   адрес для прямого dial с этого хоста — `203.81.218.203`.
2. Запустите только `verify` из подготовленного checkout. Он открывает уже
   существующий `deploy.lock` только для чтения и завершится, если Alpha
   держит lock. При свободном lock он сравнит KV и `cabinet.env`, даже если
   остался `pending.json`. Пароли, снимки и файлы состояния не выводятся.

   ```sh
   sudo -u cabinet-deploy python3 -B deploy/vault/dev/compose-secrets.py verify \
     --vault-origin https://vault.pump.internal:8200 \
     --connect-ip 203.81.218.203 --ca-file /etc/pump-vault-client/ca.pem \
     --token-stdin < "$CABINET_VAULT_READ_TOKEN_FILE"
   ```

3. Для dry-run Compose используйте на подготовленном checkout обычный
   `Deployment` с утверждённым `release.json` и тем же `cabinet.env`,
   под общей read-only блокировкой. Запустите только сформированный
   `docker compose … config --quiet` и зафиксируйте код возврата.
   Подавите вывод Compose, где могут оказаться интерполированные значения.
   Не используйте `deploy/start.py --check-only` в живом checkout:
   перед проверками он рендерит файл Gateway. Успешный config не проверяет
   готовность запущенных сервисов и не снимает незавершённый релиз.
4. Первая реальная операция только после handoff от владельца Alpha,
   проверки `current/pending` и выделения одного writer для Dev. При
   полном parity существующий `cabinet.env` уже подходит для штатной
   выкладки. Vault становится проверяемым источником этих полей перед
   выкладкой и источником восстановления при потере поля. Compose по-прежнему
   читает локальный файл. При несовпадении остановитесь, не меняйте значения
   и не начинайте rollout. `apply` для восстановления отсутствующего поля
   запускайте только в отдельно согласованном окне.
5. Dry-run не требует отката. Если согласованный `apply` создал снимок,
   восстановите его штатным `rollback` под тем же lock. Откат откажется
   менять файл при появившемся pending, активной Alpha или разошедшемся
   содержимом. Если началась выкладка, владелец Dev сначала решает состояние
   незавершённого релиза и следует штатному rollback релиза. Нельзя
   удалять pending или откатывать только `cabinet.env` поверх чужого rollout.

### Инициализация KV с нуля

1. Убедитесь, что каталог состояния принадлежит существующему deploy-пользователю
   и имеет права `0700`, а `cabinet.env` и имеющийся `deploy.lock` имеют
   права `0600` и того же владельца. Получите утверждённый точный HTTPS origin
   Vault и его CA-файл из доверенного канала. HTTP, прокси и перенаправления
   адаптеру не требуются. Для выделенного NAT-маршрута передайте
   `--connect-ip` с проверенным IPv4. TLS и HTTP продолжают использовать имя
   из `--vault-origin`. Общий DNS и `/etc/hosts` менять не нужно.
2. Получите отдельный краткоживущий токен оператора с `create, read` только
   на `pump/data/dev/compose`. Передайте его закрытым вводом
   (`--token-stdin`) или используйте файл `0600`, принадлежащий
   deploy-пользователю (`--token-file`). Пример ниже предполагает, что
   администратор уже открыл подготовленный закрытый файл через перенаправление
   stdin, а `CABINET_VAULT_ORIGIN` и `CABINET_VAULT_CA_FILE` содержат
   утверждённые несекретные значения.

   ```sh
   sudo -u cabinet-deploy python3 deploy/vault/dev/compose-secrets.py seed \
     --vault-origin "$CABINET_VAULT_ORIGIN" --ca-file "$CABINET_VAULT_CA_FILE" \
     --token-stdin < "$CABINET_VAULT_SEED_TOKEN_FILE"
   ```

   Создание использует `cas=0`; повтор подтверждает точное совпадение с
   существующей версией, сохраняя её. После операции используйте штатный отзыв
   этого токена или дождитесь короткого установленного TTL.
   [Документация API Vault KV v2](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2#createupdate-secret)
3. Повторите проверку с отдельным токеном `read` только на этот путь.

   ```sh
   sudo -u cabinet-deploy python3 deploy/vault/dev/compose-secrets.py apply \
     --vault-origin "$CABINET_VAULT_ORIGIN" --ca-file "$CABINET_VAULT_CA_FILE" \
     --token-stdin < "$CABINET_VAULT_READ_TOKEN_FILE"
   ```

   При полном совпадении выводится только номер версии KV. Сверьте без
   пересоздания контейнеров штатный Dev health и доступ по ролям. Тот же
   `deploy.lock` сериализует операции с действующей выкладкой. Перенос
   `seed` и проверка совпадения доступны во время Alpha, если блокировка
   свободна.

## Восстановление локального файла

`apply` может восстановить отсутствующие управляемые строки из Vault.
Действующие значения должны совпадать с KV. Если пароль или ключ изменился,
сначала согласуйте ротацию с владельцем потребителя. Существующий
`cabinet.env` нужен для проверки области и сохранения всех других настроек.
Если потерян весь файл, сначала восстановите его из закрытой резервной
копии хоста. Изменять файл во время активного Alpha или незавершённой Dev
выкладки адаптер откажется.

Перед изменением адаптер создаёт закрытый локальный снимок и атомарно
заменяет `cabinet.env`, сохраняя владельца, группу и режим `0600`.
Держите снимок в каталоге состояния до приёмки восстановления. Для отката
используйте напечатанное имя снимка и тот же deploy-пользователь.

```sh
sudo -u cabinet-deploy python3 deploy/vault/dev/compose-secrets.py rollback \
  --backup "$CABINET_VAULT_LOCAL_BACKUP"
```

Откат принимает только точное состояние после этой операции. Последующие
правки нужно сверять отдельно под блокировкой. Снимок содержит действовавшие
на момент операции пароли, хранится по правилам резервного копирования
секретов хоста и не прикладывается к GitLab, чатам или обычным логам.

Проверка адаптера с синтетическими значениями и без доступа к Dev или Vault

```sh
python3 -B deploy/vault/dev/test-compose-secrets.py -v
```
