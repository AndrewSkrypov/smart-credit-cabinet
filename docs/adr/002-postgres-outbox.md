# 002. Очередь конвейера в PostgreSQL

Статус: принято; отражает текущую реализацию.

**Контекст.** Задача не должна теряться между фиксацией перехода и запуском следующего
этапа. Для локального стенда уже нужен PostgreSQL; отдельного брокера нет.

**Решение.** Хранить задания в `pipeline_jobs`. Воркер захватывает готовую пачку через
`FOR UPDATE SKIP LOCKED`, помечает `RUNNING` и арендует на две минуты. Следующий переход,
журнал и новая задача записываются транзакционно. После истечения аренды возможен повтор.

**Альтернативы.** Kafka/RabbitMQ с отдельным outbox-публикатором; очередь только в памяти;
синхронная обработка в HTTP. Брокер добавляет эксплуатационные компоненты, память теряет
работу при перезапуске, синхронный запрос зависит от длительности внешних вызовов.

**Последствия.** Одна инфраструктура и восстановление задач из БД. Повторное выполнение
допустимо, поэтому нужны проверки статуса, версии и идемпотентная АБС. Блокировка захвата
сама по себе не доказывает «ровно один раз». Опрос создаёт нагрузку на БД, а размер пачки,
аренда и число воркеров ограничивают скорость. Доставка уведомлений после коммита в этот
outbox не входит и пока не имеет долговечных повторов.

Основание: `pipeline/PipelineWorker.kt`, `pipeline/infrastructure/`,
[модель данных](../data-model.md), [последовательности](../architecture.md).
