# 006. Версия заявки и ключ повторной отправки

Статус: принято; отражает текущую реализацию.

**Контекст.** Пользователь может повторить отправку после сетевого сбоя; клиент и банк
могут одновременно менять заявку. Последовательное чтение без контроля версии теряет изменения.

**Решение.** `applications.version` участвует в оптимистической блокировке. Переход,
событие и задания сохраняются одной транзакцией. `Idempotency-Key` связывается с пользователем
и заявкой в `idempotency_keys`; повтор submit с тем же ключом возвращает актуальную карточку.
Ключ, занятый другой заявкой, вызывает конфликт. Для активной заявки компании на продукт
есть частичный уникальный индекс.

**Альтернативы.** Длинная пессимистическая блокировка, глобальная очередь команд,
повторы без ключа. Первый вариант удерживает блокировки, второй добавляет инфраструктуру,
третий не различает повтор и новое действие.

**Последствия.** Конкурирующее изменение может вернуть 409; клиент должен обновить карточку.
Идемпотентность submit не распространяется автоматически на все операции. Первичный ключ
таблицы — `(user_id, key)`, поле `operation` хранится отдельно. Внешняя выдача использует
`applicationId` как ключ. Гонки, аренда и отмена выполняющихся задач требуют отдельных
интеграционных проверок; одна аннотация версии не доказывает отсутствие повторных эффектов.
