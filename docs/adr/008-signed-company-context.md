# 008. Контекст компании в подписанном токене

Статус: принято; отражает текущую реализацию.

**Контекст.** Сервисы должны одинаково определять пользователя, роль и компанию.
Принимать эти значения от клиента как обычные поля запроса нельзя.

**Решение.** Identity выпускает JWT с HS256; `JwtVerifier` проверяет подпись, срок
и обязательные claims. `cid`, роль и `sign` берутся из токена. Доступ к чужой заявке
скрывается ответом 404, отсутствие разрешённой роли — 403. `credentialsVersion`
сверяется через identity с кэшем до 30 секунд для отзыва доступа.

**Альтернативы.** Серверные сессии с общим хранилищем, запрос identity на каждый вызов,
асимметричная подпись и JWKS. Первые варианты добавляют состояние/синхронную зависимость;
JWKS лучше разделяет право подписи и проверки, но пока не реализован.

**Последствия.** Большая часть проверок выполняется локально; отзыв не мгновенный из-за кэша.
Общий HS256-секрет означает, что скомпрометированный проверяющий сервис способен выпускать
токены. В `prod` запрещён стандартный dev-секрет; нужны управление и ротация ключа.
Сетевую защиту внутренних API обеспечивает развёртывание: gateway не публикует `/internal/`,
но сами внутренние маршруты не защищены пользовательским JWT. Это граница доверия,
а не самостоятельная взаимная аутентификация сервисов.

Основание: `libs/platform-common/src/main/kotlin/ru/creditcabinet/common/security/`,
[обзор API](../api.md), [архитектура](../architecture.md).
