# 011. Переписка по заявке в credit

**Контекст.** Сообщения должны иметь те же границы доступа, что и заявка, но не менять
её финансовое состояние, версию, комплектность или бизнес-журнал. Доставка уведомления
может завершиться позже отправки сообщения. В нескольких экземплярах нельзя терять
порядок сообщений, дублировать повторный запрос или уменьшать курсор прочтения.

**Решение.** Хранить переписку в credit (V7), используя типизированные порты для JDBC,
документов и лимита. Сообщения и отдельный аудит неизменяемы. Состояние переписки
сериализует выдачу номера; уникальный ключ `(application, actor, idempotency_key)`
и хэш тела возвращают прежний результат при повторе, а другое тело даёт 409.
Сообщение, аудит и outbox фиксируются одной транзакцией. Уведомление второй стороне
содержит номер и ссылку, без текста сообщения или названия файла.

Курсор общий для каждой стороны — компании и банка; он только растёт, не превышая
последнего номера. Интерфейс подтверждает только загруженные сообщения при видимом
конце переписки и активной вкладке. История загружается страницами по стабильному номеру.
Текст выводится React как текст, без HTML и Markdown. Максимум — 2000 символов и пять
вложений; пустой текст допустим только с файлами. Лимит отправок — 30 за минуту на
пользователя, общий через PostgreSQL до переноса лимитов на Valkey.

Вложения используют существующий документный порт и закрытый download API. Контекст
`CHAT` исключает их из финансовой комплектности. До публикации файл виден только
загрузившему участнику; после привязки — участникам заявки. Составные внешние ключи
не допускают чужую заявку. Опубликованный файл нельзя удалить или перепривязать.
Старые документы получили контекст `BUSINESS` и сохраняют прежний путь.

**Альтернативы.** Отдельный сервис чата усложняет проверку владения и атомарную запись
outbox. Бизнес-журнал смешивает согласование условий и свободный текст. Локальные
счётчики и курсоры не обеспечивают согласованность нескольких экземпляров.

**Последствия.** Компания-владелец, включая представителя без подписи, и все роли банка
читают переписку; чужой клиент получает 404. Банковский аудит закрыт от клиентов.
Черновик не принимает переписку, завершённая заявка доступна только для чтения.
Разделяемая блокировка заявки сериализует отправку с её закрытием, не меняя версию.
Повтор ранее успешного ключа после закрытия возвращает прежнее сообщение. Рассылка
имеет гарантию outbox, отдельной гарантии ровно одного SMTP-письма здесь нет.
