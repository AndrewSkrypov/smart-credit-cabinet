# 017. Отдельный владелец счёта и атомарного резерва

Статус: реализуется, переключение не принято.

**Контекст.** Счёт, транши, платежи, график, план поступления и резерв — один агрегат Servicing и одна PostgreSQL-транзакция. Credit сохраняет заявку, подписанный договор, точные условия и журнал workflow. Существующие пользовательские HTTP и проверки действующего мандата остаются в Credit. Documents не выделяется этой поставкой.

**Альтернативы.** Выделение только транша за сетевой порт внутри старой Credit-транзакции нарушило бы атомарность подтверждения резерва. Поэтому чистый `ServicingEngine` изменяет резерв и счёт под одной блокировкой счёта. Внешняя транзакция реализуется инфраструктурой; DTO и ядро не зависят от JDBC, Spring, protobuf и gRPC.

**Решение.** Внутренний контракт `creditcabinet.servicing.v1` использует unary gRPC с mTLS. Сервер доверяет только сертификату Credit с заданным URI SAN. Пользовательские операции дополнительно требуют исходный JWT, роль CLIENT и совпадение userId/companyId с командой; чтение ограничено ролью и компанией. Отдельная агентская сводка не содержит сумм. Credit проверяет актуальный мандат перед RPC. Сервис открытия принимает только доверенный Credit peer, без зависимости от пользовательской сессии фонового producer.

Credit фиксирует неизменяемую команду открытия вместе с результатом CoreBanking в собственном outbox V25. В этой точке заявка остаётся DISBURSING, а публичный `loans` ещё не записан. Повторный pipeline job читает сохранённый результат, без повторного вызова CoreBanking и без повторного запроса условий в Catalog. Потеря ответа CoreBanking до фиксации результата требует прежней идемпотентности CoreBanking по applicationId; распределённой транзакции с внешней АБС нет.

Команда содержит commandId, applicationId, accepted offer id как cycleId, исходную версию заявки, id и SHA256 подписанного текста, компанию и точные условия. Снимок соответствует подписанному signing session, его SHA проверяется. Перед первым вызовом АБС используется точная сохранённая историческая редакция продукта; после фиксации команды она больше не нужна. Для legacy inflight без достоверного подписанного снимка удалённый режим закрыт до восстановления условий, без эвристик по тексту.

Servicing в одной транзакции сохраняет счёт и долговечную квитанцию с уникальными applicationId/commandId/accountId. Повтор той же команды возвращает ту же квитанцию. Другой payload, цикл или версия конфликтует. Доставщик Credit имеет отдельную аренду и задержку; отказ владельца не блокирует уведомления. Проверка квитанции включает все идентификаторы, версию, payload SHA и schemaVersion. Credit отдельно фиксирует квитанцию; только затем pipeline атомарно записывает loans, DISBURSED и обычные уведомления. Ожидание квитанции возвращает job в PENDING без расхода budget ошибок. Конфликт сохраняется отдельно и требует сверки, а не бесконечного успешного ожидания.

**Последствия.** Старый локальный режим остаётся default с прежней атомарностью одной Credit БД. Удалённый runtime включается явной валидируемой конфигурацией после принятого импорта. У Credit сохраняются прежние таблицы и FK; у Servicing самостоятельная БД с V1 без ссылок на таблицы Credit. Изменение runtime flag не передаёт право записи. Owner-only fence и триггеры запрещают старому binary писать после переключения; финансовые SELECT/IUD retired runtime-role отозваны, поэтому он не выдаёт старый баланс. Для fence-блокировки runtime вызывает узкую SECURITY DEFINER-функцию с фиксированным search_path; UPDATE fence ему запрещён. Функция удерживает shared lock до commit, поэтому freeze ждёт все текущие операции.

Перенос выполняется при остановленных Credit HTTP/pipeline writers. Операторский transfer сериализован advisory lock в Credit и блокирует новые команды/ack; требует пустой недоставленный outbox, делает backup target, fence source, согласованный экспорт счетов/траншей/платежей/резервов/событий/квитанций, импорт и проверку SHA256 каждой полной выборки. Только затем включается target writer. Возврат тем же инструментом сначала fence нового владельца, переносит последние платежи и сверяет checksum перед разрешением локального writer. Ошибка до активации оставляет writers закрытыми. Для возобновления после операторского сбоя сохранены исходный снимок и backup target; повторное включение flag без проверки данных запрещено.

Основание: [план и приёмка](../plans/alpha-servicing-service.md), `services/servicing/cutover/transfer.py`, `contracts/proto/servicing/v1/servicing.proto`.
