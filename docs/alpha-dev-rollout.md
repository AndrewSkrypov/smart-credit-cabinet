# Выкладка Alpha на Dev

Для пилота используется существующая цепочка защищённой ветки GitLab
`quality → release-images → dev-deploy`. Нужен интегрированный SHA с
миграцией Credit для поля `stream_generation`, миграциями Analytics,
файлами снимка и внутренним endpoint чтения. На pipeline задайте
`CABINET_ALPHA_PILOT=1`. Сначала должны пройти штатные проверки и задания
`alpha-pilot-analytics-jar`, `alpha-pilot-infrastructure`. Оба задания
используют отдельный раннер качества. Публикация и применение остаются
ручными защищёнными заданиями.

`alpha-pilot-infrastructure` собирает брокер из закреплённого образа
Apache Kafka и проверяет исправленный `brotli-libs`. Trivy сканирует
собранный образ до запуска синтетического сценария. [Рецепт Kafka](../ci/alpha/Kafka.Dockerfile)

`release-images` собирает Analytics из проверенного JAR и Kafka по тому
же рецепту, сканирует образы до публикации и записывает `alpha_dev` в
`release.json`. Поля `image`, `jar_sha256` и `kafka_image` связывают
образ Analytics, JAR и образ Kafka в Registry проекта с Git SHA. Для
Kafka отдельно сохранены OCI revision и исходная ссылка с digest.
Штатный набор образов Helm записывается в ключе `images`.
[Порядок штатной поставки](../ci/gitlab/README.md)

## Настройки и первый запуск

Для первого запуска достаточно защищённого `dev-deploy` с `alpha_dev` в
манифесте. Если в `/var/lib/cabinet-dev/cabinet.env` нет переменных с
префиксом `CABINET_ALPHA_DEV_`, скрипт под блокировкой выкладки добавляет
их после проверок релиза и успешной резервной копии предыдущего выпуска.
Он сохраняет существующее содержимое, владельца и права `0600`. Первое
поколение запускается в теневом режиме с чтением из SQL. Поколение и пять
секретов генерируются на хосте Dev, где сохраняются для повторного запуска.
Секреты остаются в закрытом файле.

Любая уже заданная переменная `CABINET_ALPHA_DEV_*` передаёт управление
настройками оператору. В этом случае явно задайте `CABINET_ALPHA_DEV_ENABLED`.
Для действующего или незавершённого выпуска с Alpha
при утрате настроек восстановите параметры записанного поколения.
Манифест без `alpha_dev` и запуск с `--verify-only` оставляют файл как есть.

| Переменная | Значение |
| --- | --- |
| `CABINET_ALPHA_DEV_ENABLED` | `true` для запуска пилота. По умолчанию `false`. |
| `CABINET_ALPHA_DEV_GENERATION` | Новое поколение. Например, результат `python3 -c 'import secrets; print("g"+secrets.token_hex(8))'`. |
| `CABINET_ALPHA_DEV_READ_ENABLED` | `false` при первом запуске поколения. |
| `CABINET_ALPHA_DEV_PG_ADMIN_PASSWORD` | Отдельный случайный пароль bootstrap PostgreSQL. |
| `CABINET_ALPHA_DEV_PG_OWNER_PASSWORD` | Отдельный случайный пароль роли `analytics_owner`. |
| `CABINET_ALPHA_DEV_PG_APP_PASSWORD` | Отдельный случайный пароль роли `analytics_app`. |
| `CABINET_ALPHA_DEV_READ_TOKEN` | Отдельный случайный токен вызова между Credit и Analytics. |
| `CABINET_ALPHA_DEV_JWT_SECRET` | Отдельный случайный ключ JWT только для Analytics. Минимум 48 символов. |

При ручной настройке сгенерируйте каждый секрет отдельным вызовом
`secrets.token_hex(32)` на хосте Dev. При выключенном пилоте действует
штатный стек. Kafka и PostgreSQL Analytics
остаются во внутренних сетях Compose. Сети доступа к Analytics DB и
сервисному чтению отделены. Внутренний HTTP запрос использует
`X-Analytics-Read-Token`. Публичный Caddy закрывает `/internal/*`.

## Bootstrap под блокировкой выкладки

Запустите `dev-deploy` в согласованное окно синтетического теста. Внутри
существующей блокировки Dev скрипт делает следующее.

1. Загружает точный образ Kafka по digest из манифеста, сверяет OCI revision
   и закреплённую базу, затем поднимает Kafka и приватный PostgreSQL. Мигратор выполняется от
   `analytics_owner`. Скрипт готовит topic и DLQ нового поколения с
   тремя партициями, проверяет нулевые end offsets. У Analytics нового
   поколения свой том и новая consumer group. Пилот сохраняет историю
   событий на диске брокера вместе со старыми поколениями.
2. Останавливает внешний ingress и writers платформы. Проверяет, что
   outbox Credit поддерживает маршрутизацию по поколению. Читает статусы
   одним SQL-снимком с полями `id`, `version`, `status`. CSV живёт
   в закрытом временном файле.
3. Применяет снимок и маркер поколения одной транзакцией. Повтор
   текущего выпуска проверяет маркер и topic на месте. После успешного
   bootstrap запускаются захват статусов в Credit, consumer Analytics
   и обычные входы. Credit продолжает читать из SQL.
4. Проверяет OCI revision и SHA-256 JAR, соответствие запущенных
   контейнеров digest, маркер снимка, HTTP с токеном и без него и внешний
   ответ `404`. В журнале защищённого job сохраняется итоговый отчёт без
   секретов и строк снимка.

Внешнюю запись прямо в PostgreSQL оставьте остановленной до завершения
bootstrap. Если задача прервётся, повторите `dev-deploy` у того же
манифеста с теми же настройками. Состояние Dev хранит историю использованных
поколений. Это позволяет отказать при выборе старого поколения после
отключения или смены потока.

## Чтение, откат и восстановление

После приёмки теневого прогона установите
`CABINET_ALPHA_DEV_READ_ENABLED=true` для текущего поколения и повторите
`dev-deploy` того же манифеста. В отчёте проверьте авторизованный HTTP
`200` и выполните синтетическую сверку паритета и A09. При ошибках
подождите восстановления потребления в пределах окна приёмки и повторите
проверку закреплённого выпуска. Credit возвращается к SQL по собственной
проверке готовности и outbox.

Для управляемого возврата к SQL установите
`CABINET_ALPHA_DEV_READ_ENABLED=false` и повторите защищённый Dev job.
При неуспешном переключении это разрешено для того же манифеста и поколения.
Выпуск считается текущим после проверки ролей, HTTPS и работающих образов.
Если теневой прогон не прошёл проверку, повторите его с чтением из SQL.
Для выключения всего пилота установите оба переключателя в `false`.
Контейнеры пилота останавливаются, тома и история поколений сохраняются.
Для перехода на манифест без `alpha_dev` сначала выключите пилот.
При повторном включении после отключения либо после восстановления Credit
выберите **новое** поколение и повторите теневой bootstrap. Восстановление
Credit выполняйте по штатной инструкции в согласованном контуре.
[Сценарий проверки восстановления](alpha-pilot-operations.md#возврат-к-sql-и-восстановление)

## Диагностика незавершённого выпуска

Для расследования pipeline #76 предусмотрен отдельный ручной job
`dev-diagnostics`. Параметр `CABINET_DEV_DIAGNOSTICS=1` добавляет его
только в pipeline защищённого ref вне MR и расписания. Job использует
`cabinet-dev` как ресурсную группу. `environment.action: verify` ограничивает
переменные окружением `dev` и сохраняет обычную историю выкладок.
Артефакты сборки и образы для этого job не требуются.
[Семантика GitLab](https://docs.gitlab.com/ci/environments/#access-an-environment-for-preparation-or-verification-purposes)

Существующий SSH-канал передаёт архив диагностического Git SHA и JSON с
`version=1`, `operation=diagnose-v1`, SHA диагностического кода,
целевым SHA `3e434c0adee63917d2fe088e8939207de5b84452` и SHA-256
целевого манифеста `07df658356bbc5e3501b0b00321f0177b6f72f6727e36ba624dfd44b0557791a`.
Строгий обработчик сверяет этот манифест со staged-копией и выполняет
отчёт под общей блокировкой существующего `deploy.lock`. Он читает
выбранные метаданные локального Docker для `cabinet-dev` и завершает
процесс до раскладки релиза. Успех job означает получение
`dev-diagnostics.json`. Подтверждение выкладки ведётся штатным отдельно
запускаемым `dev-deploy`.

Для следующего отказа обычного релиза в ошибке Compose показывается
категория из закрытого списка. Исторические причины по статусам
контейнеров остаются неподтверждёнными, если метаданные уже изменились.
