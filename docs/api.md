# API кабинета

Базовый адрес демо-стенда — `http://localhost:8080/api/v1`. Все данные синтетические.
Полный состав операций, DTO, примеры ошибок и схемы авторизации:
[identity](../contracts/openapi/identity.yaml), [credit](../contracts/openapi/credit.yaml),
[engagement](../contracts/openapi/engagement.yaml),
[external-sim](../contracts/openapi/external-sim.yaml). Интерактивная проверка — `/swagger/`;
импортируемые запросы и команды — [contracts](../contracts/README.md).

## Вход и границы доступа

`POST /auth/sign-in` принимает email/пароль и возвращает `token` и профиль.
`POST /auth/sign-up` подключает компанию по корректному синтетическому ИНН с `00`,
сохраняет согласие на обработку данных и возвращает сессию. Обе операции возвращают
200; создание заявки, документа и новой версии правил — 201.
Для защищённых операций нужен `Authorization: Bearer <token>`.

Подпись, срок и версия учётных данных проверяются сервером. Компания (`cid`), роль
и право подписи (`sign`) берутся из токена; передача чужого `companyId` в JSON не
меняет владельца. Проверка владения предшествует выдаче данных; чужой объект — 404.
Проверки интерфейса не заменяют серверный запрет.

| Роль | Возможности |
| --- | --- |
| Клиент | Компания и заявки своей компании, черновики, отправка, документы, отзыв, оффер и график |
| Клиент с `canSign` | Дополнительно подтверждение подписи; наличие кнопки само по себе не даёт право |
| Кредитный менеджер | Очередь и оценка, запрос документов/пояснений; без одобрения, контрпредложения и отказа |
| Андеррайтер | Ручное одобрение, контрпредложение, запрос сведений, обоснованный отказ |
| Риск-администратор | Чтение банковских данных/аналитики и создание новых версий правил; отдельная роль не заменяет роль андеррайтера |

Банк не видит чужие черновики в очереди. Списки уведомлений относятся к пользователю,
а не ко всем сотрудникам компании сразу. Помощник читает заявку с тем же JWT.

## Identity

| Запрос | Назначение |
| --- | --- |
| `GET /auth/options` | Доступность демонстрационного входа, без JWT |
| `POST /auth/sign-up`, `POST /auth/sign-in` | Подключение компании и вход, без JWT |
| `GET /auth/session` | Свежая сессия текущего пользователя |
| `GET /users/me` | Текущий профиль |
| `GET /companies/me` | Компания клиента и её представители |

Внутренние чтения пользователей/компаний и версии учётных данных находятся под
`/internal/v1/`. Они скрыты из OpenAPI и не опубликованы шлюзом.

## Credit: клиентский путь

1. `GET /products`, `/products/purposes`, `/products/{code}` — публичный каталог.
   `POST /products/match` подбирает продукты; `GET /products/{code}/calculation`
   вычисляет ориентировочный график по сумме и сроку.
2. `POST /applications` создаёт черновик из кода продукта, цели, суммы, срока,
   заявленной выручки/платежей и согласия БКИ. Компания определяется сервером.
3. `PUT /applications/{id}` сохраняет редактируемый черновик.
4. `POST /applications/{id}/documents?type=...` принимает multipart-поле `file`.
   Типы и ограничения определяются требованиями заявки; до 20 МБ по умолчанию.
   `GET .../documents/{documentId}` скачивает файл после проверки прав,
   `DELETE` удаляет документ из редактируемого черновика.
5. `POST /applications/{id}/submit` запускает конвейер. Заголовок
   `Idempotency-Key` делает повтор отправки безопасным; используйте ключ до 128
   символов. Повтор с тем же пользователем/ключом и заявкой возвращает её текущее
   состояние; привязка ключа к другой заявке — 409.
6. `GET /applications/{id}` возвращает статус, доступные действия и `process`.
   Запрос повторяют с паузой и ограничением общего времени ожидания.
7. Если запрошены сведения: загрузить документы и вызвать `POST .../info-provided`.
   Файл должен быть загружен после соответствующего запроса; ответы на вопросы
   передаются полем `answer`.
8. `POST .../offer/accept` принимает действующий оффер и начинает подписание.
   `POST .../offer/decline` закрывает его. Если сервис подписи был недоступен,
   `POST .../signing/code` получает новую сессию.
9. `POST .../sign` с полем `code` подтверждает подпись. Далее воркер выполняет
   выдачу; результат сохраняется в `process.loan`.
10. `GET .../schedule` возвращает график; `GET .../events` — журнал.
    До подписания можно вызвать `POST .../withdraw` в допустимом состоянии.

Черновик не отправляется, если не хватает обязательных данных. Статус и
`allowedActions` важнее предположений клиента: неверное действие или проигранная
конкурентная запись возвращает 409. Детали переходов — [автомат](state-machine.md).
Одна компания не может иметь две активные заявки на один продукт.

## Credit: действия банка

| Запрос | Доступ и результат |
| --- | --- |
| `GET /applications?status=...` | Очередь банка или список своей компании |
| `GET /underwriting/applications/{id}` | Карточка оценки, источники, расхождения, рекомендация и разрешённые действия |
| `POST .../approve` | Андеррайтер: оффер на запрошенных условиях |
| `POST .../counter-offer` | Андеррайтер: другие сумма/срок/продукт с объяснением |
| `POST .../request-info` | Менеджер/андеррайтер: документы и вопросы со сроком |
| `POST .../reject` | Андеррайтер: отказ с объяснением для клиента |
| `GET /rules` | Сотрудник банка: текущие параметры и история версий |
| `POST /rules` | Риск-администратор: новая версия и обязательный комментарий |
| `GET /analytics/funnel?from=...&to=...` | Сотрудник банка: воронка и время по фактическим записям |

Ручное решение не переписывает автоматическую оценку. При отклонении от
рекомендации требуется обоснование. Период аналитики задаётся ISO 8601; `from`
включается, `to` не включается. Учитывайте различие часов вызывающего компьютера
и сервера при коротких проверочных интервалах.

## Engagement и симуляторы

`GET /notifications`, `/notifications/unread-count`, `POST /notifications/{id}/read`
и `/notifications/read-all` работают только с текущим получателем. Помощник:
`GET /assistant/status`, `POST /assistant/messages` с вопросом, необязательным
`applicationId` и историей. Объект другого клиента недоступен и через помощника.

Симуляторы используют `X-Api-Key`, БКИ также получает `X-Consent-Id`. Эти
`/ext/...` API доступны внутри сети Compose; снаружи gateway возвращает 404.
Демонстрационный `/sim/` управляет режимами `OK`/`SLOW`/`DOWN`, а не реальными
реестрами. Его отключение относится к настройкам развёртывания.

## Ошибки и диагностика

| Код | Как понимать |
| --- | --- |
| 400 | Неверный JSON, формат поля, ограничение или недопустимое значение |
| 401 | Нет пригодного JWT, токен истёк/отозван; для `/ext/` — нет ключа системы |
| 403 | Роль или право подписи не разрешает действие; управление симулятором выключено |
| 404 | Объект отсутствует или скрыт от этой компании; закрытый путь шлюза |
| 409 | Неверное текущее состояние, версия изменилась, конфликт ключа или активной заявки |
| 429 | Ограничение частоты входа, загрузок или вопросов помощнику |
| 503 | Временная недоступность сервиса подписи при получении кода/подписании |

Ошибки приложений имеют `timestamp`, `status`, `error`, `message`, `path` и
`requestId`. Фильтр ключа симулятора возвращает сокращённые `status/error/message`;
отдельная схема сохранена в контракте. Лимит gateway для `/api/v1/auth/` также возвращает
JSON с русским `message`, `Retry-After` и совпадающим `X-Request-Id`; поле `path`
обозначает общую зону `/api/v1/auth/`. Другие ошибки самого nginx могут иметь другое тело.
`X-Request-Id` ответа помогает найти запрос в журнале. Повтор после 409 требует
чтения текущего состояния; не следует автоматически повторять любое действие.
