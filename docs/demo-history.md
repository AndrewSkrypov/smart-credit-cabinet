# Синтетическая история и сброс

Скрипт создаёт **120 заявок** через настоящий клиентский и банковский API. Он не пишет
в БД, не меняет серверные часы и не подставляет даты. Полная история допускает 100–200
заявок; 12 — короткая проверка всех типов. ИНН сценарных и новых компаний начинаются с
`00` и проходят контрольные суммы; данные не относятся к реальным компаниям.

Нужны Docker Compose v2 и Python 3.11+. Из корня репозитория:

```bash
python3 scripts/seed-demo-history.py --start --count 120
```

Создаётся **отдельный** проект `cabinet-demo-history`, кабинет доступен только на
http://127.0.0.1:18082. Демо-учётки и пульт включены; это локальная демонстрация.
Используются стандартные пароли из README. Остальные Compose-проекты не меняются.
При первом запуске образы собираются из исходников. Если для **этого же кода** уже
есть пять локальных образов, можно явно передать `--image-prefix cabinet-submission`;
иначе этот параметр не нужен. Для своих порта/проекта задайте `--port` и `--project`
с именем вида `cabinet-demo-example`.

На время прогона INFO/OFFER TTL равен 60 секундам: закрытия происходят настоящим
обработчиком сроков. В `finally` TTL возвращается к 30 минутам; это подтверждается
полем `normal_timings_restored`. При аварийном завершении процесса выполните
`python3 scripts/seed-demo-history.py --start --no-build --count 12` после сброса.
Не запускайте параллельно другие сценарии, меняющие политику или пульт этого проекта.
Скрипт откажется продолжать при отключённых демо-учётках, неисправных источниках,
активной заявке сценарной компании или неожиданном решении правил.

## Что появляется

Десять повторов двенадцати случаев: автоматическое одобрение, контрпредложение правил,
стоп-фактор, низкий рейтинг, одобрение/отказ/контрпредложение андеррайтера, новая компания,
отзыв, истечение оффера, истечение запроса сведений, загрузка документов и ответ на запрос.
Завершённые положительные пути доходят до выдачи. Каждый проход имеет собственную
заявку; проверяются конечный статус, единственный SUBMIT и реальные события журнала.
Измеряются воронки до/после. Времена этапов относятся к текущему прогону, история
не растягивается искусственно на прошлые месяцы.
«Технопарк» используется в первом цикле; последующие документные сценарии получают
новые компании. Так один пользователь не исчерпывает штатный лимит 30 загрузок за
10 минут, особенно при повторе загрузки из-за немонотонных дат. Лимитер не выключается.

Отчёт `scripts/demo-reports/history.json` содержит ID, статусы, события и агрегаты,
без JWT, паролей и кодов подписания. Он исключён из Git. Сводные измерения двух
полных запусков — [demo-results/history.json](demo-results/history.json).
CI повторяет **120 → reset → 120** и публикует `demo-history-reports`.

Собственные даты симуляторов и часы VM могут влиять на оценку компании. Скрипт
проверяет фактический результат и падает при отклонении; не исправляет его SQL-вставками.
Зафиксированная особенность свежести документов при обратном ходе часов описана в
[reliability.md](reliability.md).

## Вернуть исходное демо-состояние

**Все данные только указанного проекта будут удалены**, включая документы и историю:

```bash
bash scripts/demo-reset.sh --project cabinet-demo-history --confirm-project cabinet-demo-history
python3 scripts/seed-demo-history.py --start --no-build --count 120
```

В Windows используйте Git Bash (`PYTHON=python bash ...`) либо тот же обработчик напрямую:
`python scripts/demo-reset.py --project cabinet-demo-history --confirm-project cabinet-demo-history`.
`--no-build` у reset позволяет повторно использовать уже собранные образы.

Нужны точное повторное имя, префикс `cabinet-demo*` и демо-конфигурация контейнеров.
Производственные имена не принимаются. Reset удаляет только тома своего проекта,
вновь запускает его и чтением PostgreSQL подтверждает **0 заявок**. Результат —
`scripts/demo-reports/reset-cabinet-demo-history.json`. Сценарные пользователи,
продукты и базовая политика возвращаются миграциями/демо-инициализацией.
Неверное подтверждение или prod-имя завершают команду до изменения контейнеров.

IPv4-адрес выбран по измерению на Windows: три GET через `localhost` заняли
2125/2048/2040 мс, через `127.0.0.1` — 5,56/22,37/3,09 мс при IPv4-only публикации
порта. Это эффект клиента/разрешения loopback, не ускорение кредитного конвейера.
