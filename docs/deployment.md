# Развёртывание, резервная копия и восстановление

## Для какого стенда предназначен комплект

Это способ разместить проверяемый прототип на одном Linux VPS, а не замена инфраструктуры
банка. Нужны x86_64, 4 GiB RAM, диск с запасом под образы/БД/копии, постоянное имя сервера,
Docker Engine и Compose **2.24.4+**, Python 3.11+ и Git. Можно использовать уже доступную
учебную VM либо бесплатный/пробный или недорогой VPS с такими ресурсами; ограничения,
цену, резервное место и доступность тарифа проверяет владелец. Сервер в рамках этой
работы не арендовался. Ubuntu 24.04 LTS подходит при установке Engine по
[официальной инструкции](https://docs.docker.com/engine/install/ubuntu/).

Профиль `prod` включает три сервиса с БД, симуляторы, frontend, gateway и Caddy.
Spring-сервисы получают `SPRING_PROFILES_ACTIVE=prod`. Сумма лимитов — **2736 MiB**,
включая временный `db-init`; оставшееся место 4 GiB нужно ОС, Docker и резерву.
`credit` — 640 MiB, identity/engagement — по 512, external-sim/PostgreSQL — по 384,
frontend/Caddy — по 96, gateway — 48, db-init — 64. Heap JVM ограничен 55% лимита.
PostgreSQL: shared_buffers 96 MB, work_mem 4 MB, до 60 соединений.

На 4 GiB не включайте `ai` и `monitoring`: модель одна имеет лимит 4 GiB, мониторинг
добавляет 768 MiB. Обёртки очищают `COMPOSE_PROFILES`, чтобы случайная переменная окружения
не включила тяжёлый профиль. Эти бюджеты проверяются локально cgroup-лимитами и нагрузкой;
это не испытание настоящего VPS с физически ограниченной памятью, его CPU/диском/сетями.

## Подготовка

Работайте с чистым checkout нужного выпуска ветки `feature/submission-kit`. JDK/Node
на сервере не обязательны: обычная сборка проходит внутри Docker. Python-инструменты:

```bash
python3 -m venv .venv-deploy
. .venv-deploy/bin/activate
pip install -r scripts/requirements-tools.txt
python deploy/configure.py --domain cabinet.example.org --email owner@example.org
python deploy/start.py --project cabinet-prod --check-only
python deploy/start.py --project cabinet-prod
```

Замените домен/почту своими. `configure.py` создаёт `deploy/.env` с новыми разными
секретами БД, JWT и симуляторов, не печатает их и не перезаписывает существующий файл.
В Linux файл создаётся с правами 0600; на Windows дополнительно учитывайте ACL каталога.
`.env`, варианты `.env.*`, runtime и копии исключены из Git и Docker build context.
Храните секреты отдельно от репозитория и ограничьте доступ к серверу. **Не создавайте
новый пароль БД поверх существующего тома**: изменение env не меняет пароль роли PostgreSQL.

До запуска направьте A/AAAA домена на сервер и откройте входящие TCP 80/443, плюс свой SSH.
Ошибочную AAAA-запись удалите или настройте IPv6. Порты БД, сервисов, Actuator и панели
мониторинга не публикуются. Учитывайте
[ограничения firewall при публикации Docker-портов](https://docs.docker.com/engine/install/ubuntu/#firewall-limitations).

Caddy получает и продлевает публичный сертификат автоматически при выполнении
[условий ACME](https://caddyserver.com/docs/automatic-https): доступный домен, 80/443 и
постоянный записываемый `/data`. HTTP переводится на HTTPS. Caddy data/config хранятся
в отдельных именованных томах. Первую выдачу и продление публичного сертификата должен
проверить владелец на своём сервере; локальное испытание этого не доказывает.

## Граница доступа и первая учётка банка

Наружу открыт только Caddy. Он закрывает `/sim`, `/ext`, `/internal`, `/actuator`, Swagger
и OpenAPI. Gateway не имеет host-порта. Между Caddy и gateway — отдельная сеть; gateway
доверяет forwarded-заголовкам только точному адресу Caddy, затем передаёт проверенные IP
и HTTPS. Адреса по умолчанию: `EDGE_SUBNET=172.30.40.0/28`, Caddy `.2`, gateway `.3`.
При конфликте с существующей Docker-сетью измените **все три** поля .env согласованно.
Конфигурация gateway генерируется отдельно для каждого проекта.

`DEMO_ACCOUNTS=false` создаёт заблокированные демо-записи на чистой БД. Эта Flyway-настройка
не блокирует ранее созданных пользователей повторно. Поэтому `start.py` сначала останавливает
ingress, ждёт сервисы, дополнительно блокирует существующие `@demo.test` и увеличивает их
credentials_version, затем открывает Caddy. Миграции не редактируются. Переключатели
симуляторов выключены `SIM_CONTROL_ENABLED=false`: внутреннее чтение состояния остаётся,
но изменения дают 403, а внешние маршруты закрыты Caddy полностью.

Создайте отдельного оператора с собственной почтой и паролем, например:

```bash
python deploy/provision-bank-user.py --project cabinet-prod --role UNDERWRITER --email reviewer@example.org --name "Оператор банка"
```

Пароль вводится скрыто дважды, 16–72 байта UTF-8. Используется bcrypt 5.0.0, cost 12,
совместимость проверена настоящим входом в identity. Plaintext/хэш не выводятся и не
передаются аргументом процесса. Роли также MANAGER/RISK_ADMIN. Операция идёт через локальный
административный доступ Docker к выбранной БД; это не новый публичный endpoint повышения
роли. Повторный запуск не перезаписывает существующий email. `--password-stdin` нужен
для изолированных автоматических проверок, а не для помещения пароля в командную строку.

## Обновление и остановка

Сначала создайте копию, сохраните текущий SHA и проверьте зелёный CI нового SHA. Обновляйте
чистую рабочую копию; не заменяйте .env и тома. Выбор выпуска меняет только одну строку:

```bash
python deploy/backup.py --project cabinet-prod
git fetch origin feature/submission-kit
git checkout --detach НОВЫЙ_ПРОВЕРЕННЫЙ_SHA
python deploy/set-release.py НОВЫЙ_ПРОВЕРЕННЫЙ_SHA
python deploy/start.py --project cabinet-prod
```

Образы приложений получают тег выбранного SHA. Это локальные образы, registry не требуется.
Сборка проверяет, что checkout чистый и HEAD точно равен `CABINET_RELEASE`; одна смена
метки не превращает старый код в новый выпуск. В образы записывается OCI revision.
Старый тег сохраните для отката. Если нужны только образы без запуска, используйте
`python deploy/build.py --project cabinet-prod` — это важно перед восстановлением.
Остановка без удаления данных: `python deploy/stop.py --project cabinet-prod`.
Обновление имеет окно недоступности; rolling/zero-downtime здесь не заявляются.
Не откатывайте приложение поверх несовместимой новой схемы БД: сначала проверьте
совместимость миграций либо восстановите соответствующую копию в отдельный проект.

## Резервное копирование

```bash
python deploy/backup.py --project cabinet-prod
```

Сначала останавливаются Caddy и сервисы, которые пишут в БД/документы. Затем снимаются
три `pg_dump -Fc` без глобальных ролей/паролей PostgreSQL и архив общего тома документов.
Таблицы, содержимое строк и значения последовательностей получают контрольные SHA256;
файлы — размеры и SHA256. Сервисы возобновляются в `finally`, после их здоровья — ingress.
Исходная копия остаётся, даже если последующий запуск не удался: смотрите отдельно
`backup_complete` и `source_resumed` в manifest, а не только наличие файлов.

Копия — **закрытый каталог** `deploy/backups/<UTC-время>-<id>/`, четыре файла и manifest.
В ней есть документы и хэши паролей пользователей; она не обезличена. Ограничьте доступ,
шифруйте и храните отдельную проверенную копию вне диска сервера. .env, ключи Caddy и
образы в неё не входят; секреты и выбранный Git SHA храните отдельно. SHA256 обнаруживает
повреждение, но не удостоверяет доверенность источника, если атакующий подменил и manifest.

Согласованность достигается остановкой записи всех трёх сервисов, а не общей транзакцией
трёх БД. Память симуляторов и очереди доставки уведомлений не переносится. Завершённые
кредиты/графики/документы сохраняются в БД и файлах; незавершённое подписание после потери
памяти симулятора требует отдельной проверки восстановления сессии. Это не резервная
копия настоящей внешней АБС или провайдера подписи.

## Восстановление

Восстанавливайте **в новый пустой** `cabinet-prod-restore*` проект, а не поверх источника.
Выберите тот же Git SHA/тег приложений, что указан в manifest. Подготовьте новые секреты,
другую непересекающуюся внутреннюю сеть и соберите приложения без запуска:

```bash
python deploy/configure.py --domain cabinet.example.org --email owner@example.org --output deploy/runtime/restore.env
python deploy/set-release.py SHA_ИЗ_MANIFEST --env-file deploy/runtime/restore.env
python deploy/build.py --project cabinet-prod-restore --env-file deploy/runtime/restore.env
python deploy/restore.py ПУТЬ_К_КАТАЛОГУ_КОПИИ --project cabinet-prod-restore --env-file deploy/runtime/restore.env
```

На прежнем VPS перед запуском восстановленного проекта остановите исходный через
`deploy/stop.py`, освободив 80/443 и память. Даже остановленная исходная Docker-сеть остаётся:
в restore.env задайте, например, `EDGE_SUBNET=172.30.41.0/28`, `CADDY_EDGE_IP=172.30.41.2`,
`GATEWAY_EDGE_IP=172.30.41.3`. На другом сервере проверьте DNS перед ACME. Не запускайте
два полных prod-стенда одновременно на VPS 4 GiB.

Restore сначала проверяет состав/хэши копии и пути tar, запрещает ссылки/дубликаты/выход
из каталога. Затем поднимает только PostgreSQL, требует пустые целевые БД/том, восстанавливает
данные, сравнивает все таблицы/последовательности **до запуска worker**, извлекает файлы и
ещё раз сравнивает их SHA256. После этого запускает приложения и Caddy. Повторный restore
в непустой проект отклоняется, данные автоматически не удаляются. Новая JWT_SECRET делает
прежние токены недействительными; пароли пользователей из БД сохраняются. При необходимости
постоянной совместимости сессий решение о сохранении секрета принимает владелец отдельно.

## Локальная приёмка без внешнего сервера

```bash
docker compose build
python deploy/test-local.py --image-prefix smart-credit-cabinet --companies 20
```

Первая команда собирает пять приложений. Вторая использует их реальные image ID, создаёт
два новых случайно названных проекта, новые секреты/сети и loopback-порты 19443/19444,
прогоняет 20 компаний до выдачи, делает backup/restore и сверяет API/файл. Префикс образов
должен соответствовать вашему `docker compose -p`: например, для `-p cabinet-submission`
это `--image-prefix cabinet-submission`. Локальная метка `local-verification-*` обозначает
именно эти проверяемые образы, а не обещает новый билд по текущему SHA.

Используется **Caddyfile.local с внутренним CA**, без внешнего ACME. Корневой сертификат
копируется только в runtime выбранного проекта и доверяется отдельным Python SSLContext;
глобальное доверие Windows/Linux не меняется. Выделенные проекты удаляются в `finally`,
включая их тома; `--keep` оставляет только созданные этим запуском проекты для осмотра.
Существующие проекты, образы-источники и произвольные тома не удаляются. Копии остаются
в закрытом `deploy/backups`, очищенные отчёты — в `deploy/reports`.

Проверены отдельно: свежий запрет демо-входа и блокировка одной ранее активной демо-записи
до открытия HTTPS; реальные вход/выдача/PDF; восстановление в другой проект с новыми
секретами, совпадение таблиц/последовательностей, статуса DISBURSED, графика и PDF 600 байт.
Полный прогон памяти и повторный restore фиксируются отдельным JSON, не подменяются
успешным `/actuator/health`. Публичные результаты — [deployment-results](deployment-results/README.md).

## Диагностика

Ошибку запуска отделяйте от готовности приложения: смотрите stage, health/exit/OOM/restart,
логи конкретного проекта и [runbook](operations.md). Нет сертификата — проверить DNS,
80/443 и права Caddy /data. 502 — здоровье backend/DNS сети. Невозможен вход БД после
смены env — проверить реальную роль БД и сохранённый секрет, не удалять том. Есть FAILED
задачи — сопоставить заявку/шаг/last_error, не менять массово статусы SQL. Перед любой
операцией восстановления сохраните источник и проверьте копию в отдельном стенде.
