# Gateway: ограниченные ожидания и безопасные повторы

`docker/gateway/nginx.conf` использует динамическую upstream-группу `cabinet_credit`
для записей. Docker DNS обновляется каждые 5 секунд, разрешение имени ограничено
1 секундой. Общая зона 64 KiB хранит состояние адресов между worker-процессами;
после одной ошибки экземпляр исключается на 5 секунд, пока в группе несколько адресов.
GET/HEAD разрешают `credit:8080` через переменную в отдельный список адресов запроса:
обновление общей DNS-группы не может удалить оставшуюся попытку уже начатого чтения.
Для чтений состояние отказов между запросами не общее; это увеличивает число ожиданий
при зависшем экземпляре, сохраняя ограничение времени каждого запроса. Один credit поддерживается.
Production-конфигурация генерируется из того же файла `deploy/render-gateway.py`:
доверие forwarded-заголовкам ограничено приватным адресом Caddy.

| Запрос | Соединение | Отправка / чтение upstream | Повтор |
| --- | --- | --- | --- |
| GET/HEAD к credit, включая документы и OpenAPI | 1 с | 5 / 5 с | До двух разных адресов при error/timeout/502/503/504; окно начала повторов 8 с |
| POST/PUT/PATCH/DELETE и остальные методы | 1 с | 30 / 30 с | `proxy_next_upstream off`, в том числе при отказе соединения |
| Остальные сервисы | 1 с | 30 / 30 с | Отключён |
| Помощник | 1 с | 30 / 120 с | Отключён |

Маршрут GET/HEAD выбирается через `map` и внутренний named location. Метод, URI,
query string и Authorization сохраняются. Публичных 418 нет. `401`, `403`, `404`,
`409`, `429` не повторяются. Закрытые `/internal/` и `/ext/` остаются закрытыми.
После отправки клиенту части ответа Nginx не может перенести скачивание на другой
экземпляр. Повтор записи остаётся решением клиента с контрактом идемпотентности,
а не действием gateway; нельзя считать любой timeout доказательством отката.
`load/gateway-write-refusal.py` проверяет отдельный случай: недоступный первый адрес
и исправный резервный. POST/PUT/PATCH/DELETE должны получить 502 с одной попыткой;
при разрешённом `error` запрос ушёл бы на резервный адрес. Конфигурация gateway
смонтирована только для чтения, поэтому проверка запускает рядом временный Nginx из того
же образа и в той же сети с его действующей конфигурацией, меняя только адреса upstream
credit, и удаляет его после завершения; сам gateway стенда не меняется.
Запросы неавторизованы и не создают бизнес-данные.

При интеграции с main `9782707` проверка сначала выполнена на его конфигурации и
синтетическом резервном HTTP-ответчике: все четыре метода сделали две попытки и
получили 401 от резервного адреса. После отключения повторов все четыре получили
502 от единственной попытки к закрытому порту. Это проверка политики настоящего
Nginx, а не измерение бизнес-операций; в CI та же проверка использует здоровый credit.
Отдельные тесты ниже проверяют бизнес-записи и падение настоящего экземпляра.

## Границы бюджета времени

`proxy_read_timeout` и `proxy_send_timeout` ограничивают паузу между операциями,
а не полную продолжительность передачи. `proxy_next_upstream_timeout` ограничивает
переход к следующей попытке, но не обрывает уже начатую. Для запроса без тела и
upstream, который совсем не отвечает, две попытки имеют оценку до 12 секунд
(дважды connect 1 + read 5), плюс разрешение DNS и планирование. В проверке
используется клиентский предел 15 секунд. Это не абсолютный deadline произвольного
ответа: медленный непрерывный поток может идти дольше, как и большой файл.
Нельзя называть 8 секунд общим максимальным временем HTTP-запроса.

Основание: официальные описания
[повторов](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream),
[read timeout](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)
и [динамического upstream](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#server).
Параметр `resolve` доступен в открытом Nginx начиная с 1.27.3; образ закреплён на 1.30.5.

## Повторяемая проверка

Только отдельный синтетический проект, два credit, исправные identity/Valkey/БД.
Проверка останавливает или приостанавливает один контейнер и возвращает его в `finally`.
Тома не удаляются. Нельзя запускать параллельно другим тестам того же стенда.

```bash
python3 load/gateway-fault.py --project cabinet-e2e --label gateway-current --expect-hardened
python3 load/gateway-write-fault.py --project cabinet-e2e --label gateway-writes
```

Первый скрипт проверяет 32 здоровых, 32 при зависании, 16 после возобновления и
32 после SIGKILL запросов GET/HEAD, concurrency 8, timeout 15 с. IP из реальных
gateway-логов сверяются с Docker inspect. Журнал содержит только request ID, метод,
статус, адрес upstream и время; токены и тела не публикуются. Четыре небезопасных
метода должны иметь одну upstream-попытку. Флаг `--expect-hardened` дополнительно
требует ноль ошибок чтения и фактически наблюдаемый переход между адресами.

Второй скрипт создаёт восемь отдельных компаний, приостанавливает credit и отправляет
по одному POST создания заявки, параллельно проверяя PUT/PATCH/DELETE. Для каждой
попытки журнал должен показать ровно один upstream. После возобновления API и история
сверяются на отсутствие дублей, затем передаются 12 MiB PDF через настоящий AV/storage
и сравниваются байты скачанного файла. Выполняется обычный запрос к помощнику.
Это проверка маршрута помощника; качество и длительность ответа модели измеряются отдельно.

Оба прогона — `cabinet-release-work`, одинаковые образы Java и тестовые запросы.
Первичный прогон до изменения Nginx сохранён; это новое сравнение, а не повторное
использование восьми ошибок из прежнего спринта. Percentiles считаются nearest-rank
по исходным длительностям, включая сетевые таймауты.

После SIGKILL вся пачка GET/HEAD завершилась за 1,008 с вместо 15,238 с.
При зависании — 4,831 с вместо 30,062 с. Первое успешное чтение здорового экземпляра
занимало 0,013–0,019 с; это не время восстановления упавшего процесса.

Отдельно выполнен одинаковый `chaos.py crash` для двух новых когорт по 20 компаний
(lease 15 с, source timeout 45 с, external read timeout 2 с). До: 264 чтения/действия,

различается, потому что раньше клиентские потоки простаивали на таймаутах.

за 23,970 и 24,153 с соответственно; ускорение бизнес-конвейера не заявляется.
В обеих когортах повторены восемь арендованных задач, все 20 решений достигнуты,
нулевые duplicate offers / failed jobs / due open jobs, один SUBMIT и без дублей

POST/PUT/PATCH/DELETE имели ровно один upstream в журнале, дублей нет.
12 582 957 байт PDF прошли AV, S3 и скачивание с совпадением SHA256 за 1,106 с;
обычный запрос помощника вернул 200 за 3,907 с. Это измерение текущего rules/fallback
маршрута, а не приёмка качества отдельной модели.

### Уточнение после полноценного CI

CI SHA `18ed7c9`, run `39965949697`, впервые исполнил проверки после прежнего
ограничения аккаунта. Он выявил гонку: после SIGKILL **24/32** чтения вернули 200,
**8/32** — 504 за 1 с; в журнале у неудачных запросов ровно одна попытка.
Локальный повтор прежней конфигурации дал 32/32 — дефект зависит от момента DNS-обновления.

Исходник закреплённого Nginx показывает два препятствия повтору при изменении общей
группы: проверку поколения адресов при выборе следующего peer и сброс `tries=0`,
когда группа стала одиночной при освобождении прежнего peer. Это объяснение по коду,
а не наблюдение внутренних переменных CI. Чтения теперь используют список адресов,
принадлежащий запросу; записи остаются без повторов. Основание — функции
`ngx_http_upstream_create_round_robin_peer`, `ngx_http_upstream_get_round_robin_peer`
и `ngx_http_upstream_free_round_robin_peer` в
[исходнике Nginx 1.30.5](https://github.com/nginx/nginx/blob/release-1.30.5/src/http/ngx_http_upstream_round_robin.c).

После изменения локально: зависание **32/32 HTTP 200**, p95 **4,754 с**,
вся пачка **14,159 с**; SIGKILL **32/32 HTTP 200**, p95 **0,974 с**,
вся пачка **2,004 с**. Нулевых ошибок не следует путать с улучшением throughput:
из-за отдельных списков адресов больше запросов ожидают зависший peer.
Новые цифры относятся к этой конфигурации; прежняя таблица выше сохранена как история.

Повтор записей: **8** черновиков, **8** CREATED, **0** дублей; **3** POST вернули
504, но затем сохранились. Все 11 POST/PUT/PATCH/DELETE имели по одной попытке.
12 582 957 байт PDF прошли AV/S3 и скачивание с совпадением SHA256 за **3,233 с**.
Исходные отчёты — [gateway-final-local.json](reliability-results/gateway-final-local.json).

Тот же CI выявил отдельную ошибку изоляции аварийных тестов: `chaos.py crash`
завершал cleanup сразу после `docker start`, и следующая подготовка получила 502
на POST создания заявки в ещё запускавшийся credit. Cleanup теперь ждёт реального
Docker health не более 90 с и сохраняет время восстановления; неготовность завершает
тест ошибкой. Условия аварийного этапа и запрет повторять запись сохранены.
Проверки ожидания отличают starting/unhealthy/healthy, остановившийся процесс и deadline.
Полная приёмка требует зелёного CI окончательного опубликованного SHA.
