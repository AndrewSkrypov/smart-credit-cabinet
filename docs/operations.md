# Эксплуатация и наблюдаемость

Для PostgreSQL: [роли, обновление, восстановление и диагностика](database-isolation.md).
Три *-migrate должны завершиться с exit 0 до старта соответствующих HTTP-сервисов.

Для общего Valkey: [пороги, метрики и runbook](shared-state.md#runbook).
`cabinet_shared_limits_total` различает allowed/limited/unavailable; ошибки кэша отзыва
видны в `cabinet_revocation_cache_total`. Отказ Valkey не включает локальные квоты,
потеря identity не разрешает непроверенный JWT. Не применяйте FLUSHDB как способ
восстановления доступности: это обнулит окна ограничения.

## Переписка по заявке

Сообщения хранятся в credit; `application_chat_audit` — отдельный аудит, `application_events`
остаётся бизнес-журналом. Если сообщение записано, но уведомление ещё не появилось,
проверить outbox credit и receipt engagement по обычному runbook доставки. Тип уведомления
— `APPLICATION_MESSAGE`, ключ дедупликации содержит UUID сообщения и адресата/роль.
Счётчик списка обновляется периодически: клиент — 5 секунд, банк — 10 секунд.
Открытая переписка проверяет новые сообщения каждые 5 секунд. Не исправлять вручную
последовательности, курсоры и неизменяемый аудит. Непрочитанное подтверждается при
видимом конце переписки; открытие невидимого раздела само по себе его не сбрасывает.

## Запуск

```bash
docker compose --profile monitoring up --build -d
python monitoring/verify.py --require-activity
```

Перед второй командой проведите заявку до решения, например коллекцией Newman из
[сценариев](test-scenarios.md). Пустой стенд можно проверить без `--require-activity`.
Если запущены две реплики `credit`, добавьте `--replicas 2`. Не используйте другой project
name с теми же опубликованными портами. Для существующего проекта передайте прежнее `-p`
и те же compose-файлы. В CI проверка идёт после нагрузки и ошибок источников.

Prometheus: http://localhost:9090, targets: `/targets`, alerts: `/alerts`.
Grafana: http://localhost:3000, дашборд **«Кредитный конвейер»** в папке «Кабинет»,
UID `credit-pipeline`. Локальный вход: `admin` / `local-monitoring-change-me`;
переопределения — `GRAFANA_USER`, `GRAFANA_PASSWORD`, `GRAFANA_PORT`, `PROMETHEUS_PORT`.
Оба порта слушают только `127.0.0.1`; на сервере используйте SSH-туннель и собственный пароль.
Изменение env-пароля не меняет уже созданного администратора в существующем томе Grafana.

Prometheus 3.15.1 и Grafana 13.2.4 работают как отдельные открытые компоненты.
Конфигурация, datasource и 14 панелей поставляются в [monitoring](../monitoring/prometheus.yml).
[DNS discovery](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#dns_sd_config)
для `credit` получает все A-записи Docker, а не один случайно выбранный IP.
[Provisioning Grafana](https://grafana.com/docs/grafana/latest/administration/provisioning/#dashboards)
читает файлы при запуске. Изменять дашборд следует в репозитории; правка через UI не сохраняется.
Prometheus хранит до 7 дней / 512 MB, его память ограничена 256 MB;
Grafana — 512 MB с `GOMEMLIMIT=384MiB`. Проверка браузером при исходных 256 MB
привела к перезапускам и недогруженным панелям, поэтому одного успешного `/api/health`
недостаточно для выбора лимита.
Профиль мониторинга добавляет ресурсы к приложениям; 4 GB комплект проверяется отдельно
без тяжёлых необязательных профилей.

## Что означают метрики

| Метрика Prometheus | Значение и агрегация |
| --- | --- |
| `cabinet_pipeline_step_seconds_*` | Histogram времени одной попытки шага, `step`, `result=completed/exception`. Включает внешние вызовы и запись результата, не ожидание в очереди. `completed` не означает финальное одобрение заявки. Rate/count суммируются по экземплярам. |
| `cabinet_source_call_seconds_*` | Histogram вызова источника, `source`, `result=success/not_found/rejected/timeout/error/circuit_open`. 404 — полученный ответ, а не отказ источника. Open breaker означает пропущенный вызов, не сетевой запрос. |
| `cabinet_source_breaker` | One-hot gauge состояния каждого breaker каждого экземпляра; состояние в label `state`. |
| `cabinet_pipeline_jobs` | Gauge общей БД по `status` и корзине попыток `0/1/2-4/5+`; сначала `max by (status, attempts)`, потом сумма нужных корзин. |
| `cabinet_decisions` | Gauge числа сохранённых решений по `outcome`, `actor`. Включает промежуточные REQUEST_INFO/MANUAL_REVIEW и повторные решения; это не число уникальных заявок и не counter. `max by (outcome, actor)` исключает удвоение по репликам. |
| `cabinet_decision_time_average_seconds`, `...maximum_seconds` | По всей БД: от первого SUBMIT до первого APPROVE/COUNTER_OFFER/REJECT каждой заявки. Ожидание ручного решения входит; REQUEST_INFO/MANUAL_REVIEW не считаются итоговым решением. Это исторические среднее/максимум, не percentile за окно. Нет наблюдений — NaN. |
| `cabinet_pipeline_queue_oldest_due_seconds` | Возраст самой старой PENDING-задачи, срок которой уже наступил; будущее истечение оффера не создаёт ложную просрочку. |
| `cabinet_pipeline_metrics_snapshot_age_seconds` | Возраст последнего успешного снимка БД. При ошибке сохраняется старый снимок, возраст растёт. До первого снимка — NaN. |
| `cabinet_pipeline_metrics_snapshot_errors_total` | Неуспешные обновления снимка; запросы мониторинга имеют отдельный query timeout 3 с. |

Снимки обновляются раз в 15 с, scrape — раз в 15 с. Между запросами снимка возможен
новый commit, поэтому это операционная сводка, а не транзакционный бухгалтерский отчёт.
SQL читает агрегаты; при больших объёмах истории стоимость полного расчёта нужно измерить.
Существуют также HTTP latency/error histograms, JVM и пул соединений Actuator.
Custom labels ограничены enum/фиксированными списками; ИНН, UUID, пользователи, коды и
тексты ошибок в них не попадают. Источники вне фиксированного списка получают `other`.
Метрики HTTP не заменяют проверки прав доступа или журнал решений.

Проверки инструментирования: реальный PostgreSQL с изолированными временными таблицами
проверяет корзины попыток, первое итоговое решение и отсутствие подмены пустой истории нулём;
тест источника проверяет timeout → OPEN → восстановление и 404; тест worker проверяет,
что метрика исключения сохраняет прежний retry. Недоступная БД метрик не ломает worker.

## ID запроса и логи

Сохраните ответный `X-Request-Id` и время из браузера/ошибки API, затем найдите ID:

```bash
docker compose logs --since 15m --no-color identity credit engagement external-sim > cabinet.log
rg 'ПОЛУЧЕННЫЙ_ID' cabinet.log
```

`X-Request-Id` сервиса — trace ID Micrometer в MDC. Для отказа gateway по лимиту это
собственный ID nginx; такой запрос до сервиса не доходит. Входной произвольный заголовок
не является доказательством серверного ID. Не публикуйте логи с документами/персональными
данными/секретами. Не каждая успешная HTTP-операция пишет строку лога: отсутствие совпадения
само по себе не доказывает отсутствие запроса. Экспорт distributed traces пока не настроен.

Фоновая задача outbox не продолжает исходный HTTP-span автоматически. Для неё нужны
UUID заявки/задачи, журнал переходов и `last_error`. Успешный HTTP submit означает постановку
работы, а не выполнение всего конвейера. Уведомление тоже не является доказательством выдачи:
проверяйте статус, договор и график через API.

## Источник недоступен

1. Посмотрите `cabinet_source_call_seconds_count` по source/result и one-hot breaker.
   `timeout` отличается от HTTP-ошибки и `circuit_open`. Проверьте доступность сети,
   конфигурацию URL/системного ключа, журнал `SOURCE_FAILED` заявки. Не выводите секреты.
2. На демо-стенде сравните `/sim/` с ожидаемым NORMAL/SLOW/DOWN. Вне демо пульт должен
   быть выключен. Режим сбоя возвращайте только после окончания контролируемого теста.
3. После восстановления breaker делает пробный вызов; до него OPEN не обязан исчезнуть
   мгновенно. Проверьте продвижение ожидающих заявок, а не только здоровье контейнера.
4. `SOURCE_TIMEOUT` ограничивает ожидание источника: заявка уходит в MANUAL_REVIEW с
   `SOURCE_TIMED_OUT`, а не получает кредитный отказ из-за сбоя. Очередь/длительность вызова
   могут задержать фактический переход; успешный ответ имеет приоритет при обработке.
   Измерения и воспроизводимый тест — [reliability.md](reliability.md).

## Задачи FAILED

```bash
docker compose exec -T postgres psql -U cabinet -d credit -c "select id, application_id, step, attempts, updated_at, last_error from pipeline_jobs where status='FAILED' order by updated_at limit 50"
```

Если логин БД изменён, используйте своё имя пользователя. `last_error` — диагностические
данные, не публичный API. Сопоставьте шаг с журналом заявки, доступностью источника и
ошибкой worker. FAILED появляется после исчерпания неожиданных ошибок; обычный сбой
источника обрабатывается ожиданием и не равен FAILED. Не сбрасывайте все статусы SQL:
внешняя выдача могла состояться до сбоя фиксации результата.

Публичного redrive API нет. Сначала воспроизведите и устраните причину в изолированном
стенде, подтвердите идемпотентность внешней операции и согласованность журнала. Оператор
принимает решение о восстановлении конкретной задачи после резервной копии и проверки
текущего состояния. Отозванные CANCELLED-задачи возобновлять нельзя.

## Очередь растёт

1. Разделите PENDING в будущем, просроченные PENDING, RUNNING с действующей арендой,
   RUNNING с истёкшей арендой и FAILED. `EXPIRE_OFFER` в будущем — нормальная работа.
2. Сравните возраст очереди, интенсивность/время шагов, HTTP p95, CPU/память, пул БД и
   ответы источников. Увеличение числа worker при недоступной БД/источнике может ухудшить ситуацию.
3. Если узкое место — worker и БД имеет запас, проверьте две реплики:
   `docker compose up -d --scale credit=2`. DNS discovery должен увидеть два target,
   а графики общей БД не должны удвоиться. Документы используют общий том; leases и
   SKIP LOCKED допускают повтор после падения, поэтому проверяйте отсутствие двойных
   итоговых событий/офферов. Методика — [load/README.md](../load/README.md).
4. Остановите наращивание нагрузки, если растут ошибки/очередь; сохраните фактические
   измерения и условия. Сравнение двух небольших когорт не является пределом мощности.

В [alerts.yml](../monitoring/alerts.yml) есть правила недоступности сервиса, FAILED,
просрочки очереди, устаревшего снимка и длительно открытого breaker. Они видны в Prometheus;
Alertmanager и доставка внешних уведомлений не настроены, поэтому письма/сообщения не обещаются.

## Очереди уведомлений и SMTP

В identity, credit и engagement очередь `delivery_outbox` имеет состояния PENDING,
RUNNING, DELIVERED и FAILED. Общие метрики: `cabinet_delivery_outbox_messages`
(channel/state), `cabinet_delivery_outbox_oldest_seconds`,
`cabinet_delivery_snapshot_age_seconds`, `cabinet_delivery_snapshot_errors_total`,
`cabinet_delivery_attempt_seconds_count` (channel/outcome). Нет user/application/event IDs
в метках. Снимок обновляется каждые 15 секунд, до первого успешного чтения значения NaN.
Для одной БД две реплики показывают одни и те же строки: используйте
`max by(application,channel,state)`, не сумму по экземплярам.

Если очередь растёт: проверить доступность получателя и identity, возраст самой старой
записи, `last_error_code`, аренды и повторы. `notification` направлен в engagement,
`email-notification` — в SMTP. Логи содержат id задания, канал, попытку и класс ошибки,
без payload и ссылок. Не очищать очередь и `notification_receipts`.

Если SMTP недоступен: уведомление в кабинете сохраняется; задания почты повторяются
с паузами до 256 секунд, максимум 12 попыток. Проверить DNS/порт/учётные данные/TLS
в закрытой конфигурации, не выводя пароль в логи. Mailpit — локальный перехватчик,
его SMTP не публикуется наружу. UI доступна только на loopback-порту 8025.
`MAIL_MODE=auto` обнаруживает mailpit в Docker-сети; отсутствие сервиса отключает
возможности UI. После успешного обнаружения временный отказ не отключает настройки.
Внешний SMTP использует `MAIL_MODE=on` и явную конфигурацию; `off` запрещает отправку.
При холодном старте без обнаруженного mailpit сервер честно показывает выключенный
канал; уже сохранённые почтовые задания остаются в БД и требуют последующего повтора.

FAILED не возвращается в очередь автоматически. После исправления причины оператор
может в транзакции вернуть конкретный проверенный UUID задания в PENDING, обнулить
attempts, назначить next_attempt_at=now() и снять claim_token/locked_until. Обязательные
условия UPDATE: id выбранного задания и state='FAILED'; действие и причина фиксируются
в эксплуатационном журнале. Не менять channel/event_key/payload и не удалять receipt.
Это сохраняет защиту от повторного эффекта в кабинете. Повтор письма после потерянного
SMTP ACK возможен даже при устойчивом Message-ID — exactly-once SMTP не обещается.

## Одноразовые ссылки и отзыв сессий

`email-security` — отдельный канал той же очереди identity: восстановление и приглашение.
Он не зависит от opt-in бизнес-писем. Задание хранит назначение и UUID; ссылка собирается
в момент отправки с отдельным `IDENTITY_LINK_KEY`, затем сверяется с сохранённым SHA-256.
Версия ключа — `IDENTITY_LINK_KEY_VERSION`. Истёкшее, использованное или отменённое задание
заканчивается без отправки; DELIVERED означает обработку задания, а не подтверждение прочтения
или безусловную отправку SMTP. Ошибочный ключ не должен порождать новое недействительное письмо:
задание повторяется и требует исправления конфигурации или новой ссылки.

Храните ключ ссылок отдельно от JWT, БД и симуляторов в закрытой конфигурации (Linux 0600).
`deploy/configure.py` создаёт его и HTTPS `PUBLIC_CABINET_URL`; ключ получает только identity.
Не перегенерируйте секреты при обновлении выпуска. Для доставки ожидающих писем после
восстановления БД нужен прежний ключ ссылок и его версия; в обычный архив БД секрет не входит.
JWT при восстановлении меняется отдельно. Если ключ ссылок потерян или скомпрометирован,
не пытайтесь восстановить токен из outbox или отключить проверку хэша.

Ротация ключа: остановить все identity, сохранить эксплуатационную запись с причиной,
отменить непринятые ссылки одной транзакцией через закрытое соединение оператора:

```sql
begin;
update password_reset_requests set revoked_at=now() where used_at is null and revoked_at is null;
update company_invitations set revoked_at=now() where used_at is null and revoked_at is null;
insert into identity_audit (id,action,occurred_at) values (gen_random_uuid(),'LINK_KEY_ROTATED',now());
commit;
```

Затем обновить только ключ и его версию в закрытом env, сохранить остальные секреты,
запустить identity. После этого пользователи запрашивают восстановление заново, а подписант
создаёт новые приглашения. Сохранённый хэш сам по себе позволяет проверить уже выданную ссылку
без старого ключа, поэтому при ротации именно отмена строк завершает действие прежних ссылок.
Не выводить токены, письма или env в эксплуатационный отчёт.

Без почты восстановление отвечает 503 с понятным сообщением; приглашение возвращает ссылку
только при первом создании/замене. Если ответ со ссылкой потерян, повторить ключ безопасно,
но ссылку он не покажет: нажать «Отправить повторно», чтобы отменить старую и получить новую.
Последнего активного подписанта нельзя отозвать; при отсутствии доступа к его учётке требуется
проверенное владельцем восстановление, а не прямое присоединение нового пользователя по ИНН.

Проверка `credentials_version` не использует положительный кэш. После успешного ответа
смены/восстановления/отзыва каждый новый защищённый запрос со старым JWT получает 401.
Уже выполняющийся запрос не отменяется задним числом. При недоступности identity — 503,
браузер сохраняет сессию. Проверить health и БД identity; не включать fail-open ради доступности.
Восстановление ограничено тремя запросами на нормализованный адрес и двадцатью на IP
за 15 минут; ключи в БД хэшированы, IP берётся из заголовка, который перезаписывает шлюз.
