# Выпуск Catalog R1

- `release.json` сохраняет прежний формат `revision` и `images`. Новый выпуск добавляет пару `images.catalog-grpc` и `catalog = {"jar_sha256": "...", "config_digest": "sha256:...", "dev_mode": "disabled|local|remote"}`. Образ публикуется всегда. `CABINET_CATALOG_DEV_MODE` передаётся защищённой release job, по умолчанию `disabled`. Старый manifest без обоих полей читается. Публикация связывает registry digest с OCI config digest образа, на котором проверены SHA-256 JAR и OCI revision. Направление Dev входит в хеш manifest, повтор одного выпуска использует те же байты.
- Точка входа Dev остаётся `stage <SHA>` и `deploy <SHA>`. `deploy/dev-release.py` под существующей блокировкой готовит стабильные пароли в `cabinet.env` с правами 0600 и отдельный CA с сертификатами Catalog и Credit в приватном каталоге состояния с правами 0700. Поля `CATALOG_DB_PASSWORD` и `CATALOG_MIGRATION_PASSWORD` генерируются на Dev. Kubernetes использует отдельные Secret refs. Закрытые ключи CA и owner-пароли остаются в операторском контуре.
- Compose подключает overlay для `local` и `remote`. Catalog слушает приватный gRPC 9094, Credit предъявляет сертификат с URI SAN `spiffe://creditcabinet/credit`. Серверный SAN соответствует DNS имени `catalog-grpc`. Каталог использует отдельную БД `catalog` из `template0` с ролями `catalog_owner`, `catalog_app`, `catalog_writer`. SQL V1, grants и ограждение Credit применяются один раз и проверяются перед переходом. Пакет SQL берётся из исходников выпуска.
- Кандидат останавливает публичный вход и старый Credit, затем доводит миграции Credit до конца. Проверка двух runtime-ролей, перенос и сверка истории и указателей выполняются штатным R1 `snapshot.py`. Для Dev PostgreSQL-клиент берётся из уже проверенного контейнера PostgreSQL. Переключение `remote` готовится при выключенной записи Catalog, может быть повторено после сбоя и завершает запуск Credit только после подтверждения единственного писателя и контрольных сумм. Промежуточные файлы хранятся приватно, постоянная квитанция содержит контрольные суммы, направление и состояние записи.
- Возврат с `remote` в `local` запускает обратный перенос до старта Credit: последние редакции и указатели из Catalog возвращаются в Credit, после сверки Catalog закрыт, Credit открыт. Повтор запуска использует подтверждённое состояние и квитанцию. `disabled` применяется к стендам до ввода Catalog; после ввода откат выбирает `local` с сохранением БД. Привязка к ранее проведённому переносу сохраняется между релизами. Дампы и штатное восстановление учитывают обе БД после ввода.
- Helm передаёт тот же pinned digest, включает выключенный по умолчанию Catalog независимо от режима Credit и настраивает ClusterIP, probes и NetworkPolicy. Миграции и перенос выполняются до включения `remote`. Выбор режима в values не открывает запись в БД. Перед возвратом с `remote` выполняется обратный перенос, затем меняются values.

## Операционный запуск

- Для Dev задайте `CABINET_CATALOG_DEV_MODE=local` при публикации первого включённого выпуска, затем `remote` для следующей ревизии с проверенным runtime. Переход и возврат выполняет штатный `dev-deploy`, используя исходник и digest из выбранного release. Для возврата подготовьте новую ревизию с `local`, сохраните прежние настройки Analytics и примените её через тот же защищённый вход. Релиз на уже опубликованной ревизии использует неизменный manifest. Если передача прервана при двух закрытых писателях, повторяется её исходный manifest. Если передача в Catalog завершилась, а health-проверка remote сорвалась, допустим новый защищённый релиз `local`; он переносит историю обратно перед запуском.
- Проверка Dev перед открытием HTTPS подтверждает режим запущенного Credit, флаги обеих БД и unary gRPC с сертификатом Credit. `verify-release.py` сверяет digest и OCI-метки образа Catalog и включает последнюю квитанцию в отчёт. Квитанция каждой передачи сохраняется в приватном `catalog/receipts` по идентификатору попытки. В ней указаны направление, ревизия, хеш manifest и хеши истории. Повторный выпуск после возврата создаёт новую квитанцию. При сбое после открытия записи используется идентификатор из журнала и сверяется история обеих БД. Частичный снимок хранится до завершения или повтора перехода.
- В Helm для включения нужны `catalog.enabled=true`, `catalog.databaseSecret` с двумя разными 64-символьными hex-паролями, `catalog.serverTLSSecret` и `catalog.creditTLSSecret` с `ca.crt`, `tls.crt`, `tls.key`. Release values предоставляют digest. При первом включении `catalog.creditMode=local`, pre-upgrade job подготавливает схему и проверяет флаги. Переключение владельца проходит по процедуре ниже.
- Резерв Dev после включения Catalog помечается форматом 3, содержит оба дампа, снимки таблиц, флаги записи и хеш релиза. `restore.py` принимает этот формат в новом изолированном проекте и восстанавливает ограничения и гранты до первого запуска. Форматы 1 и 2 используются для прежних выпусков. Helm PostgreSQL backup включает Catalog с момента создания БД; согласованный резерв для передачи снимается под остановленными писателями.

## Смена владельца в Helm

1. Примените защищённым `deploy-prod.sh` values с текущим `catalog.creditMode` и `catalog.maintenance=true`. Chart устанавливает ноль реплик gateway. Скрипт дожидается удаления его Pod. HTTPS и ролевая приёмка выполняются после открытия. Наличие gateway проверьте до начала любых действий по переносу.
2. Остановите текущие экземпляры Credit и Catalog через scale до нуля и дождитесь удаления Pod. Согласованный backup Credit и Catalog снимите под остановленными писателями. Используйте штатный R1 `snapshot.py switch` из [инструкции R1](alpha-catalog-r1.md). Сохраните квитанцию истории, проверьте два флага записи и отклонение старого runtime writer.
3. Оставьте `catalog.maintenance=true` и задайте целевой `catalog.creditMode`. Скрипт сверяет флаги в PostgreSQL, проверяет ноль реплик gateway и обоих писателей и сверяет хеши истории и указателей из двух БД перед выкладкой. Helm запускает целевые рантаймы с `--wait`, gateway остаётся закрыт. Внутренняя приёмка проверяет workload, OCI imageID и gRPC по mTLS из каждого активного Credit Pod. Проверка TCP в chart отражает доступность транспорта. Для отрицательной проверки требуется явный TLS alert о клиентском сертификате или статус gRPC об отказе в доступе. Таймаут или сбой exec прерывает приёмку.
4. Для открытия подайте ту же успешно выложенную ревизию и тот же режим с `catalog.maintenance=false`. В роли выкладки должны быть права на `deployments/scale` только для gateway. Перед открытием скрипт повторяет внутреннюю приёмку и сохраняет маркер открытия в ConfigMap. По сохранённому маркеру повтор закрывает gateway сразу после сверки UID namespace, до обращения к Helm. При `pending-upgrade` gateway остаётся закрытым на время разрешения незавершённой операции Helm. Маркер удаляется после успешной HTTPS и ролевой приёмки или повторного успешного ввода maintenance.
   Для обслуживания Catalog Helm 4 применяет client-side merge. После внешнего `scale` он восстанавливает число реплик из chart без разрешения на принудительный перехват полей SSA. Обычная выкладка по-прежнему выбирает метод Helm по истории релиза.
5. При неудачной смене режима оставьте gateway закрытым. Если фактическое состояние БД уже расходится с Helm, закройте gateway через scale до нуля из операторского контура перед восстановлением. Можно повторить выкладку, пока подтверждён целевой писатель. Для возврата остановите оба рантайма и выполните перенос в прежнюю БД по R1 с проверкой всех новых редакций и указателей. Затем примените прежний режим в maintenance через защищённый скрипт и выполните внутреннюю приёмку до открытия. Прямой `helm rollback` не переносит данные. `--atomic` / `--rollback-on-failure` применяются только к обычной выкладке с тем же проверенным владельцем и совместимым предыдущим Helm-релизом.
