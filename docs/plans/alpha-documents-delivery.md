# Documents в Dev

`images.documents` задаёт OCI digest `<registry>/<project>/documents@sha256:<64 hex>` из проекта Credit. Запись `documents` содержит `jar_sha256` и `dev_mode`. Сначала выпускают `dev_mode=local`: Credit остаётся единственным владельцем, а Documents поднимается с `FROZEN` на отдельной БД и хранилище. Первый выпуск с `remote` и старый manifest без записи после подключения отвергаются. Docker проверяет RepoDigest и OCI-метки `org.opencontainers.image.revision` и `org.opencontainers.image.jar.sha256`. Readiness проверяет OCI ID контейнеров, DB grants, mTLS с DNS SAN `documents` и URI SAN `spiffe://credit-cabinet/credit`, gRPC ListDocuments и фактические режим и epoch контейнера Credit.

Compose подключает `deploy/compose.documents.yaml` только для Dev-кандидата. Роли Documents `postgres`, `documents_owner` и `documents_app` используют отдельные автоматически созданные секреты. Креденшелы и записи журнала хранятся с правами 0600, корень состояния рядом с защищённым Dev ENV имеет права 0700. Первое подключение закрепляет поколение, CA и режим хранения. Встроенные S3 Credit и Documents размещаются в разных volumes и бакетах, с отдельными runtime и operator credentials; LOCAL также использует разные именованные volumes. Только off-line задача Documents получает учётные данные и volumes обеих сторон. RPC, БД, анти­вирус и миграционный доступ используют приватные сети, без опубликованных портов.

`documents_app` запускается с отключённым Flyway. Bootstrap применяет имеющийся Documents V1, фиксирует SHA-256 SQL и накладывает стандартные и специализированные grants. PostgreSQL требует UPDATE хотя бы одного столбца для `SELECT … FOR SHARE`. Роль Documents получает UPDATE только для `singleton`, который ограничен `NOT NULL`, `PRIMARY KEY` и `CHECK(singleton)`. Поля owner и epoch доступны ей только для чтения. Триггер Credit берёт блокировку от имени владельца с фиксированным `search_path`, прямой EXECUTE у runtime отозван.

## Активация

1. Выложить manifest `local` в `cabinet-dev`. Проверить readiness и сделать согласованную копию, в которой есть `documents_runtime`. Снять копию после остановки HTTP/HTTPS и writers. Оставить Credit SeaweedFS доступным до проверки SHA в Documents hook.
2. Выбрать проверенный manifest с `dev_mode=remote`. На Dev-хосте зафиксировать разрешение оператором в том же защищённом каталоге, который использует Dev rollout.

   ```sh
   python3 deploy/documents_dev.py authorize \
     --env-file "$DEV_ENV" --release-manifest "$TARGET_RELEASE" --backup "$QUIESCED_BACKUP"
   ```

3. Запустить штатный Dev rollout с выбранным manifest. Hook сверяет OCI provenance до запуска, останавливает доступ до переключения, проверяет успешное завершение Credit Flyway и применяет grants. При переносе Credit и Documents переходят в `FROZEN` с новым epoch. Старые lease сбрасываются под fence. Штатный JAR с `DOCUMENTS_MIGRATION_DIRECTION=forward` копирует записи и байты. Независимая сверка сравнивает полный набор восстановленных метаданных, включая удалённые строки, immutable input и статусы подготовленных артефактов. Для каждой доступной записи LOCAL сравниваются размер и SHA-256, для S3 выполняются HEAD и GET с вычислением SHA-256. Список метаданных за пределы защищённого состояния не выводится.
4. Запись `verified.json` создаётся атомарно до первого изменения владельца. После проверки Credit переходит в `REMOTE`, Documents в `DOCUMENTS`, с тем же epoch. Квитанция содержит идентификатор попытки, SHA manifest и backup, OCI digest, SHA JAR, поколение и агрегированные SHA сверки. После mTLS-проверки выставляются Credit mode/epoch. HTTPS открывается после проверки запущенного Credit. Если процесс прервался, повторить тот же manifest: существующая попытка сверяет обе БД и продолжает с последнего допустимого состояния. Попытка с несовпадающим manifest или необъяснимой парой owner/epoch остаётся заблокированной.
5. Для обратного перехода сделать новую согласованную копию, авторизовать manifest с `dev_mode=local` и снова запустить rollout. Целевой владелец Credit становится `LOCAL` только после reverse import при двух `FROZEN`. Documents сохраняет свои DB, LOCAL, S3 и TLS. Повторный forward после reverse возможен, если сохранённые строки всё ещё совпадают с источником. При изменении локальных метаданных штатный forward отвергает конфликт с оставшейся копией. Допустимое вмешательство требует отдельной миграции и проверки, поэтому rollout оставляет оба writer под fence.

## Интерфейс инструментов

- `DocumentsDev.open(deployment)` выбирает Dev overlay. `compose_environment()` даёт безопасные начальные значения `local/1`, пути и реквизиты.
- `preflight(deployment)` вызывается до переключения. `prepare(deployment, arguments)` вызывается после остановки Caddy, Credit, Documents и после основных Credit bootstrap/Flyway. Он поднимает изолированные компоненты, проверяет готовность и выставляет подтверждённую конфигурацию. `verify_credit(deployment)` вызывается после старта Credit и перед открытием Caddy.
- `backup(deployment, directory)` вызывается после остановки HTTP и обоих runtime, пока PostgreSQL и исходный SeaweedFS доступны. Она возвращает метаданные `documents_runtime`. Копия содержит БД Documents, LOCAL, при включённом S3 отдельный volume, границы эпохи, защищённое состояние с CA и отпечатки полных наборов объектов по обеим сторонам.
- `verify_backup(directory, metadata)`, `stage_restore(state, directory, metadata)` и `restore(deployment, directory, metadata, arguments)` используются в отдельном пустом `cabinet-dev-restore-*`. Сначала проверить общую копию и перенести защищённое состояние до открытия Deployment. Затем восстановить Credit и его хранилища, держать HTTPS и writers остановленными и вызвать Documents restore. Сравнение таблиц и SHA всех LOCAL/S3 объектов выполняется до старта. Production restore использует прежний интерфейс.

Helm-кандидат `values.documents.yaml` предназначен для namespace `cabinet-dev` в режиме `local`. Отдельные Kubernetes Secrets предоставляют DB, mTLS и S3 credentials. Для TLS нужны `ca.crt`, `tls.crt`, `tls.key` с указанными SAN; для DB нужны `POSTGRES_PASSWORD`, `OWNER_PASSWORD`, `APP_PASSWORD`; для каждой S3-роли нужны `S3_ACCESS_KEY` и `S3_SECRET_KEY`. Тест Helm выполняет аутентифицированный gRPC probe в состоянии `FROZEN`. Kubernetes cutover и согласованный Helm backup/restore находятся вне этой схемы. Helm запрещает `remote`.

Локальная проверка этого изменения охватывает Python, shell и рендер Helm. Доказательство выполнения JAR/mTLS/DB/LOCAL/S3 на Dev требует отдельного ограниченного запуска из опубликованного неизменяемого выпуска.
