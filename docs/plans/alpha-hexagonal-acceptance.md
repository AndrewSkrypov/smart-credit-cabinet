### Наборы для A03

**Исторический пилот.** На `7476cb814ee12667c3b5ad674ad4fdcfa75521ec` сверены восемь строк по статусному правилу v1. В набор входили два `WITHDRAWN` без факта подачи. Этот набор фиксируют пилотные фикстуры и команды сравнения. Квитанция `/var/tmp/alpha-pilot-verify.uQCHokYt/merge-readiness-7476cb8.md` относится к той выборке. [Реестр пилота](alpha-hexagonal-execution.md) · [Историческая фикстура](../../e2e/alpha/seed-credit.sql) · [Статусный экспорт](../../e2e/alpha/export-credit.sql) · [Историческая сверка](../../e2e/alpha/funnel.py)

**Текущая банковская выборка.** Карточка, очередь и чат банка используют факт подачи `submitted_at`. `currentStatuses` считает все поданные заявки, включая `WITHDRAWN` после подачи и заявки за пределами периода. Период ограничивает исторические показатели воронки. Для старой агентской заявки V21 восстанавливает первую передачу по `REQUEST_CLIENT_CONFIRMATION`, а при отсутствии события использует `submitted_at` у поданной заявки или `status_changed_at` у `PENDING_CLIENT_CONFIRMATION`. Эти признаки определяют доступ своего клиента. [SQL воронки](../../services/credit/src/main/kotlin/ru/creditcabinet/analytics/infrastructure/JdbcAnalyticsQueries.kt) · [Миграция V21](../../services/credit/src/main/resources/db/migration/V21__financing_scenarios.sql)

**Выбор источника.** Контракт v1 передаёт статус. Для каждой записи Credit сопоставляет членство по `submitted_at` со статусным правилом проекции до и после HTTP-чтения. При отсутствии незавершённых событий outbox расхождение хотя бы одной записи, например `WITHDRAWN` до подачи, переводит чтение на SQL с причиной `submission_visibility`. При совпадении наборов и готовом поколении доступно чтение из проекции. Отдельно сверяются её счётчики с SQL. [Выбор источника в Credit](../../services/credit/src/main/kotlin/ru/creditcabinet/analytics/infrastructure/HttpCurrentStatusesProjection.kt)

**Локальное подтверждение.** На `830448d6712a32d50bbabff2333f94fda15bea92` прошли все пять тестов `BankSubmissionVisibilityIntegrationTest`. При смешанном наборе PostgreSQL вернул счётчики с учётом только поданных заявок, HTTP-вызов отсутствовал и записалась причина `submission_visibility`. При совпадении наборов Credit прочитал готовый ответ локального HTTP-имитатора Analytics, получил те же счётчики и записал `projection/ready`. Это проверка PostgreSQL и выбора источника в Credit. Живой Kafka/Analytics входит в приёмку Dev. ## Условия завершения

Теневой этап закрывается после A01–A08, A10–A13 на кандидате в доступной изолированной среде. A09 и целевые доказательства A11 закрывают допуск к переключению на dev. Для проверки текущего API при выключенном флаге используется часть A09. Точное значение допустимого отставания согласуется по измерению теневого прогона и фиксируется до переключения.

По каждому ID реестр хранит `ожидает`, `в работе`, `пройдено`, `не пройдено` или `заблокировано`. Проверка инфраструктуры и успешная компиляция подтверждают только свои строки. При частичной готовности указываются открытые критерии и условия продолжения.
