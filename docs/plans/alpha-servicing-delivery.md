# Поставка Servicing на Dev

В обычном режиме Credit владеет финансовыми таблицами и работает с
`SERVICING_MODE=local`. Защищённый manifest с `servicing.dev_mode=local`
добавляет приватный кандидат Servicing с заблокированным писателем.
`servicing.dev_mode=remote` разрешает перенос после проверок. Режим
`disabled` и исторический manifest без descriptor допустимы до
регистрации приватного состояния Servicing. Возврат зарегистрированного
стенда выполняется manifest с `dev_mode=local`.

## Образы и приватные ресурсы

Общий manifest содержит `images.servicing` с digest, `revision` с полной
Git-ревизией и объект `servicing` с `jar_sha256` и `dev_mode`.
Общий release job берёт SHA-256 из артефакта проверенной сборки Servicing
и прикрепляет к образу OCI-метки `org.opencontainers.image.revision` и
`org.opencontainers.image.jar.sha256`. Hook сравнивает обе метки, полный
repo digest и OCI ID контейнера.

Compose запускает отдельный PostgreSQL. `servicing_owner` выполняет
`MIGRATION_ONLY=true` из того же образа. Runtime подключается как
`servicing_app` с выключенным Flyway. Для доступа к БД используется SCRAM,
роль приложения не владеет схемой и не может менять `servicing_writer_fence`.
БД и приложение имеют лимит 384 MiB каждое. Owner-процесс миграции
выполняется отдельно с лимитом 384 MiB. При запуске compose-процесс
проверяет HTTP health Servicing на 8095 из контейнера. gRPC 9095, БД
5432 и HTTP health остаются внутри Compose. Отдельные внутренние сети
соединяют Servicing с Credit для gRPC, с PostgreSQL, с Identity для
проверки отзыва сессии и с аутентифицированным Valkey. Только Credit
получает клиентский сертификат. SAN сервера содержит DNS `servicing`,
SAN клиента содержит URI `spiffe://creditcabinet/credit`. Корневой ключ
CA доступен только оператору. В контейнеры монтируются раздельные
каталоги удостоверений только для чтения.

В каталоге `servicing/` рядом с защищённым `cabinet.env` сохраняются
приватный `servicing.env` 0600, CA, сертификаты, идентичность PostgreSQL,
поколение и квитанции. Повтор читает существующие значения. PostgreSQL
использует том `<compose-project>-servicing-<generation>`, проверенный
по имени, принадлежности проекту и PG system identifier. Потеря тома,
сертификата или настроек зарегистрированного поколения останавливает
запуск. Каталог состояния имеет права 0700. Финансовые снимки попытки
имеют права 0600.

## Общий порядок Compose

1. Вызвать `ServicingDev.open(deployment)`. Для включённого descriptor
   добавить `deploy/compose.servicing.yaml` и применить
   `compose_environment()`, где Credit изначально локальный. Подготовить
   образы из manifest и выполнить `prepare(deployment, up)` под
   блокировкой Dev rollout. Hook сверяет OCI provenance и поднимает
   отдельный PostgreSQL, сохраняя идентичность. Текущий Credit продолжает
   работу до общей остановки.
2. Закрыть вход через Caddy и штатно остановить Credit вместе с pipeline
   и delivery worker. Остановка Credit требует `stop -t 150` и
   `SERVER_SHUTDOWN=graceful`. Перед переносом не должно оставаться
   `RUNNING` для `DISBURSEMENT` или неподтверждённых строк
   `servicing_open_outbox`. Мигрировать Credit владельцем до наличия
   `V25__servicing_boundary.sql` и согласовать общие grants.
3. Вызвать `switch(deployment)` с закрытым входом. Hook проверяет
   PostgreSQL и Valkey, останавливает Servicing, выполняет отдельную
   миграцию, поднимает и проверяет кандидат с сети Credit. Затем
   останавливает Servicing перед переносом. Если режим меняется, под
   advisory lock из `services/servicing/cutover/transfer.py` сохраняет
   начальный снимок цели, блокирует исходного писателя и цель, снимает
   актуальное финансовое состояние источника, переносит и сверяет его
   SHA-256. Активация следует за сверкой, затем согласуются отметка
   Credit и grants обеих БД. Hook поднимает и проверяет Servicing,
   возвращая окружение Credit из `credit_environment()`. Его следует
   применить только после успешного `switch`.
4. Запустить Credit с подтверждённым режимом при закрытом входе.
   Вызвать `verify_credit(deployment)` до запуска Caddy. Hook проверяет
   фактический режим Credit, принадлежность OCI ID, владельца и
   ограничения роли, HTTP health и mTLS из работающего Credit. Запрос
   gRPC без клиентского сертификата отвергается. Тот же `ByApplication`
   с корректной mTLS identity без JWT получает `UNAUTHENTICATED`. Этот
   запрос проверяет путь и границы аутентификации без операции с
   балансом. Квитанция готовности связывает manifest с конкретной
   принятой попыткой или начальным локальным режимом.

## Восстановление попытки и штатный возврат

Идентификатор попытки создаётся один раз перед изменением fence.
Неизменяемый `attempt.json` фиксирует выпуск, поколение и исходные
эпохи. `target-before.json` сохраняется до блокировки, `source-fenced.json`
после неё. `verified.json` подтверждает импорт, а `completed.json`
фиксирует итоговые fence, SHA-256 и количества строк по таблицам.
После сбоя повторить тот же защищённый manifest при закрытом входе и
с сохранённым каталогом попытки. При сбое до записи исходного снимка
hook продолжает блокировку только для ожидаемых эпох. При повторе
после активации он сверяет квитанцию и grants, сохраняя новые операции
принятого писателя. Расхождение эпох, SHA-256 или grants останавливает
процедуру для разбирательства. Незавершённые выдачи требуют сверки с
АБС и outbox до переноса.

Для штатного возврата использовать защищённый manifest с
`dev_mode=local`. Источник новой попытки — действующая БД Servicing.
Снимок после блокировки включает счета и остатки, транши, платёжные
графики и фактические платежи, резервы и журнал их событий, а также
идемпотентные команды открытия. Credit запускается локально после
импорта и сверки; Servicing остаётся FENCED. Следующий перенос в уже
использованный remote manifest получает новую попытку и новый снимок.
Резервная копия выпуска предназначена для аварийного восстановления.

## Согласованная копия и изолированное восстановление

Общий backup закрывает вход и останавливает Credit и Servicing штатно,
оставляя обе БД доступными. `backup(deployment, directory)` под общей
блокировкой проверяет владельца и создаёт `servicing.dump` с правами
0600. В общий manifest добавляются размер и SHA-256 файла, режим,
fence и идентификатор принятой попытки, отпечатки сертификатов,
поколение и PG system identifier, SHA-256 и количества по таблицам
обоих финансовых агрегатов. Общий backup также сохраняет Credit.
Операторский защищённый архив состояния хранит `servicing.env`,
`tls/`, `authority.json` и каталог принятой попытки, если она была.
Обычный dump и квитанции сохраняют контрольные данные без приватных
ключей и паролей.

Для восстановления общий restore проверяет файлы по backup manifest и
выбирает новый `cabinet-dev-restore-<id>` с закрытым входом. Оператор
переносит защищённое состояние с исходными правами, сохраняя указанные
файлы и каталог принятой попытки. `database.json`, `pending.json` и
`ready/` исходного проекта не переносятся. После восстановления Credit
и согласования его ролей вызвать
`restore(deployment, directory, metadata, up)` до запуска приложений.
Hook создаёт новый том и PostgreSQL, загружает dump под
`servicing_owner`, согласует права приложения через миграцию и
сравнивает оба финансовых агрегата и владельца. Новая привязка
сохраняет исходный PG system identifier для проверки происхождения.
После ошибки восстановления следует выбрать новый пустой проект.

## Helm и пределы проверок

`helm/cabinet/values.servicing.yaml` описывает выключенного по умолчанию
кандидата. После явного включения в namespace `cabinet-dev` chart
использует внешние Secrets, private ClusterIP и ingress NetworkPolicy,
отдельный PostgreSQL с PVC и owner init container. Второй init
container проверяет FENCED под ролью приложения. Credit в Helm продолжает
локальную работу. Смена владельца описана для защищённой поставки Compose.

Локальные проверки покрывают повторы после фиксации fence, импорта и
активации, возврат с последними данными, повторный remote manifest,
привязку изолированной копии, режимы файлов и TLS SAN. Перед
эксплуатацией на Dev остаются живые проверки PostgreSQL, OCI и gRPC,
согласованный backup/restore и финансовый сценарий с реальным
штатным возвратом.
