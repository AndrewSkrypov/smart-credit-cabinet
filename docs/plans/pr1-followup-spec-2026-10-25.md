# ТЗ на доработку интерфейса и больших списков в открытом PR

Версия 1.0, 25 октября 2026, МСК. Проект Smart Credit Cabinet.

Цель: довести представление версий, документов, заявок и ролей до согласованного интерфейса, ограничить рост основных списков и устранить дефекты общих оболочек. Результат реализации после проверки качества добавляется новым коммитом в существующий PR. Этот документ является заданием; реализация и приёмка перечисленных изменений пока не выполнены.

## 3. Общие ограничения

- Сохранить брендинг «А», тему и текущую структуру продукта. Использовать существующие токены/компоненты и зависимости; новый дизайн-фреймворк не нужен.
- Не менять скоринг, ставки, правила кредитного решения, финансовые формулы, полномочия и статусы процесса ради UI. Не добавлять EFRSB, новую финансовую модель, стоимость задачи/собственные средства/резерв или календарные даты расчётного графика.
- Сохранить immutable условия заявок/предложений/договоров, expectedVersion/409, подтверждения, dirty guard, профиль, self-revoke и защиту последнего подписанта.
- Сохранить PDF/XLSX, авторизованную загрузку, ошибки/повторы генерации, подпись/выдачу и границы PCI из первого PR. Не заявлять соответствие PCI DSS.
- Пользовательский preview не seed/reset. Массовые данные, клики сохранения политики и негативные проверки — только на изолированных fixtures. Не выполнять изменяющие E2E параллельно на одной БД.
- Один владелец у каждого общего файла в каждый момент. Чужие незакоммиченные изменения не удалять, не stash/reset/clean без согласованной координации. Не использовать force-push и не переписывать историю открытого PR.

## 4. Версии и редакторы

### U00 История версий

**Исходное поведение:** общий `VersionHistory.tsx` отрисовывает весь массив. Уже 11 версий правил значительно удлиняют правую колонку.

**Требования:**

1. Desktop при двухколоночной раскладке: карточка истории с неподвижными заголовком, общим количеством и обозначением текущей версии. Скроллится только список. Высота списка адаптивная, ориентир 480–560 px на обычном экране; на невысоком окне уменьшается. При 0/1 записи пустую фиксированную высоту не резервировать.
2. В desktop-списке максимум 20 записей на страницу; при большем количестве доступны страницы и диапазон записей. До 20 записей навигация скрыта. На одноколоночной раскладке — по 5 записей, обычная прокрутка страницы без вложенного вертикального скролла истории.
3. Компактная строка: номер, «Действует» только у текущей, дата/время МСК, автор, причина до двух строк и действие «Посмотреть». Длинная причина целиком доступна в просмотре. Роль и полный UUID — в подробностях. Если имени нет, показать корректный ID/fallback; автора не выдумывать.
4. Порядок: текущая версия первой, остальные по убыванию номера. Все версии остаются достижимыми. Пагинация первого пакета может быть клиентской поверх существующего ответа; это ограничивает DOM, но не объявляется серверным масштабированием.
5. Закрытие просмотра и фоновое обновление не сбрасывают страницу/позицию списка. При добавлении версии сохранять контекст через видимую запись/ID, а не молча переносить пользователя. Если размер страницы меняется при resize, сохранить выбранную/первую видимую версию на допустимой странице.
6. Скроллируемая область имеет доступное имя и видимый фокус. Возврат фокуса после Dialog — к вызвавшей кнопке; если строка исчезла, к заголовку истории. Клавиатура достигает последней записи, колесо вне истории прокручивает страницу.

**Приёмка:** 0/1/11/20/21/100 версий; 1440×900, 1280×720, 1024, 900, 390 и 320 px; длинные причина/автор, отсутствие имени; переход на последнюю страницу; открытие/закрытие; resize; обновление истории. Высота основной страницы не растёт пропорционально полной истории.

### U01 Вторичные действия

- «Открыть» заменить на текстовое «Посмотреть» с небольшой иконкой и доступным именем «Посмотреть версию N». Не создавать одновременно кликабельную строку и отдельную дублирующую кнопку.
- У скачивания оставить понятное «Скачать PDF» / «Скачать XLSX», добавить иконку; использовать спокойное текстовое/лёгкое нейтральное оформление без тяжёлой контрастной рамки. Справа единое выравнивание; слева название документа, формат и размер. В узкой раскладке действие переносится под описание.
- Сохранить состояния загрузки, disabled, ошибки, retry и защиту повторного клика. ARIA-имя содержит название документа и формат. Иконки декоративны, текст обязателен.
- Основные «Сохранить новую версию», «Принять», «Подписать» сохраняют визуальный приоритет. На touch зона нажатия минимум 44×44 px; для desktop допускается меньшая визуальная высота при достаточном доступном фокусе.
- Менять локальные варианты `VersionHistory` и `GeneratedFilesBlock`. Глобальный `MuiButton.outlined` не переписывать: от него зависят другие проверенные действия.

**Приёмка:** READY/PENDING/ERROR, ошибка загрузки, retry; длинное имя файла; клавиатура; mobile; основные CTA различимы. Скачивание выдаёт прежний авторизованный артефакт, а не вновь рассчитанные условия.

### U02 Просмотр версии

Общий `VersionPreviewDialog` сохраняется. Его содержимое привести к единой структуре:

1. Шапка: название объекта и номер; статус «Действует» / «Архивная». Для исторической версии — «Сейчас действует версия N» по полученным данным. При недоступности текущей версии статус не угадывать.
2. Реквизиты: дата/время с годом и МСК, автор и роль, причина изменения. Полный UUID — в раскрываемых технических сведениях, доступен выделением/копированием; не скрывать единственный идентификатор автора без замены.
3. Правила: «Нагрузка и выручка», таблица «Рейтинг / От баллов / Надбавка, п.п.», «Отраслевой риск». Пары подпись/значение с единицами; длинные ОКВЭД переносятся без горизонтального переполнения и сотен чипов.
4. Продукт: описание отдельно; ставка/сумма/срок/автолимит; тип лимита/доступность; цели. Равные min/max показывать одним значением: «12 месяцев». Формат ru-RU и единицы сохраняют числовой смысл.
5. Высота Dialog ограничена экраном, прокручивается тело; заголовок и закрытие доступны. На узком экране адаптивный Dialog без обрезания. Escape, кнопка закрытия и возвращение фокуса работают.

Просмотр не восстанавливает старую версию, не заменяет черновик и не даёт редактировать историю. Подтверждение сохранения и обработка 409 остаются прежними.

**Приёмка:** оба объекта, текущая/старая/начальная системная версия; loading/error/retry; длинные реквизиты; мобильная раскладка; неизменность dirty-формы после открытия/закрытия снимка. Проверить manager/underwriter read-only и risk-admin.

### U08 Чекбоксы продукта

Измерено на текущем PR: два последних флага сдвинуты на 11 CSS px вправо; вертикальный шаг около 62 px против 42 px в целях. У вложенных и прямых дочерних `FormControlLabel` разные margin из-за правил `Stack.spacing`.

- Разделить «Цели финансирования» и «Параметры продукта». Во втором блоке — возобновляемость и доступность каталога.
- В обеих группах одинаковые правила контейнера строк/контролов: квадраты стоят на одной вертикали, подписи — на другой. Явно нормализовать margin локально; не компенсировать два флага `translateX`.
- Одинаковый ритм внутри группы, увеличенный интервал только между группами. Многострочная подпись выравнивается предсказуемо относительно первой строки. Клик по подписи и touch-зона сохраняются.
- checked/disabled, значения продукта, dirty guard и сохранение не менять.

**Приёмка:** все девять чекбоксов, отмеченные/пустые/read-only, длинная подпись; desktop и 320/390 px; клавиатура. Изолированная проверка сохранения меняет только ожидаемые параметры.

## 5. Клиент и сотрудники банка

### U03 Экран выданного кредита

Для DISBURSED после общей шапки/этапов первым содержательным блоком показывать «Кредит выдан» с данными договора и графиком; непосредственно следом — файлы. Прошлое предложение перенести ниже в явно исторический блок «Согласованные условия»; допустимо сворачивание. Историческое одобрение не выглядит текущей задачей.

Для OFFER_ISSUED/SIGNING/DISBURSING сохранять правильное текущее предложение, действие подписи/ожидания и предварительные файлы. Не дублировать график и документы и не менять условия по текущему каталогу.

**Приёмка:** все четыре состояния; у DISBURSED договор/график/файлы видны до прошлого сравнения условий; у SIGNING доступно подписание уполномоченной ролью; прежние документы скачиваются с прежними значениями.

### U04 Тексты групп и аналитики

- Пустая ручная очередь: «Заявок на ручном рассмотрении сейчас нет»; отсутствие записей не доказывает автоматическое решение остальных.
- Диаграмма с завершёнными статусами: «Распределение заявок по статусам» вместо «Сейчас в работе».
- Клиентская группа: «Выданные и закрытые заявки» вместо неопределённого «Завершённые». Краткое название во вкладке допустимо при пояснении состава; не представлять это полноценным обслуживанием кредита.
- При серверных страницах отличать «Нет заявок вообще», «Нет по фильтру» и временную ошибку. Не вводить дублирующие заголовки при интеграции U09.

**Приёмка:** пустой список, пустой фильтр, выдача, отказ, отзыв и закрытие; счётчики и названия соответствуют одной выборке.

### U06 Полномочия и следующий шаг

- Для CLIENT рядом с ролью или в первом экране кабинета показать «С правом подписи» / «Без права подписи» из существующего canSign. Не делать вывод по названию пользователя.
- Сотрудник без подписи заранее понимает, что договор подписывает уполномоченный представитель. Запрет подписания и управления сотрудниками остаётся серверным.
- В MANUAL_REVIEW менеджеру показать доступное действие из assessment.actions и пояснить, что кредитное решение принимает андеррайтер. Не добавлять разрешения, отсутствующие у роли.
- В BankSummary конечные статусы имеют предметный итог: «Кредит выдан», «Отказано», «Заявка отозвана/закрыта» с доступной причиной. Общее «Для вашей роли действий…нет» не заменяет известный результат.
- Сохранить различимость ожидания клиента, автоматической обработки, отсутствия данных и stale-ответа; не выдавать неизвестное за нулевое/нормальное.

**Приёмка:** CLIENT с/без canSign, MANAGER, UNDERWRITER, RISK_ADMIN; ручное рассмотрение, ожидание клиента, stale, конечные статусы. UI не показывает недоступное действие как разрешённое; API-отказы на границах прав сохранены.

### U05 Понятность действий

| Элемент | Требуемое поведение |
| --- | --- |
| «Все продукты» | Якорь `#products` с видимым заголовком после прокрутки |

| Информационные плитки | Если клик не даёт отдельного результата, убрать интерактивность; продуктовые/целевые плитки сохраняют выбор и понятное действие |

- Для каждой кнопки подпись соответствует результату. Один главный сценарий оформления, вспомогательные якоря и вход различимы. Сохранение intent первого PR не откатывать.

- Кнопка «Наверх» появляется после ухода за первый экран; возвращает к началу без перекрытия шапкой, доступна с клавиатуры, учитывает reduced-motion. Развести с помощником и safe-area на mobile.
- Проверить контраст вспомогательного текста/фокуса в изменённых блоках на фактическом фоне. Не осветлять серый текст ради второстепенности. Существующая тема сохраняется.
- Измеренные сроки решения/подключения не установлены. Непроверенное «за минуты/за пару минут» заменить нейтральным «Автоматическая проверка небольших заявок» / «Подключите компанию онлайн» либо явно ограничить демонстрационным сценарием без обещания реального SLA. Предупреждение о прототипе/синтетике доступно, демонстрационные ставки не выглядят публичной офертой банка.

**Приёмка:** гость/клиент/банковская сессия; 320/390/900/1024/1440 px; оба якоря, оформление с intent, шаги, scroll-to-top, reduced-motion; нет горизонтального переполнения или перекрытия помощника.

### U11 Маркеры списков в AuthFrame и аналогичных блоках

На пользовательском скриншоте и в PR маркеры прижаты к верху строки. Измерено: dot 8 px, line-height 24 px, dotY=textY и computed margin-top=0, хотя в исходнике задан mt=7 px. `Stack.spacing` сбрасывает отступ дочернего маркера. Перенос заголовка на две строки сам по себе допустим; дефект — положение точек.

- Центр маркера выровнять по центру **первой строки** текста, а не по середине многострочного пункта. Для line-height 24 px и dot 8 px расчётный отступ равен 8 px; при изменении типографики выравнивание сохраняется.
- Использовать устойчивую локальную раскладку строки: CSS gap/grid или отдельную обёртку маркера, не конфликтующую с margin-правилами Stack. Цвет/размер точки и текст сохранить.
- Исправить общий AuthFrame, который используется входом, регистрацией, восстановлением, сменой пароля и приглашением. В лендинге проверить списки блока «Один процесс для клиента и банка»: там аналогичные маркеры с mt=9 px внутри Stack; при том же конфликте применить общий приём. Не менять глобальные правила всех Stack.
- Текст имеет минимум доступной ширины, переносится рядом с маркером; декоративная точка не дублирует озвучивание списка.

**Приёмка:** одно-/двух-/трёхстрочные пункты, увеличение текста/zoom 200%, desktop breakpoint и обе карточки аудитории лендинга. При mobile, где aside скрыт, не возникает пустых отступов. Проверять общий компонент, а не чинить каждую форму отдельно.

## 7. Большие списки

### Общий контракт страниц заявок

Для первого этапа использовать совместимый дополнительный read-endpoint, например `GET /api/v1/applications/page`. Старый массив `/applications` сохранить для текущих потребителей, оба основных UI перевести на страницу. Окончательное имя зафиксировать до разделения FE/BE; дальше не держать два расходящихся контракта.

Параметры: `page` с нуля, `size` (default 20, допустимые 1..100), `group` из фиксированного набора по роли, `q` (до 100 символов после trim), `sort` из allowlist. Банковские group: `review`, `client`, `system`, `done`; клиентские: `active`, `done`, `action` (существующие требующие клиентского действия статусы). `action` пересекается с `active`, их счётчики нельзя суммировать как непересекающиеся группы. Клиентский UI явно передаёт size=10. Некорректные отрицательные/слишком большие параметры, неизвестные группы и переполнение вычисления offset возвращают согласованный 400, а не неограниченную выдачу. Не подставлять имена полей/направления сортировки из запроса в SQL без allowlist. Поиск — № заявки, название компании и ИНН; клиенту достаточно № и продукта в своей компании. Точный набор согласовать в OpenAPI.

Ответ: `items`, `page`, `size`, `totalElements`, `totalPages`, `hasNext`, `countsByGroup`; для клиентского превью — `actionRequiredCount` и до пяти записей `actionRequiredPreview`. Нулевая выборка: totalPages=0, page=0, пустые items. countsByGroup отражает все доступные заявки соответствующей группы при текущем поиске, до разбиения на страницы. Превью требующих действия считается независимо от выбранной страницы; при активном поиске явно определить, применяется ли он к превью, и подписать результат. Рекомендуется самостоятельный глобальный блок «Нужно ваше действие» по своей компании.

Права компании/роли и исключение банковских DRAFT применяются в БД **до** поиска, count и limit. unreadChatCount вычислять для возвращаемых items/ограниченного превью, не для полного банка. Страница не должна сначала материализовать всю выборку в памяти и затем slice/subList. Существующие индексы проверить через план запроса; новые добавлять только при необходимости новой миграцией.

У каждой сортировки есть уникальный tie-breaker ID. Offset-страницы не дают snapshot-гарантии при конкурентном изменении записей; не заявлять обратного. В UI фоновый ответ не переставляет видимые строки под курсором: показать «Есть обновления» и применить их явно; собственное действие может обновить страницу с сохранением фильтра. При больших глубоких очередях отдельным этапом возможен cursor API.

Фильтр, поиск, sort, page и size хранятся в URL. Ввод поиска с debounce около 300 мс; смена фильтра/size сбрасывает page. Ответ предыдущего запроса игнорируется при смене фильтра. Ошибка фонового обновления сохраняет последний успешный список. Возврат из карточки восстанавливает выборку и позицию. При опустевшей последней странице перейти к последней допустимой с понятным состоянием, не показывать бесконечную ошибку/пустую страницу.

### U09-BANK Банковская очередь

Группы сохраняют существующие статусы:

| Группа | Статусы | Порядок по умолчанию |
| --- | --- | --- |
| Ждут решения | MANUAL_REVIEW | statusChangedAt ASC, id ASC |
| Ждут клиента | INFO_REQUESTED, OFFER_ISSUED, SIGNING | statusChangedAt ASC, id ASC |
| В обработке | SUBMITTED, ENRICHMENT, SCORING, DISBURSING | statusChangedAt ASC, id ASC |
| Выданные и закрытые | DISBURSED, REJECTED, WITHDRAWN, CLOSED | statusChangedAt DESC, id DESC |

По 20 строк default, выбор 20/50/100. Таблица и мобильные карточки используют одну выдачу. Общие счётчики вкладок получаются из API. Сохраняются SLA-подсветка и unreadChatCount. Вместо полного массива каждые 10 секунд обновлять только текущий ограниченный запрос/счётчики; не накапливать запросы при медленной сети, при скрытой вкладке приостанавливать polling. Более простой существующий интервал допустим при тех же границах выдачи и отсутствии overlap.

### U09-CLIENT Клиентские заявки

Группы «В работе» и «Выданные и закрытые заявки» по существующему FINISHED_STATUSES; по 10 карточек. Группы можно сделать вкладками, чтобы обе истории не удлиняли страницу одновременно. Сохраняются понятный подбор финансирования и состояния пустого кабинета.

«Нужно ваше действие»: максимум пять ссылок, общий счётчик, «Все N» переводит в соответствующий серверный фильтр. Использовать существующий смысл статусов DRAFT/INFO_REQUESTED/OFFER_ISSUED/SIGNING, а не произвольный новый workflow; доступность действия учитывает canSign. Точные общие количества нельзя вычислять по текущим 10 items.

В боковом блоке представителей показать максимум пять и ссылку «Все сотрудники» с общим числом. Это ограничение превью; сам ответ компании пока может содержать полный массив до U09-STAFF. Не называть такой превью серверной оптимизацией сотрудников.

### U09-NOTIFY Уведомления

Использовать готовый page/size API (серверный максимум 50). В popover по 10 уведомлений, неподвижные шапка и навигация «Более новые / Более ранние», диапазон и total. Новая порция заменяет старую. При отсутствии следующей страницы соответствующее действие недоступно; при <=10 навигация скрыта.

Просмотр порции ничего автоматически не отмечает прочитанным. Сохранить отдельные правила открытия конкретного уведомления и «Прочитать все», обработку ошибки и disabled на время запроса. Счётчик unread — общий, не число текущей страницы. При появлении новых уведомлений не перескакивать со старой порции без явного действия; не скрывать открывшуюся ошибку.

**Общая приёмка страниц:** 0/1/size/size+1/1000+ заявок на изолированной БД; одинаковые даты, поиск записи за первой страницей, неверные параметры, чужая компания/роль/DRAFT, стабильная сортировка на неизменяемом наборе, переход статуса и новая запись во время просмотра, пустая последняя страница, медленный/поздний/ошибочный ответ, Back из карточки, mobile. Проверить, что SQL и ответ ограничены страницей. Для уведомлений — 0/10/11/50+, навигация в обе стороны и неизменность read-state при простом просмотре.

### U09a Контекст помощника

Сейчас UI отправляет все messages; входной DTO принимает максимум 10 реплик, а модель использует MAX_HISTORY=4. При шести завершённых парах история содержит 12 реплик и следующий запрос превышает DTO. Это подтверждено исходниками; проверка нового поведения обязательна.

Отделить показанную переписку от отправляемого контекста. В текущем пакете отправлять последние четыре предыдущие валидные реплики, согласованные с серверным MAX_HISTORY, сохраняя порядок и текущий вопрос отдельным полем. Ошибочный незавершённый запрос не подставлять как выдуманный ответ; retry не дублирует текущий вопрос. Текст контекста ограничить действующим MAX_TEXT, не расширять серверный лимит ради UI. Текущую историю с экрана не удалять.

Сохранить привязку к applicationId, очистку при переходе в другую заявку, ticket-защиту поздних ответов, источники и режим ответа. **Приёмка:** минимум 12 последовательных вопросов через настоящий UI с контролируемым API; в каждом запросе допустимое окно, текущий вопрос один раз, на экране прежние сообщения. Ошибка/retry и смена заявки во время ответа. Подтверждение настоящего MODEL отдельно от мокового UI-теста; менять модель/AI-профиль для этого пакета не требуется.

## 8. U10 Фон документа и границы прокрутки

### 8.1 Найденные общие места

На исходном стенде html прозрачен, body светлый, а night/nightGlow находятся внутри React. Попытка колёсной прокрутки на верхней границе Edge не воспроизвела transient-белый участок; пользователь наблюдает его при выходе за верх/низ, включая двухцветные формы. Причину конкретного белого canvas нельзя считать окончательно установленной до повторения исходного жеста.

Проверены определения маршрутов и общих компонентов. Исправление должно покрыть семейства, а не набор исключений по URL:

| Оболочка | Маршруты/состояния | Требуемый фон за границей |
| --- | --- | --- |
| LandingPage | `/` | Продолжение тёмной области наверху и тёмного footer внизу, без светлого провала |
| AppShell | `/profile`, `/client`, `/client/new`, `/client/employees`, `/client/applications/:id`, `/bank`, `/bank/applications/:id`, `/bank/analytics`, `/bank/rules`, `/bank/products` | Сверху согласован с nightGlow; снизу со светлой поверхностью кабинета, без чужой полосы |
| AuthFrame | `/sign-in`, `/sign-up`, `/password-recovery`, `/reset-password`, `/accept-invitation` и их loading/error/invalid-token состояния | Desktop: продолжение тёмных 5/12 слева и светлых 7/12 справа; ниже md — светлый фон, поскольку aside скрыт |
| Системный экран | `/access-denied`, wildcard 404, RouteErrorBoundary | Явная светлая поверхность всей доступной высоты; не наследует тёмную подложку предыдущего маршрута |
| Bootstrap/переход | До React, загрузка шрифтов/кода, redirect RoleGuard, смена layout | Непрозрачный fallback, затем согласованный фон без transient-белой вспышки и без устаревшей темы |
| Вложенный скролл | Version Dialog, история, уведомления, сообщения, помощник | Достижение края внутреннего списка не ломает фон и блокировку модалки; обычная страница продолжает работать согласно текущему UX |

### 8.2 Реализация

1. Ввести одного владельца document/canvas background с явным вариантом layout. Допустим общий компонент/утилита уровня маршрутов/оболочек с GlobalStyles/CSS-переменными. Не разносить несогласованные document.body.style по страницам. При смене/ошибке/unmount применять актуальный fallback, исключить гонку cleanup старого layout с новым.
2. Согласовать html/body/root и внутреннюю подложку. Переиспользовать night, page, nightGlow и breakpoint/grid AuthFrame. Для двухцветной формы использовать соответствующую адаптивную подложку, например горизонтальный gradient по тем же долям. Одна чёрная заливка на все формы не принимается: она даст неправильную полосу справа и на mobile.
3. Для AppShell отдельно проверить верх и низ. Сохранить светлое содержимое и закругления, не менять глобально palette.background.default на тёмный. Высота коротких системных экранов/ошибок должна заполнять viewport, не оставляя открытый неуправляемый canvas.
4. Первым исправлять фон с сохранением штатного скролла. Если браузер продолжает показывать нежелательный bounce, адресный `overscroll-behavior-y: none` корневого scroller допустим после проверки влияния на pull-to-refresh и поддержки. `contain` само по себе не гарантирует удаления bounce. Решение и результат записать в приёмке.
5. Не применять глобальные preventDefault на wheel/touchmove, body overflow:hidden или новый внутренний scroller всего сайта. Не ломать sticky header, якоря, клавиатуру, browser Back, Dialog focus/scroll lock и доступность.
6. Если поле находится вне canvas документа и остаётся только в IAB после CSS-исправления, сохранить воспроизведение и отдельно обозначить ограничение WebView/хоста. Не считать CSS исправленным только потому, что обычный screenshot не поймал жест, и не останавливать остальные независимые работы из-за отсутствия устройства с этим жестом.

Техническая опора: [W3C о фоне canvas](https://www.w3.org/TR/css-backgrounds-3/#special-backgrounds), [MDN об overscroll-behavior](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overscroll-behavior). Поведение конкретного WebView проверяется отдельно.

### 8.3 Проверка без ручного обхода каждого экрана

- Один автоматический контроль соответствия всех объявленных маршрутов семействам layout: новый маршрут либо наследует policy оболочки, либо явно использует fallback. Не привязывать проверку к точной строке CSS.
- Для визуальной проверки выбрать представителей: `/`, клиентский и банковский список, `/sign-in`, длинная `/sign-up`, форма с invalid-token без настоящего токена, `/access-denied`, 404, искусственный ErrorBoundary на изолированной fixture. Дополнительно проверить короткое и длинное содержимое каждой оболочки.
- Матрица переходов: landing → auth → workspace → profile → sign-out → auth; workspace → forbidden/404 → landing; auth → auth. Проверить отсутствие наследования неправильного фона.
- Для каждого семейства — верх **и** низ, desktop и mobile, resize через md, zoom 200%, модалка открыта/закрыта. Для split-layout проверить обе стороны границы. По исходному жесту пользователя — IAB и Edge/Chrome, если устройство доступно.
- Если gesture-проверка недоступна, закрыть кодовую/автоматическую часть как verified в её объёме, а U10 целиком оставить partially_verified с воспроизводимыми данными о доступной среде. Это не останавливает остальные работы и подготовку коммита: к review допускается кандидат с подтверждённой общей политикой фона и явно открытой проверкой нативного жеста. Сообщать «белое поле полностью исправлено» до этой проверки нельзя. Приёмка устранения именно пользовательского эффекта остаётся отдельным открытым пунктом; недоступность одного устройства не повод бесконечно ждать или скрывать статус.

У сообщений уже есть before/after/limit и ограниченная высота; при тысячах вручную догруженных сообщений рассматривать окно отрисовки отдельно. Развёрнутый длинный график можно ограничить по высоте со sticky-заголовком; полный график и экспорт сохраняются.

До кода записать занятые зоны и согласовать JSON-контракт. Не требуется создавать новый goal. Можно использовать временные локальные коммиты исполнителей, но интегратор готовит один согласованный новый коммит для открытого PR без изменения уже опубликованной истории. Если организация команды требует нескольких reviewable-коммитов, решение фиксируется до push; цель пользователя — тот же PR, а не новый ответвлённый процесс.

Единица приёмки — общий кандидат с совместимыми FE/BE. Изменение shared-файла или базы повторно проверяет затронутые задачи, даже если их изолированная ветка ранее была зелёной. Не заносить тестовые PNG/PDF, логи с данными, секреты и локальные env в Git автоматически; включать только согласованные обезличенные материалы ревью.

## 11. Проверка качества

### 11.1 Проверка ТЗ перед передачей

Проверить покрытие всех U00–U11 и подпунктов U09, соответствие утверждённым границам первого PR, явные owners/зависимости/acceptance, разделение обязательного пакета и следующего этапа. Reported overscroll и статический риск помощника должны оставаться отличимы от воспроизведённых дефектов. Отменённое удаление фона изображения не является задачей.

### 11.2 Адресные проверки реализации

| Группа | Значимые проверки |
| --- | --- |
| Версии | Пагинация/позиция/фокус, old/current, 409/dirty/cancel, read-only, длинные метаданные |
| Кредит/файлы | Порядок DISBURSED, прежние immutable значения, предварительные/финальные файлы, download/retry/auth |
| Роли | Пять пользовательских вариантов, ранняя видимость canSign, серверные границы действий |
| Заявки API | БД ограничивает выдачу до материализации; поиск/фильтры/total/counts/права; граничные параметры; tied timestamps |
| Заявки UI | URL/Back, debounce/late response, обновления без перестановки под курсором, пустая последняя страница, mobile |
| Уведомления | Навигация старше десяти, total/unread, ошибки, отсутствие read-side-effect при листании |
| Помощник | 12+ вопросов, допустимый контекст, ошибка/retry, смена заявки/поздний ответ |
| Общие оболочки | Матрица маршрутов/переходов U10, жесты сверху/снизу, обе части AuthFrame, маркеры первой строки |

Раскладку подтверждать реальным браузером. Не писать хрупкие тесты на каждый CSS-отступ; проверять доступность, геометрию важных границ и поведение. Для крупных списков нужны DB-интеграционные проверки, UI-mock сам по себе не доказывает ограниченный SQL.

### 11.3 Общий кандидат

Проверенные scripts проекта: во frontend — `npm run lint`, `npm run test:coverage`, `npm run build`; backend — `./gradlew build --no-daemon` с окружением JDK 21/PostgreSQL/остальных зависимостей по README/CI; e2e — `npm run typecheck` и `npm test` на изолированном стенде с корректными переменными Playwright. На Windows использовать штатный gradlew.bat при соответствующем окружении. Не запускать эти команды поверх изменяющихся чужих сборочных результатов или общей fixture-БД.

Перед публикацией: адресные тесты, применимые общие FE/BE/E2E, визуальная матрица, `git diff --check`, обзор полного diff, совместимость API/OpenAPI/миграций и отсутствие незаявленных правок. После публикации — все применимые штатные CI jobs итогового SHA, без отключения security/storage/restore/contracts для получения зелёного результата. Новую CI-конфигурацию/таймауты не ослаблять ради прохождения.

Итоговые снимки: одинаковые данные до/после для истории 11 версий, архивного правила, продукта с чекбоксами, AuthFrame с многострочными пунктами, DISBURSED и файлов, очереди с несколькими страницами, старых уведомлений. Для U10 — кадры/короткая запись исходного жеста и сведения о браузере/устройстве; отсутствие дефекта на статичном кадре не является доказательством исправления.

### 11.4 Условия допуска нового коммита

- Все обязательные ID реализованы и имеют результаты адресных проверок на общем кандидате. Допустимое исключение — недоступная нативная gesture-проверка U10 по разделу 8.3: кодовая часть и переходы проверены, ограничение явно отражено в отчёте, пользовательский эффект остаётся partially_verified. Это разрешает публикацию проверенного коммита для review, но не заявление о полном устранении reported-эффекта.
- Прежние возможности первого PR сохранены; найдённые регрессии исправлены и адресно перепроверены.
- Для каждого ID в чеклисте: status, SHA/идентификатор кандидата, тест/снимок/лог, результат, ограничение при наличии. Исходное состояние — planned, проверки не предзаполнены как успешные.
- Неполные будущие задачи имеют deferred и понятный следующий этап. Недоступный один источник/устройство не отменяет независимую часть пакета; используется локальная fixture/документация/другой браузер, но их доказательная граница сохраняется.
- Интегратор проверил актуальный remote HEAD, состав staged и чужие изменения; создан обычный новый коммит только согласованных файлов. Push в feature/cabinet-polish обновил PR #1, CI нового SHA завершился штатно.
- Финальный отчёт содержит новый SHA, ссылку на CI/PR, что изменилось, чем проверено и что осталось deferred/ограничено хостом. Main не слит, auto-merge выключен.
