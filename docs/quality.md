# Покрытие и воспроизводимость проверки

Покрытие измеряет исполненные строки и ветвления, а не полноту требований. Его дополняют
интеграционные тесты с PostgreSQL, Playwright, контракты, проверки доступа и аварийные прогоны.
Тесты ради процента не добавлялись. Первоначальные измерения ниже предшествуют
cabinet-polish; новые измерения этой ветки приведены отдельно.

## Бэкенд

JaCoCo **0.8.15** подключён общей convention-конфигурацией к четырём сервисам и
`libs/platform-common`. Отдельные HTML/XML — в `*/build/reports/jacoco/test/`, общий отчёт —
`build/reports/jacoco/jacocoAggregateReport/`. Включены все классы `classes/kotlin/main`
этих модулей без ручного исключения контроллеров, инфраструктуры или DTO. Применяются
стандартные фильтры JaCoCo для сгенерированного Kotlin bytecode.

Измерение локального прогона 97 тестов, JDK 21, PostgreSQL 16:

| Область | Покрытые / все строки | Строки |
| --- | --- | --- |
| Все пять модулей | 3809 / 4321 | 88,15% |
| `domain.product` | 98 / 99 | 98,99% |
| `domain.company` | 13 / 13 | 100% |
| `domain.assessment` | 345 / 373 | 92,49% |
| `domain.document` | 41 / 52 | 78,85% |
| `domain.application` | 181 / 184 | 98,37% |
| `domain.user` | 24 / 25 | 96% |

Ветвления всех модулей: 1114 / 1940, **57,42%**. Высокое покрытие строк не означает,
что все комбинации условий проверены.

`./gradlew build` включает задачу `domainCoverage`: **каждый** пакет `domain` должен
покрывать не менее **75% строк**. Порог оставляет небольшой запас от худших измеренных
78,85%, но не позволяет прятать провал одного пакета средним по проекту.
Повышение до 99% действительно завершило проверку ошибкой JaCoCo `Rule violated`;
штатный порог прошёл. Свойство разрешает только повышение в диапазоне 0.75–1.0,
понижение ниже 75% отвергается. Для улучшения прежде всего нужны осмысленные граничные
случаи документов и ветвления инфраструктуры.

```bash
DB_PORT=55432 ./gradlew build
# Отрицательная проверка порога: ожидается ненулевой код и Rule violated
DB_PORT=55432 ./gradlew domainCoverage '-PdomainCoverageMinimum=0.99'
```

## Фронтенд

Vitest и `@vitest/coverage-v8` имеют одну версию **4.1.12**. V8 учитывает весь
`src/**/*.{ts,tsx}`, включая не импортированные тестами файлы; исключены только тесты,
их setup и `.d.ts`. HTML, LCOV и JSON находятся в `frontend/coverage/`.

Первоначальные 15 тестов в 9 файлах дали: строки **291 / 929 (31,32%)**, statements **317 / 1080
(29,35%)**, branches **232 / 956 (24,26%)**, functions **81 / 390 (20,76%)**.
Локально использован Node 25; CI использует Node 20. CI публикует собственный отчёт,
значения могут немного различаться из-за версии V8.

Порог фронтенда не вводился: значительная часть страниц и компонентов не покрыта
модульными тестами. Playwright проверяет важные пользовательские пути, но не прибавляется
к этой метрике. Улучшения тестов компонентов и редизайн остаются задачей владельца фронтенда.

### Измерение cabinet-polish, 24 октября 2026

53 теста в 24 файлах прошли с V8 coverage на Node 20.20.2. Показатели этого локального
прогона: строки **821 / 1553 (52,86%)**, statements **949 / 1878 (50,53%)**,
branches **838 / 1739 (48,18%)**, functions **256 / 640 (40%)**. Это измерение до
последующих адресных CSS-правок якорей/границы навигации; после них отдельно прошли
пять тестов лендинга, lint/build и реальный браузерный прогон ширин. CI публикует
собственное покрытие окончательного SHA.

При неограниченном числе локальных воркеров четыре теста превысили прежний лимит
5 секунд. С двумя threads-воркерами весь набор прошёл за 78,04 с, затем с одним
forks-воркером — за 79,83 с. Таймауты и утверждения не ослаблялись, конфигурация CI
не менялась. Это наблюдение о ресурсах конкретного ноутбука, не сравнение скорости runners.
Новые проверки воспроизводят поздний ответ другой заявки, сохранение фокуса при опросе,
подтверждение/конфликт версий и работу с готовностью файлов; проценты не заменяют
[сквозную приёмку и ограничения](cabinet-polish-review.md).

```bash
cd frontend && npm ci && npm run test:coverage
cd .. && python3 scripts/coverage-summary.py
```

Сводка [quality-results/coverage.json](quality-results/coverage.json) сохраняет исходные
счётчики. В CI артефакты `backend-test-reports` и `frontend-coverage` содержат HTML/XML
и HTML/LCOV/JSON соответственно, в том числе после падения тестов.

## Проверенные артефакты в CI

Job `backend` один раз выполняет полную сборку с тестами, job `frontend` — проверки и
сборку SPA. Они публикуют четыре `app.jar` и `frontend/dist` вместе с SHA256.
Jobs сканирования образов, E2E, demo-history и deployment скачивают эти же файлы,
проверяют хеши, затем выбирают `JAR_SOURCE=prebuilt` / `DIST_SOURCE=prebuilt` через
[ci/compose.yaml](../ci/compose.yaml). OCI revision равен SHA запуска CI;
deployment дополнительно сверяет его у всех пяти образов.

Это устраняет повторную компиляцию в каждом Docker build и позволяет проверять именно
протестированные бинарные файлы. Обычный `docker compose up --build` по-прежнему собирает
исходники внутри Docker. Локальный `prebuilt` требует свежих результатов сборки;
для обычного запуска он не нужен. Результаты длительностей CI сравниваются отдельно:
разные runners и кэши не позволяют считать их строгим измерением ускорения.

Локально путь prebuilt отдельно прошёл [полный prod-прогон](quality-results/prebuilt-production.json):
20 выдач, HTTPS, новый оператор банка, независимое восстановление трёх БД и PDF,
отказ старого JWT после смены ключа и запрет повторного restore в непустую БД.
Пик суммы наблюдаемых Docker memory samples — **1542450050 байт (~1471 MiB)**,
OOM/restarts — 0. Локальная OCI revision — тестовая метка, не SHA коммита;
в CI требуется точный SHA запуска. Несовпадающий release локальный build-helper
отверг до Docker build.
