# Общие лимиты и отзыв сессий

Valkey входит в обычный `docker compose up --build`; отдельного профиля не требуется.
Порт 6379 доступен только контейнерам сети cabinet. Новый `VALKEY_PASSWORD` имеет
локальный демонстрационный default; `deploy/configure.py` генерирует отдельный случайный
секрет. Для существующего prod `.env` добавьте новый URL-safe секрет длиной не менее
32 символов, отличный от остальных. Не меняйте JWT ради добавления Valkey.

| Операция | Общая квота | Ответ при отказе Valkey |
| --- | --- | --- |
| Вход | 5/email/15 мин + 30/IP/мин | 503, пароль не проверяется |
| Восстановление | 3/email/15 мин + 20/IP/15 мин | 503, ссылка и письмо не создаются |
| Файлы, включая чат | 30/user/10 мин | 503 до сохранения файла |
| Сообщения чата | 30/user/мин | 503 до сообщения, аудита и уведомления |
| Вопросы помощнику | 20/user/10 мин | 503 до контроллера |

429 содержит `Retry-After` в секундах. Вход очищает квоту email при правильном пароле;
IP-квота остаётся. Квоты скользящие, время общее — часы Valkey. Gateway продолжает
проверять реальный адрес клиента и перезаписывает внешний `X-Real-IP`.

В `platform-common` доступны настройки `cabinet.valkey.*`: `enabled`, `host`, `port`,
`password`, `connect-timeout` (300 ms), `read-timeout` (500 ms), `pool-wait` (200 ms),
`connections` (16). Compose включает их через `CABINET_VALKEY_*`. Значения ограничены
при старте, пароль не журналируется. Нет автоматического повтора изменяющей Lua-команды
после таймаута. Соединение проверяется PING до выдачи из пула.

Отзыв сессий остаётся строгим во всех сервисах. Valkey хранит монотонную нижнюю границу
версии, достаточную для отказа, но не для допуска. Для допуска всегда нужна свежая
identity. После смены/сброса пароля, logout-all и отзыва сотрудника старый JWT получает
401; совместная недоступность identity и Valkey — 503. Полное решение и границы
гарантий описаны в [ADR 013](adr/013-shared-limits-and-revocation.md).

## Проверка на отдельном синтетическом стенде

```bash
MAIL_MODE=on docker compose -p cabinet-e2e --profile mail up -d --build \
  --scale identity=2 --scale credit=2 --scale engagement=2 --wait --wait-timeout 300
python3 load/shared-state.py --project cabinet-e2e --report-name shared-state
```

Скрипт создаёт собственные синтетические компании, посылает реальные HTTP-запросы
каждой реплике, вызывает рестарт/остановку Valkey и identity, затем FLUSHDB только
выбранного тестового Valkey. Он не запускается на prod и восстанавливает остановленные
контейнеры в `finally`. Отчёт `load/reports/shared-state/verified.json` содержит счётчики,
ID экземпляров, p95, действия и задержки, без JWT, паролей и одноразовых ссылок.

Нативные проверки: PostgreSQL `common_test` на `DB_PORT`, Valkey на localhost:16379
(`VALKEY_TEST_PORT` для другого порта). Настройка реального Valkey и закрытого тестового
пароля приведена в backend job CI. Запуск — `./gradlew :libs:platform-common:test`.
Отсутствующий Valkey даёт ошибку теста, а не пропуск.

## Измеренный прогон 23 октября 2026

[Полный отчёт](security-results/shared-state.json): шесть реальных экземпляров
(по два identity, credit, engagement), отдельный локальный синтетический стенд.
Время HTTP включает Docker exec и работу операции, не только Lua. Валидный файл
проходит настоящий ClamAV и записывается в S3.

| Область | Запросов | Допущено | 429 | p95, с |
| --- | ---: | ---: | ---: | ---: |
| Вход/email | 12 | 5 проверок пароля → 401 | 7 | 0,366 |
| Вход/IP, разные email | 38 | 30 проверок пароля → 401 | 8 | 0,329 |
| Восстановление/email | 8 | 3 | 5 | 0,332 |
| Восстановление/IP | 24 | 20 | 4 | 0,286 |
| Загрузки | 40 | 30 | 10 | 0,430 |
| Чат | 40 | 30 | 10 | 0,359 |
| Помощник | 26 | 20 | 6 | 4,051 |

Каждая строка использует обе реплики. Все 429 содержат положительный Retry-After.
AOF сохранил исчерпанное окно после рестарта. После смены/сброса пароля, logout-all
и отзыва сотрудника все шесть проверок старого JWT дали 401 с первой попытки;
последовательная проверка всех шести закончилась за 1,164–1,269 с после ACK.
Это длительность наблюдения, а не задержка распространения отзыва. Повторное
приглашение оставило старый JWT недействительным и разрешило новый во всех шести.

Отдельно проверены успешный commit отзыва при недоступной публикации в Valkey,
потеря всего кэша и восстановление. Чувствительные операции при отказе дали 503;
совместный отказ Valkey/identity также дал 503. p95 всех 503 — **7,763 с**, включая
Docker DNS и проверки authority. Таймаут TCP-клиента 500 ms не является общей
длительностью HTTP-запроса. При выключенном Valkey последовательная проверка шести
401 заняла до 28,934 с; положительных ответов старому JWT не было.

170 backend-тестов прошли без ошибок и пропусков, включая десять настоящих
интеграционных проверок общего состояния. UI-ошибка входа прошла на 1440 и 375 px
(2 теста, 44,4 с). Это локальные результаты рабочего кандидата; опубликованный SHA
проходит отдельный CI.

## Runbook

1. При росте `cabinet_shared_limits_total{outcome="unavailable"}` проверьте здоровье
   контейнера, память, доступность частной сети, совпадение пароля и состояние AOF.
   Не выключайте лимиты и не очищайте базу для восстановления доступности.
2. Для 429 проверяйте operation и `Retry-After`: это ожидаемый отказ квоты, не отказ
   сервера. Метрики не содержат email/IP/user ID. Разовый таймаут может учесть попытку,
   даже если ответ не дошёл; дождитесь TTL вместо повторного EVAL на уровне клиента.
3. При ошибках `cabinet_revocation_cache_total` чтение продолжает сверяться с identity.
   Недоступная identity должна давать 503, старые JWT не должны проходить. Проверьте
   обе зависимости и повторите контрольный logout-all отдельной тестовой учёткой.
4. После перезапуска AOF сохраняет окна; потеря тома/FLUSHDB обнуляет их и требует
   расследования. Отзыв остаётся в БД. Backup бизнес-данных не включает Valkey;
   штатное восстановление создаёт новое пространство с новым JWT_SECRET.
