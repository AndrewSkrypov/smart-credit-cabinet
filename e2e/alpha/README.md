# Независимая приёмка Alpha

База сравнения — `e5bce6d79e478c7f20fc33fff6d1820c85ee2f63`. Все прогоны ниже предназначены для отдельного локального стека или изолированного CI с синтетическими данными. Для Kafka используйте отдельные топики и группы, для PostgreSQL — отдельные БД, для внешних уведомлений — локальный приёмник. Сценарии восстановления выполняйте в отдельных экземплярах. Порядок запуска и настройки берите у владельца поставки для проверяемого SHA.

## A02–A04. API, паритет и роли

1. Поднимите исходный `credit` и кандидат на одинаковых синтетических данных. Для снимка мигрируйте пустые БД `alpha_qa_*`, остановите writers, установите фикстуру в обе БД и сделайте выгрузку SQL. Загрузите проекцию кандидата штатным bootstrap. Дождитесь контрольной точки и удерживайте данные неподвижными до конца сверки.

   ```bash
   psql -X -v ON_ERROR_STOP=1 "$qa_baseline_db_dsn" -f e2e/alpha/seed-credit.sql
   psql -X -v ON_ERROR_STOP=1 "$qa_candidate_db_dsn" -f e2e/alpha/seed-credit.sql
   psql -XAt -v ON_ERROR_STOP=1 "$qa_baseline_db_dsn" -f e2e/alpha/export-credit.sql > baseline-sql.json
   psql -XAt -v ON_ERROR_STOP=1 "$qa_candidate_db_dsn" -f e2e/alpha/export-credit.sql > sql.json
   cmp baseline-sql.json sql.json
   ```

2. Из хранилища Analytics выгрузите одним statement выбранное поколение проекции по фактическому условию видимости читателя. Формат совпадает с `sql.json`: объект с массивом `rows` из объектов с `id`, `version`, `status` и с картой `currentStatuses`, которую возвращает читатель проекции. Сохраните запрос экспорта и отдельно приложите полный список строк поколения, если хранилище содержит скрытые состояния. Оставьте порядок строк произвольным. Проверка сверит атомарный экспорт SQL, пары `(id,status)`, набор ключей и значения счётчиков. Для этой неподвижной фикстуры `--snapshot-versions` дополнительно сравнивает версию каждой строки с начальным снимком. Снимок содержит 10 заявок, из которых 8 видимы. Ожидаются `WITHDRAWN=2`, `SUBMITTED=2` и по одной `MANUAL_REVIEW`, `REJECTED`, `DISBURSED`, `CLOSED`. Обе отозванные заявки имеют `submitted_at IS NULL`, а две скрытые строки существуют в credit.

3. В изолированном Identity заведите синтетические сессии для пяти ролей и второго клиента из другой компании. Передайте bearer-токены через `ALPHA_QA_CLIENT_TOKEN`, `ALPHA_QA_UNRELATED_CLIENT_TOKEN`, `ALPHA_QA_AGENT_TOKEN`, `ALPHA_QA_MANAGER_TOKEN`, `ALPHA_QA_UNDERWRITER_TOKEN`, `ALPHA_QA_RISK_ADMIN_TOKEN`. Для разных стеков используйте их собственные сессии. Адреса — локальные порты credit или шлюза на loopback.

   ```bash
   python3 e2e/alpha/funnel.py capture --url "$qa_baseline_url" \
     --sha e5bce6d79e478c7f20fc33fff6d1820c85ee2f63 --mode sql > baseline.json
   python3 e2e/alpha/funnel.py capture --url "$qa_candidate_url" \
     --sha "$qa_candidate_sha" --mode shadow > shadow.json
   python3 e2e/alpha/funnel.py verify --sql sql.json --projection projection.json \
     --snapshot-versions --baseline baseline.json --candidate shadow.json
   ```

   Снимите HTTP кандидата также в SQL-режиме и после выключения проекции (`--mode sql` и `--mode off`). После допуска к переключению снимите `--mode projected` с подтверждённой готовностью. Добавьте файлы повторяемым `--candidate`. Метка режима в файле задаётся оператором. В доказательство приложите конфигурацию и наблюдаемый источник ответа по процедуре A09.

4. `verify` сравнивает операцию Swagger, связанные схемы и схему bearer, тела всех успешных ответов и поля ошибок без изменяющихся времени и request ID. Ожидаются `401` без действующей сессии, `403` для клиентов и агента, `200` с одной картой для всех банковских ролей и `400` при равных, переставленных или неразбираемых границах. В окнах февраля и марта ожидаются соответственно две и одна подачи, суммы выдач 1 млн и 0, ноль и один исход `REJECT`. Карта текущих состояний одинакова. Запрос только с `to` проверяет границу `to - 30 дней`. Для запроса без параметров отдельно зафиксируйте диапазон времени запроса, проверьте `to` внутри него, `from = to - 30 дней` и ту же карту. Сверьте исходный снимок с [версией OpenAPI репозитория](../../contracts/openapi/credit.yaml).

5. Для A03 дополнительно прогоните пустую БД, затем БД только с двумя скрытыми состояниями. В обоих случаях ждите `{}` от SQL и проекции. Отдельно через штатный workflow переведите последнюю заявку одного статуса в другой, дождитесь контрольной точки и проверьте исчезновение ключа. Сохраните строки и карты до и после. Повторите для записи с прежним статусом, например `SOURCE_FAILED` при попытке обогащения. Статус и карта сохраняются, Kafka-событие смены статуса отсутствует, JPA-версия может вырасти. У активной проекции сверяйте версию с последней реально применённой записью Kafka или строкой начального снимка. Синтетическая SQL-фикстура моделирует исторические строки. Реальные переходы отдельных сценариев проверяются через A06–A08 и A13.

## A06–A09. Отказы, восстановление и переключение

A05 остаётся у владельца backend. Для ревью запросите обе трассы `Transitions.commit`: смена статуса с откатом и последующим успехом, а также сохранение прежнего статуса без `ApplicationStatusChanged.v1`.

До каждого отказа зафиксируйте один исходный успешный цикл. Используйте те же наблюдатели и ID после восстановления. Берите версии, topic/partition/offset, счётчики и состояния из отдельных соединений или процессов. Запишите дедлайн из настроек кандидата до прогона и ждите по условию с этим пределом. Таймаут или пропуск контрольной точки считается отдельным исходом. Точные имена таблиц, метрик и команд управления возьмите из кандидата и внесите в протокол.

### A06. Повтор и порядок Kafka

- В пустом поколении используйте синтетические UUID и ключ `applicationId`. В одну партицию отправьте `v7 SUBMITTED`, точный повтор с тем же `eventId`, запоздалое `v5 WITHDRAWN`, `v11 REJECTED` с разрывом и конфликт `v11 CLOSED` с новым `eventId`. После обработки каждой записи сохраните строку, подтверждённый offset и результат применения или счётчик мутаций. Ожидаются версии `7, 7, 7, 11, 11`, статус последней строки `REJECTED`, две эффективные мутации и наблюдаемый конфликт.
- Для новой записи следующей версии поставьте тестовый барьер сразу после commit проекции и до подтверждения offset. Увидьте закоммиченные строку и факт применения при ещё не продвинувшемся committed offset группы. Завершите изолированный процесс на барьере, запустите без барьера с той же группой. Убедитесь, что committed-next-offset достиг offset записи + 1, а строка и факт применения остались в единственном экземпляре. Для доказательства повторной доставки сохраните результат повторной обработки или счётчик. Барьер нужен в тестовом процессе кандидата, случайное завершение между стадиями не воспроизводит условие.

### A07. Недоступная Kafka и ack перед подтверждением outbox

- Отключите брокер, сохранив доступность credit и приёмника обычных уведомлений. Выполните штатную подачу или подтверждение с ожидаемым уведомлением. Пока Kafka отключена, зафиксируйте успешный HTTP и сохранённые версию, запись журнала, запись Kafka outbox, следующую pipeline job, а также полученное синтетическое уведомление. Снимите состояние попытки, причину отказа и метрику отдельного канала. Восстановите брокер и проверьте доставку Kafka, точные версии и догон проекции.
- Отдельно остановите изолированный Kafka worker на тестовом барьере после broker ack перед подтверждением outbox. Наблюдайте запись с известными ключом, `eventId` и offset в Kafka при ещё неподтверждённой строке outbox. Проверьте независимую доставку обычного уведомления, пока барьер удерживается. Завершите Kafka worker, дождитесь окончания lease и запустите снова. Ожидайте повтор записи с тем же ключом и `eventId`, последующее подтверждение outbox и одну эффективную мутацию проекции.
- Для управляемого повтора доведите отдельную запись до исчерпания попыток в тестовой конфигурации. Зафиксируйте её состояние и удержание готовности, восстановите брокер, выполните штатный redrive и проверьте переход в доставленное состояние с тем же `eventId`. Повтор только из-за истечения lease и redrive проверяются отдельно.

### A08. Снимок, повтор и восстановление более ранней БД

1. Подготовьте старую строку `v7` до включения записи outbox. Включите захват на всех writers и зафиксируйте начало согласованного снимка. На тестовом барьере снимка через штатный writer доведите заявку до `v11` и создайте ещё одну заявку. В одном прогоне обработайте события до загрузки старой строки снимка, в другом после. Добавьте видимые и скрытые записи и трафик во все используемые партиции. Повторите bootstrap по той же контрольной точке. После догона сверяйте все видимые пары `(id,status)` и карту с SQL, версии — со снимком и результатами применения Kafka. Сохраните открытый outbox и позиции всех партиций до и после готовности.
2. Сохраните ранний backup с `v7` и его SHA-256. Продвиньте исходную БД и старый поток до `v11` и добавьте заявку, отсутствующую в backup. Восстановите backup в новый экземпляр credit. Создайте новое поколение потока и проекции и новую consumer group по процедуре поставки. Оставьте старый поток доступным для контрольного чтения и добавьте в него ещё одну тестовую запись.
3. Пока новая готовность не достигнута, зафиксируйте HTTP с картой восстановленного SQL, отличной от старой проекции, и фактический источник ответа. После bootstrap в новом поколении ожидаются `v7`, отсутствие заявки из старого потока и паритет с восстановленным SQL. Выполните новый переход в восстановленном сервисе и проверьте догон именно через новое поколение. Сохраните идентификаторы поколения, топиков, групп и все позиции партиций.

### A09. Готовность, fallback и сервисный доступ

- Сначала получите готовую проекцию в разрешённом режиме и зафиксируйте положительное чтение из неё. По одному создайте лаг выше утверждённого бюджета в одной из нескольких партиций, открытый или исчерпавший попытки outbox при нулевом Kafka lag, недоступность Analytics, потерю или рассогласование контрольной точки и выключение флага при здоровой проекции.
- Для каждого случая сравните весь HTTP-ответ с SQL, проверьте ожидаемую задержку по настроенному дедлайну, дельту признака `SQL` и причину fallback. Где возможно, используйте различимые карты. При равных картах нужна независимая метрика источника или трасса. Снимите условие отказа и дождитесь подтверждённой готовности перед повторной положительной проверкой. Повторите отказ для неподходящих ролей.
- Если внутреннее чтение опубликовано, проверьте запрос напрямую из тестовой сети в обход шлюза. Без сервисной идентичности, с обычным пользовательским JWT и с неверной сервисной идентичностью доступ закрыт. При штатной сервисной идентичности нужное чтение доступно. Приложите фактическую сетевую политику и результаты HTTP.

## A12–A13. Ревью и регрессии

A12 проводится по полному SHA интегрированного кандидата. Проверьте diff относительно базы и соответствие каждого результата критерию. Для каждой попытки сохраните SHA и дайджесты реально поднятых образов, идентификатор изолированного проекта, время с UTC+03:00, точную команду и код выхода, очищенные логи, запросы, offsets, дельты метрик и хеши выгрузок. Храните прежние попытки рядом с повторными. В отчёте укажите недостающие доказательства и конкретную причину открытого статуса.

Для A13 используйте PostgreSQL из локальной или CI-подготовки репозитория. Проверьте результаты JUnit по классам, в том числе идемпотентную подачу, агентское подтверждение, отзыв мандата, изменение версии продукта, кредитное решение, запись и доставку уведомлений.

### Локальный прогон 26 ноября 2026

- В отдельном PostgreSQL 18.6 с локальным Unix-сокетом запущены миграции credit `V1`–`V18` через `psql -XAt -v ON_ERROR_STOP=1 -f`, затем `seed-credit.sql`, `export-credit.sql` и `funnel.py verify --sql`. Код выхода 0. В SQL восемь видимых строк, две отозванные до подачи и две скрытые. Выгрузки пустой БД и временной таблицы только со скрытыми состояниями совпали. В февральском и мартовском окнах SQL дал соответственно `2/1` подачи, `1000000/0` суммы выдач, `0/1` автоматических решений. SHA-256 файла `sql.json` — `4baf7b2f6e7d2dc5e091edea2734dfde2982d1e1640e3560a6730eed060cc551`.
- Повторное применение фикстуры к наполненной БД завершилось ожидаемым кодом `psql` 3. Две выгрузки до и после попытки идентичны по `cmp`, код 0.
- Python CLI на локальном имитаторе HTTP записал два снимка и сверил HTTP/OpenAPI, статусы и зафиксированные версии, код 0. Сверка статусов с разницей версий также вернула 0. Для режима сверки версий со снимком эта разница, а также отдельные пробы с нулевым ключом, доступом агента и изменением OpenAPI завершились ожидаемым кодом 1. Имитатор проверял инструмент QA.
- `docker info --format '{{.ServerVersion}}'` завершился с кодом 1, сокет Docker отсутствует. Gradle 8.10.2 и Java 21 в пробе `--offline :services:credit:test` с шестью классами credit из команды A13 завершились с кодом 1 до запуска JUnit. В локальном кэше не разрешился плагин `com.github.jk1.dependency-license-report:3.1.4`. Эти попытки оставляют runtime-критерии открытыми.
