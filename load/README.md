# Нагрузка, падение и гонки

Нужны Python 3.10+, Docker Compose v2 и отдельный синтетический стенд. Скрипты разрешают
только проекты `cabinet-submission`, `cabinet-reliability`, `cabinet-e2e` и их суффиксы.
Это защита от случайного выбора обычного проекта, а не проверка содержимого произвольного сервера.
`--base` должен указывать на gateway **того же** проекта: HTTP-проверки сверяются с его PostgreSQL.

Первый запуск из корня (порт можно поменять через `GATEWAY_PORT`, затем передать `--base`):

```bash
python load/start.py --project cabinet-reliability --replicas 2 --build
python load/run.py --project cabinet-reliability --companies 20 --label normal
```

Для уже собранных образов повторный `start.py` запускается без `--build`. Параметр
`--replicas 1` нужен для сравнения с одним экземпляром; базовая конфигурация приложения
не меняется. Все команды ниже тоже выполняются из корня.

## Что измеряет k6

`run.py` регистрирует отдельные компании с корректными ИНН `00`, создаёт по одному
черновику и запускает `grafana/k6:1.3.0`. Подготовка проходит до нагрузки, с паузой
2,1 с между регистрациями для соблюдения настоящего лимита gateway.

В нагрузке N виртуальных пользователей одновременно отправляют свои заявки, опрашивают
статус раз в 0,5 с и получают `OFFER_ISSUED`/`REJECTED`. Если правила направили заявку
специалисту, отдельный токен андеррайтера подтверждает её с объяснением. Поэтому время
до решения включает этот реальный API-вызов; это не только время автоматического скоринга.
Для обычной когорты 1 млн ₽ на 12 месяцев обязательных документов нет.

Проверки: все HTTP-коды, отсутствие ошибок HTTP, ровно N решений, один SUBMIT, отсутствие
двойных переходов статуса, максимум один оффер, отсутствие FAILED/незавершённых рабочих
задач в БД. Отложенные задачи истечения оффера остаются открытыми по назначению.

`cabinet_api_ms` — время HTTP-запросов отправки, чтения и ручного решения;
`cabinet_decision_ms` — от начала submit до наблюдаемого решения (включая интервал опроса).
Сохраняются p50 (`med`), p95, p99 и число решений в секунду. Это конечная пачка,
а не измерение предельной устойчивой производительности. В отчёт входят ID образов,
лимиты памяти и SHA проверочного кода; SHA сам по себе не устанавливает версию уже
запущенного контейнера. У k6 поле `http_req_failed.values.passes` считает истинные
значения «запрос не удался», `fails` — ложные; ориентируйтесь на `rate` и `http_reqs`.

## Балансировка

```bash
python load/chaos.py balance --project cabinet-reliability --cohort normal
python load/chaos.py disburse --project cabinet-reliability --cohort normal
```

После ожидания обновления DNS выполняются 100 запросов. Журнал gateway содержит
`upstream_addr` и безопасный `X-Request-Id`; проверяются оба IP реально работающих
контейнеров и все 100 ответов 200. Токены и тела в этот журнал не пишутся.
`disburse` принимает и подписывает все офферы этой когорты параллельно, затем проверяет
по одному DISBURSED, кредиту и DONE-задаче выдачи на заявку. Запускать до истечения
офферов; это самостоятельная проверка после измерения времени до решения.

## Принудительная остановка и аренда

```bash
python load/run.py --project cabinet-reliability --companies 20 --label crash --prepare-only
python load/chaos.py crash --project cabinet-reliability --cohort crash
```

Когорта должна быть свежей. Скрипт одновременно отправляет заявки и ждёт больше десяти
RUNNING-задач этой когорты: один воркер держит максимум десять перед последовательной
обработкой, значит оба экземпляра захватили работу. Один контейнер целевого проекта
принудительно останавливается `docker stop --time 0`; проверяется exit 137.
Второй подхватывает задачи после аренды, все заявки доходят до решения. Проверяются
повтор захваченной задачи, журнал и отсутствие двойных офферов. Остановленный контейнер
запускается в `finally`, в том числе после ошибки проверки.

В override аренда уменьшена с 2 минут до 15 секунд, ожидание источника — до 45 секунд,
таймаут HTTP-источника — до 2 секунд. Это ускоренные условия эксперимента; они не доказывают
такое же время восстановления с базовыми настройками. Возможные 502/503/504 во время
падения учитываются отдельно; окончательные инварианты не смягчаются.

## Недоступный/медленный источник и дедлайн

Для каждого режима нужна новая когорта:

```bash
python load/run.py --project cabinet-reliability --companies 10 --label source-down --prepare-only
python load/chaos.py recover-down --project cabinet-reliability --cohort source-down
```

Повторить с другими метками для `recover-slow` и `timeout`. Скрипт переключает БКИ
через настоящий `/sim/control`, проверяет SOURCE_FAILED и отказ вызова открытым breaker.
В `recover-*` БКИ включается до дедлайна: все заявки продолжаются без SOURCE_TIMED_OUT.
В `timeout` сбой сохраняется: каждая заявка попадает в MANUAL_REVIEW с SOURCE_TIMED_OUT.
Исходный режим БКИ восстанавливается в `finally`. Принудительное завершение всего процесса
не даёт этой гарантии — проверьте пульт вручную перед следующим сценарием.

## Одновременные действия

```bash
python load/run.py --project cabinet-reliability --companies 6 --revenue 999000000 --label races --prepare-only
python load/chaos.py races --project cabinet-reliability --cohort races
```

Завышенная заявленная выручка гарантирует направление к специалисту из-за расхождения
с синтетической ФНС; реальные данные не подменяются. Две одновременные отправки с одним
ключом дают 200/200 либо 200/409 при конфликте версии; последующий повтор тем же ключом
даёт 200 и остаётся один SUBMIT. Затем одновременно выполняются отзыв и **отказ**
андеррайтера: строго один 200, один 409 и один терминальный переход. Отказ выбран потому,
что он закрывает заявку; после одобрения разрешён отдельный последующий отзыв оффера,
и последовательные 200/200 сами по себе не означали бы потерю обновления.

Регрессия позднего callback после отмены — `ApplicationApiIntegrationTest`,
тест `a withdrawn running job cannot be revived by a stale worker`:

```bash
DB_PORT=55432 ./gradlew :services:credit:test --tests '*ApplicationApiIntegrationTest*'
```

## Отчёты и повторный запуск

В `load/reports/<метка>/` сохраняются сводка k6, журнал и проверки API/SQL.
`cohort.json` содержит временные токены тестовых компаний: каталог исключён из Git,
Docker build context и CI-артефактов. Не публикуйте его. Новая метка и новые компании
нужны для каждого прогона: существующий каталог не перезаписывается.
Скрипты не удаляют БД или тома. Остановить только свой стенд:
`docker compose -p cabinet-reliability down`. Измеренные результаты и ограничения —
в [docs/reliability.md](../docs/reliability.md).
