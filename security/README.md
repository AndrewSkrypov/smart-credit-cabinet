# Проверки безопасности

`python security/db-permissions.py --project cabinet-e2e --report-name db-permissions`
проверяет реальные runtime-роли через TCP: чужие базы, DDL и изменение аудита запрещены,
свой CRUD и default grants работают. [Устройство и восстановление прав](../docs/database-isolation.md).

Запускать только на отдельном локальном синтетическом стенде. Матрица и негативные
проверки разрешают `localhost`/`127.0.0.1`/`::1` и проекты `cabinet-submission`,
`cabinet-reliability`, `cabinet-e2e` с необязательным суффиксом. `--base` и `--project`
должны описывать один стенд; проверки не предназначены для изменения внешнего сервера.

## Матрица всех операций

После установки Python-зависимостей [контрактов](../contracts/README.md):

```bash
python security/matrix.py --check-only
python security/matrix.py --project cabinet-submission
python security/negative.py --project cabinet-submission
```

Матрица использует PyYAML 6.0.3; негативные проверки — только стандартную библиотеку.
В PowerShell можно использовать `../.venv/Scripts/python.exe`, если окружение контрактов
создано рядом с репозиторием. Базовый URL — `http://localhost:8080`, меняется `--base`.

Ожидания находятся в [access-policy.json](access-policy.json), читаемая таблица —
[access-matrix.md](access-matrix.md). Это явная политика, а не ожидаемые коды, полученные
из текущего ответа сервера. Список из всех четырёх OpenAPI проверяется на точное
совпадение: новая операция или пропущенная роль останавливает проверку. Для обновления
читаемой таблицы после осознанного изменения политики: `python security/matrix.py --write-table`.

53 операции × 6 ролей = 318 проверок. Девять системных `/ext/` входят в полноту
контракта и должны давать 404 через gateway для всех пользовательских ролей; отдельно
проверяется их `X-Api-Key` внутри Docker. 204 — предусмотренный контрактом успех без тела.
400/409 не используются как замена успешного доступа в матрице.

Новые компании создаются по API. Для каждого действия подготовлено допустимое состояние:
черновик, отправленная заявка на ручном рассмотрении, запрос сведений с загруженным файлом,
оффер или подписание. При двух разрешённых ручных действиях используются разные заявки.
Личные уведомления готовятся через внутренний API engagement в сети целевого проекта.
После проверки открытые заявки отзываются; режимы источников и параметры правил
восстанавливаются в `finally`. Ошибка восстановления не считается успешным прогоном.

## Негативные сценарии

Проверяются IDOR заявки, документа (в том числе чужой файл через свою заявку), уведомления
и помощника; поддельная подпись, изменённая роль, `alg=none`, правильно подписанный
просроченный токен; отсутствие права подписи; игнорирование роли/компании из заголовков
и companyId из JSON; поддельный PDF; внешние ссылки уведомлений; границы gateway;
системный ключ; заголовки браузера; ограничения входа, загрузок и помощника.

Для проверки срока и `sign=false` тест читает **ключ только локального тестового
контейнера**, создаёт контролируемые подписанные фикстуры в памяти и сначала доказывает
работоспособность повторной подписи. Это не возможность внешнего клиента менять claims:
изменение роли без новой подписи должно возвращать 401. Ключи, JWT и коды подписи не
сохраняются в отчётах и не выводятся в лог. Производственный ключ для этих тестов не нужен.

Лимиты сервиса считаются на экземпляр. При нескольких credit число принятых загрузок
до первого 429 зависит от распределения по экземплярам; скрипт учитывает их реальное
число. Ограничение входа проверяется и для одной учётной записи, и для адреса gateway.
Для ожидания пополнения лимита адреса после всплеска оставлена пауза 6 с.
Регрессия формата ответа gateway запускается отдельно: `python security/gateway_rate.py`.
429 должен быть JSON с русским объяснением, временем, `Retry-After` и ID, совпадающим
с заголовком. Путь в этой ошибке обозначает общую зону `/api/v1/auth/`.

## Аудит npm

```bash
python security/audit-dependencies.py
```

Проверяются frontend, e2e, contracts/postman, scripts/license-tools с dev-зависимостями.
Критичные пакеты блокируют CI; прочие находки остаются в полном отчёте. Сохранённый
отчёт можно проверить тем же gate: `python security/audit-dependencies.py --report путь.json`.
Ненулевой код npm из-за некритичных находок не скрывает сами находки; ошибки сети/формата
не превращаются в успешный аудит.

## Trivy и проверка исключений

```bash
python security/check-exceptions.py
python security/scan.py --report-name source
python security/scan.py --image smart-credit-cabinet-credit --report-name credit
```

В последней команде укажите реальный локальный тег из `docker compose images`.
Сканер закреплён версией и digest. Исходники берутся из HEAD, образ — по image ID;
сначала зафиксируйте изменения, которые нужно включить в проверку. При первом запуске
нужны сеть и место для баз CVE и Java. Кэш — отдельный том `cabinet-submission-trivy-cache`.
CRITICAL с исправлением и любая находка секрета дают ненулевой код. Прочие CVE и два
ограниченных исключения сохраняются в отчёте. Обоснования — в [docs/security.md](../docs/security.md).
В JSON секретных находок остаются только правило, категория, уровень, заголовок и строки;
само значение и фрагмент кода удаляются до экспорта. Входной tar удаляется после отчёта;
`--keep-archives` оставляет его локально и не предназначен для CI-артефактов.
Для большого образа используется `--remote --image имя@sha256:digest`: сканер читает
закреплённый образ из registry с параллелизмом 1, без локального pull и второго Docker save.
Тег без digest в этом режиме отклоняется. Это сохраняет проверку всех слоёв и секретов,
но не требует двух полных распакованных копий GPU runtime на диске CI runner.

## Сохранение отчётов

`security/reports/access-matrix.json`, `negative.json`, `npm-audit-summary.json` и полные
`npm-*.json` содержат фактические результаты. Каталог исключён из Git и Docker build
context. В CI доступны `access-security-reports` и `npm-audit-reports`; сессионных токенов
в них нет. Скрипты не удаляют тома или базы. Все учётные записи и документы синтетические.
